Installer Atlas

Atlas est un outil de bureau local : un daemon sur 127.0.0.1, ta machine, tes repos. Son paquet est privé pendant la bêta. Voilà comment demander l'accès, exactement ce qu'il faut taper, et à quelle condition.

La condition, avant la commande

Atlas se distribue comme un paquet npm global, @gregoirelacoste/atlas. Il est publié sur GitHub Packages et rattaché au dépôt de distribution gregoirelacoste/atlas-dist — un dépôt qui ne contient aucun code : il ne fait que porter le droit d'installer.

Installer depuis le registre demande donc deux choses : un jeton GitHub — un PAT classique, portée read:packages — et que le compte qui le porte ait accès à ce dépôt de distribution. Sans cet accès, les commandes ci-dessous échouent sur un refus du registre, et elles ne s'arrangeront pas d'elles-mêmes.

Obtenir l'accès : la bêta

L'accès se demande par un formulaire — s'inscrire à la bêta. C'est une issue GitHub, donc publique : ton compte suffit, n'y mets rien que tu ne dirais pas en public. Si c'est oui, une invitation en lecture sur le dépôt de distribution arrive par le mail de ton compte GitHub ; l'accepter est ce qui rend les trois lignes ci-dessous possibles. Rien n'est automatique : quelqu'un lit la demande, et répond dans le fil.

Il n'y a pas de version hébergée à essayer : Atlas ne tourne nulle part ailleurs que sur ta machine. Sans l'accès, la seconde voie ci-dessous — un fichier .tgz qu'on te remet — est la seule.

Avant de commencer

  • Node ≥ 20 (node -v), et git avec tes accès habituels aux dépôts.
  • Tes repos déjà clonés côte à côte sous un même dossier — c'est ce dossier, le chapeau, qu'Atlas analyse. Le nom et l'emplacement n'ont aucune importance : tout sous-dossier qui contient un .git est découvert tout seul.
  • Du JavaScript ou du TypeScript. Atlas sait ce que sont Nest, Angular, GraphQL, Jest, React, Next, Vue, Nuxt, Svelte, Express, Fastify, Hono, Koa et axios — .tsx, .vue, .svelte compris, un mono-repo lu comme du back là où c'est du back. Un projet écrit dans un autre langage n'a aujourd'hui aucun chemin de configuration.

Depuis le registre

Trois lignes, à taper une seule fois — les deux premières déclarent le registre et le jeton dans ta configuration npm, la troisième installe :

npm config set @gregoirelacoste:registry https://npm.pkg.github.com
npm config set //npm.pkg.github.com/:_authToken <ton PAT>
npm i -g @gregoirelacoste/atlas@latest

Une fois la commande atlas posée dans ton PATH, tu n'auras plus jamais à retaper ces lignes : c'est ce que fait atlas update (plus bas).

Depuis un fichier .tgz

C'est la voie de quelqu'un qui n'a pas encore accès au registre : on lui remet le fichier produit par l'outil, et il l'installe comme n'importe quel paquet local.

npm i -g /chemin/absolu/vers/atlas-x.y.z.tgz

⚠️ Le chemin doit être absolu, ou commencer par ./. Un chemin relatif du genre paquets/atlas-0.1.10.tgz est lu par npm comme un dépôt GitHub du même nom, et échoue sur « Repository not found » — message trompeur, le fichier est bien là.

Vérifier ce qui tourne

atlas version   # la version de l'instance qui tourne (ou, sans daemon, celle installée sur le disque)
atlas status    # pareil, plus l'état du daemon et son pid

atlas version imprime un JSON brut — au minimum la version, et selon l'origine du paquet le commit, la date, la branche. atlas status ressemble à ceci :

● en marche — http://127.0.0.1:3030 (pid 48213)
  version : {"version":"0.1.44","commit":"a1b2c3d","date":"2026-09-01T10:00:00Z","branch":"package"}

— ou ○ arrêté si rien ne tourne. C'est la première chose à taper quand on ne sait plus quelle version on a sous les yeux : le commit dit exactement ce qui tourne, pas une branche.

Le premier projet

cd mon-chapeau   # le dossier qui héberge tes repos — pas un repo
atlas init       # déclare le projet : .atlas-workspace/ à côté de tes dépôts
atlas            # démarre le daemon, active ce projet, ouvre le navigateur

atlas init crée .atlas-workspace/ : les règles du projet, un dossier par fonctionnalité à venir, et un .gitignore qui rend ce dossier sûr à versionner. Il n'écrase jamais rien s'il existe déjà, il ne fait pas git init, et il n'installe pas le plugin IA à ta place — celui-ci touche ta configuration globale, il se demande à part (atlas plugin install).

⚠️ Lance ces commandes dans le dossier qui contient tes repos, jamais dans un repo lui-même : un repo n'a pas de sous-dossier .git en plus du sien, et Atlas y produirait un chapeau à zéro membre, donc une carte vide.

La suite — déclarer une fonctionnalité, ce qu'il faut pour qu'une carte s'affiche, le tour de l'écran — est dans la prise en main.

Rester à jour

Une seule commande, pour tout le monde : atlas update. Elle installe la dernière version publiée, redémarre le daemon, et rafraîchit le plugin IA s'il est déjà posé. Quand elle échoue, c'est presque toujours le registre ou le jeton — elle te redonne alors les deux lignes npm config set ci-dessus.

Atlas ne se met jamais à jour tout seul : il n'existe aucune route ni aucun automatisme qui installerait quoi que ce soit derrière ton dos. Quand une version plus récente existe, la page Config le dit — à jour, une version existe, ou « je n'ai pas pu regarder » avec sa raison — et c'est toujours toi qui tapes la commande.

Ce qui sort de ta machine

Il n'y a pas de serveur d'Atlas : rien ne remonte nulle part, et il n'y a aucun compte à créer. Deux destinations seulement reçoivent une requête, et tu les connais déjà : ton hébergeur de dépôt — GitLab ou GitHub — pour la conversation d'une revue (merge ou pull request), et ton registre npm, pour savoir s'il existe une version plus récente. Atlas n'écrit chez l'hébergeur que sur un clic confirmé.

Limites connues

  • atlas update n'est éprouvé que sous Linux : la façon dont il retrouve le binaire fraîchement installé suppose une disposition de fichiers qui ne tient pas encore sous Windows.
  • Le paquet étant privé, sans registre ni jeton configurés la page Config ne peut pas dire s'il existe une version plus récente. Elle le dit — « je n'ai pas pu regarder » — plutôt que d'afficher « à jour » par défaut.
  • React, Vue et Svelte ont chacun leur stack : couches, points d'entrée sur les événements de l'interface, et pour Vue et Svelte un plugin dédié qui lit le gabarit embarqué dans le fichier (.vue, .svelte) — React s'appuie directement sur le même lecteur que le reste du TypeScript, JSX compris.
