Prise en main

Installer Atlas, lancer le daemon, déclarer ton premier projet et ta première feature — de l'écran d'accueil jusqu'à ta première carte.

Installer Atlas, lancer le daemon, déclarer ton premier projet et ta première feature — de l’écran d’accueil jusqu’à ta première carte.

Atlas reconstruit, pour une feature à la fois (un ticket : PROJ-412, FOO-42…), la carte de son code : quelle entrée, quelles méthodes appelées, à travers combien de services — pour que tu valides plutôt que tu ne relises fichier par fichier. Cette page t’amène du paquet installé à cette première carte ; le reste de la documentation part de là (voir le README de cette doc).

Installer le paquet

Atlas est un outil de bureau local : rien à déployer, un seul daemon qui écoute sur 127.0.0.1, mono-utilisateur, mono-machine. Il sert à la fois l’API et la page web sur un unique port. Il se distribue comme un paquet npm global, @gregoirelacoste/atlas — privé, hébergé sur GitHub Packages via le dépôt de distribution gregoirelacoste/atlas-dist (il ne contient aucun code, il ne fait que porter le droit d’installer).

Deux façons de l’obtenir :

  • On te donne un .tgz (le fichier que produit npm run pack, pour quelqu’un qui n’a pas encore accès au registre) :

    npm i -g /chemin/absolu/vers/atlas-x.y.z.tgz

    ⚠️ Le chemin doit être absolu (ou commencer par ./). Un chemin relatif comme dist-pkg/atlas-0.1.10.tgz est lu par npm comme un dépôt GitHub du même nom, et échoue sur « Repository not found ».

  • Tu as accès au registre — il faut le déclarer une fois, avec un jeton (PAT classique, portée read:packages) :

    npm config set @gregoirelacoste:registry https://npm.pkg.github.com
npm config set //npm.pkg.github.com/:_authToken <ton PAT>
npm i -g @gregoirelacoste/atlas@latest

Les deux posent une commande atlas dans ton PATH. Une fois qu’elle existe, tu n’auras plus jamais à retaper ces commandes toi-même : c’est ce que fait atlas update (plus bas).

Vérifier ce qui tourne

atlas version   # la version de l'instance qui tourne (ou, sans daemon, celle installée sur le disque)
atlas status    # pareil, plus l'état du daemon et son pid

atlas version imprime un JSON brut — au minimum version, et selon l’origine du paquet commit, date, branch. atlas status ressemble à ceci :

● en marche — http://127.0.0.1:3030 (pid 48213)
  version : {"version":"0.1.44","commit":"a1b2c3d","date":"2026-09-01T10:00:00Z","branch":"package"}

— ou ○ arrêté si rien ne tourne. C’est la première chose à taper si tu ne sais plus quelle version tu as sous les yeux : le commit dit exactement ce qui tourne, pas une branche.

Rester à jour

atlas update

Une seule commande, pour tout le monde : elle installe la dernière version publiée (@gregoirelacoste/atlas@latest), redémarre le daemon, et rafraîchit le plugin IA s’il est déjà installé. Si elle échoue, c’est presque toujours le registre ou le jeton : elle te redonne alors les deux lignes npm config set ci-dessus.

Atlas ne se met jamais à jour tout seul. Quand une version plus récente existe, Config › Atlas te le dit (trois états : à jour, une version existe, ou « je n’ai pas pu regarder » avec sa raison) ; c’est toujours toi qui tapes atlas update.

Si tu es dans un clone du dépôt Atlas lui-même, atlas update te prévient avant d’agir : il installerait la dernière version publiée, pas ton code en cours. atlas promote fait ce second geste — il n’apparaît dans atlas help que là où il peut servir, c’est-à-dire près d’un clone.

Le daemon

commande effet
atlas démarre le daemon si besoin, active le projet du dossier courant, ouvre le navigateur
atlas start démarre le daemon (port 3030 par défaut)
atlas stop l’arrête
atlas restart stop puis start
atlas status l’état et la version de l’instance qui tourne
atlas logs suit les logs du daemon (les 20 dernières lignes, puis en direct)

Le daemon sert l’API et la page web sur le même port — pas deux serveurs séparés. Le port se change avec ATLAS_PORT (ou PORT) ; pid et log vivent sous ~/.local/state/atlas/ (ou $XDG_STATE_HOME/atlas), un fichier par port — deux instances sur deux ports coexistent sans se marcher dessus.

Une seule instance sert cependant un seul projet actif à la fois : atlas tapé depuis un autre chapeau bascule dessus à chaud, sans redémarrer — c’est start/stop/restart/status qui pilotent le daemon lui-même, indépendamment du dossier où tu te trouves.

Le workspace : le dossier qui héberge tes repos

Atlas n’analyse jamais un seul repo : il analyse un chapeau, le dossier qui héberge côte à côte tous les repos d’un même projet. Sa configuration vit dans un sous-dossier .atlas-workspace/, trouvé par remontée depuis le dossier où tu lances atlas — exactement comme git trouve son .git/. Tu peux donc lancer atlas depuis n’importe quel sous-dossier du chapeau, pas seulement à sa racine.

Les repos membres sont auto-découverts : tout sous-dossier direct du chapeau qui contient un .git en est un, sans rien à déclarer un par un. Le détail — exclure un repo, forcer un motif de branche, une ligne de production par repo — est dans Configurer un projet.

⚠️ atlas init (et atlas tout court) doivent se lancer dans le dossier qui contient tes repos, jamais dans un repo lui-même. Un repo n’a pas de sous-dossier .git en plus du sien : y lancer Atlas produit un chapeau à zéro membre, et une carte vide.

atlas init : déclarer un projet

atlas init [DIR] [--stack a,b]

Sans argument, DIR est le dossier courant. La première fois (aucun .atlas-workspace/ là), atlas init crée project.json (les règles du projet), un dossier features/ vide, un .gitignore et un ESPACES.md — pour que versionner ce dossier soit sûr, et pour rappeler qui écrit quoi dedans. Si .atlas-workspace/ existe déjà, atlas init le dit et n’écrase rien. Un aperçu de ce qu’il annonce, sur un chapeau à deux repos :

✓ stacks DÉTECTÉES dans 2 repo(s) : nest, react, typescript  (dépendances déclarées)
✓ repos FRONT détectés : projet-front  (dépendance @angular/core, react…)
✓ features par TICKET : 7 branche(s) sur 12 portent un jeton (PROJ-123…) — `featureId: "ticket"`
✓ ligne de base : `develop` — détectée dans 2 repo(s) (`base` dans project.json, éditable dans Config › Projet)
✓ /home/toi/mon-chapeau/.atlas-workspace créé (project.json + features/ + .gitignore + ESPACES.md)
  · stacks actives : nest, react, typescript (prouvées par les dépendances — re-dérivées à chaque chargement, rien n'est copié)
→ édite /home/toi/mon-chapeau/.atlas-workspace/project.json (stack, couches, repos membres) puis :  cd /home/toi/mon-chapeau && atlas

Les stacks — ce qu’Atlas sait d’un framework — n’ont pas besoin de --stack pour s’activer : à chaque chargement, Atlas lit les dépendances déclarées dans les package.json de tes repos membres et allume tout seul ce qu’elles prouvent. Quinze sont livrées : angular, axios, express, fastify, graphql, hono, jest, koa, nest, next, nuxt, react, svelte, typescript, vue. La dernière couvre aussi le JavaScript pur. Le détail est dans Les stacks et project.json. --stack a,b sert à forcer une décision explicite (ajouter une stack que rien ne prouve, ou en refuser une qui l’est) ; une stack inconnue fait échouer la commande, qui liste alors celles qui existent.

atlas init détecte aussi trois choses et les écrit comme des décisions, modifiables ensuite : les repos qui rendent une interface, ce qui fait une feature ici (un jeton de ticket dans le nom des branches, ou bien chaque branche), et la ligne de base — la branche à laquelle une feature est comparée. En cas de désaccord entre repos, rien n’est écrit et il le dit.

atlas init n’installe pas le plugin IA (atlas plugin install, à part — voir Brancher l’IA) : toucher ta configuration globale de session de code est un geste de confiance qui se prend à part. Il ne fait pas non plus git init, et il ne copie aucun fichier de stack dans ton workspace — elles vivent dans l’outil et suivent ses mises à jour.

Partager cette config avec l’équipe se fait en versionnant .atlas-workspace/ (le .gitignore posé protège déjà ce qui doit rester personnel — ta lecture des fils, tes validations) ; un collègue la reçoit avec git clone <url> .atlas-workspace au lieu de relancer atlas init.

Le registre des projets

Atlas garde la liste des projets que tu as ouverts dans ~/.config/atlas/config.json (ou $XDG_CONFIG_HOME/atlas/config.json) — l’équivalent des « projets récents » d’un IDE, rangé hors de tout workspace. Tu le gères depuis ⚙️ Config › Projet, chapitre « Projets connus » : activer un projet (bascule à chaud, sans redémarrer), en ajouter un par son chemin, en retirer un (ça ne touche rien sur le disque). Au démarrage du daemon, le dernier projet actif du registre l’emporte sur la découverte automatique du dossier courant, tant qu’il pointe encore vers un vrai workspace.

L’accueil : l’écran sans feature

atlas ouvre le navigateur sans feature. Ce que tu vois alors n’est pas une carte vide, c’est une page d’accueil — et c’est aussi ce que tu retrouves en quittant une feature (le bouton ⊘ tous les repos du panneau Git). De haut en bas :

  • la marque, puis la promesse : « Relire et endosser le code d’une feature, flux par flux. » — un flux est un chemin d’appel complet, de l’entrée jusqu’au bout ; endosser, c’est dire « j’ai relu cette ligne et je la prends à mon compte ». Sous elle : « La carte d’un ticket à travers ses repos : ce qui a changé, qui l’appelle, et un rond par symbole à endosser. »
  • la touche maîtresse en une phrase — « Espace ouvre la boîte des raccourcis : une lettre choisit une colonne, la suivante agit. Échap ferme. » — suivie des sept colonnes de l’écran avec leur lettre : disposition, volet gauche, Arbre, Code, recherche, Git, pages ;
  • cinq gestes, cliquables, chacun avec sa touche ;
  • les dernières features ;
  • un pied : « Espace pour commencer ».

Les cinq gestes, dans l’ordre où la page les pose :

Touche Le geste, tel qu’il est écrit Sans feature
Espace p t « Choisir une feature — le Tableau » actif
Espace s g « Chercher dans le contenu des fichiers » atténué — « sans feature »
Espace s f « Ouvrir un fichier par son nom » atténué — « sans feature »
Espace g m « Les repos du chapeau — le panneau Git » actif
Espace p c « Config — projet, repos, IA » actif

Un geste qui ne peut rien faire ici n’est ni caché ni gris muet : il est atténué avec sa raison en clair, et son clic ne fait rien. Les deux qui le sont cherchent dans les fichiers de la feature ouverte — sans feature, il n’y a rien où chercher. Cliquer un geste actif joue exactement le même accord que la touche : la page ne fait rien que le clavier ne fasse.

Sous les gestes, Dernières features liste jusqu’à six features, la dernière poussée d’abord (le même ordre que le Tableau ; celles que rien ne date passent après). Chaque ligne porte son id, son titre et la colonne où elle tombe ; un tiret quand elle n’est dans aucune colonne. Cette liste ne paie ni l’historique git ni l’hébergeur : la colonne affichée y vaut donc « En cours » pour une feature que le Tableau rangerait plus loin — c’est lui qui tranche. Elle a ses trois états : en cours de chargement, l’erreur en clair (« pas pu lister : … »), ou « aucune feature déclarée — ▦ Tableau pour en déclarer une ». ▦ toutes les features ouvre le Tableau.

Deux choses restent à l’écran sur l’accueil. Le header, qui affiche 📍 aucune feature, les deux boutons de page et la version. Et le panneau Git, en bas : c’est le seul panneau qui parle encore de quelque chose, puisque sans feature il liste tous les repos du chapeau.

⚠️ Une page ouverte à ta dernière visite garde la main : si tu as quitté Atlas sur le Tableau ou sur Config, tu les retrouves au démarrage, et c’est Échap qui les referme sur l’accueil.

Choisir ou déclarer ta première feature

Depuis l’accueil, ▦ Tableau (Espace p t) montre toutes les features du projet, rangées en colonnes par ce qu’il reste à faire ; un clic sur l’une d’elles charge sa carte. Le détail des colonnes est dans Le Tableau.

Si ta feature n’existe nulle part encore, la colonne Déclarée porte un bouton ＋ : c’est le seul endroit du produit où une feature peut naître sans qu’une branche existe déjà. Il te demande un identifiant, un titre (optionnel), puis Déclarer. Deux saisies sont acceptées : un id de ticket (PROJ-412), ou un nom de branche collé — feat/login-bug déclare login-bug, jamais feat-login-bug. À l’ouverture du formulaire, Atlas cherche déjà sur origin les branches qui portent un identifiant, pour te les proposer en autocomplétion ; s’il n’a pas pu les lire, il le dit et propose de réessayer plutôt que de déclarer à l’aveugle.

Si l’id que tu tapes correspond à une branche déjà trouvée sur origin, ses repos sont pré-déclarés — la feature se lit alors directement sur refs, sans rien avoir à sortir localement. Si l’id n’existe encore nulle part, Atlas pose une spec vierge (ticket.md) à côté : tu es en train de créer le ticket, pas de reprendre du code. Et si l’id existe déjà, « Déclarer » ne renvoie pas une erreur : Atlas rouvre simplement la feature qui existe.

Ta première carte

Ce qu’il faut pour qu’une carte s’affiche : au moins un repo du chapeau doit porter une branche que ton projet reconnaît comme celle de cette feature — un nom qui contient l’id exact du ticket (feat/PROJ-412-paging convient, PROJ-41 ne matche jamais PROJ-412), ou, si le projet compte ses features par branche, la branche elle-même. Cette branche est alors comparée à la ligne de base : celle déclarée pour la feature, sinon celle du projet, sinon la variable d’environnement BASE, sinon develop (Configurer un projet).

Tant qu’aucune branche ne porte l’id nulle part, la feature reste sur « Déclarée » : ce n’est pas un retard, c’est l’état normal d’un ticket qu’on vient d’ouvrir — et si tu ouvres quand même sa carte, l’Arbre le dit plutôt que de rester silencieux : « Aucun fichier touché : le diff avec est vide — la branche n’a pas encore de commit. Rien à lire, et ce n’est pas un défaut de détection. »

Le tour de l’écran

Une fois une feature ouverte, l’écran se partage en quatre zones fixes, plus deux pages qui les remplacent entièrement — et, sans feature, l’accueil décrit plus haut.

Le volet gauche, en trois familles d’onglets :

Onglet Sous-onglets Ce qu’il montre
● Relecture — ce qu’il te reste à relire, en lignes — voir Relire et endosser
🗂 Fichiers Fichiers · Inventaire l’explorateur du chapeau avec le diff marqué en place, et son jumeau chiffré par famille — voir Fichiers et Inventaire
🧭 Parcours Ticket · Parcours · Journal la spec et ce qu’on a compris, les étapes cliquables du flux, et tous les fils par date — voir Ticket, fils et Journal

L’Arbre, au centre : tout le diff de la feature, rangé par chemin d’exécution plutôt que par fichier — voir L’Arbre.

Le Code, à droite : la source live du nœud sélectionné, avec ses liens et ses fils de conversation — voir Le Code.

Le panneau Git, en bas de l’écran (Espace g m pour le montrer, et le masquer) : l’état local de tes checkouts, les branches et la lignée du ticket, la revue des merge ou pull requests — voir Le panneau Git.

Le header affiche l’id de la feature ouverte (📍 PROJ-412) suivi de sa branche entière, une puce qui reprend l’état du Tableau pour cette feature (même lecture, jamais un second calcul), un drapeau qui ne s’allume que si .atlas-workspace/ a été mis en dépôt git partagé et qu’un collègue y a poussé du neuf que tu n’as pas encore récupéré, et la version de l’instance (vX.Y.Z · <commit>). Une fine barre d’activité tout en haut nomme ce qui charge sans jamais bloquer l’écran — la feature précédente reste utilisable pendant qu’une autre se charge.

Deux boutons du header ouvrent des pages qui remplacent la carte entière (Arbre, Code, volet gauche et panneau Git masqués le temps qu’elles sont ouvertes) :

  • ▦ Tableau — toutes les features du projet d’un coup d’œil. Détail : Le Tableau.
  • ⚙️ Config — trois vues : Feature (les repos et branches de la feature ouverte), Projet (les projets connus et les réglages du projet actif, dont la ligne de base et ce qui fait une feature), Atlas (le thème, la version, brancher ton IA). Détail : Configurer un projet et Brancher l’IA.

Une touche maîtresse pilote tout l’écran

Atlas se pilote entier depuis une seule touche : Espace ouvre une boîte en bas à droite, qui liste les colonnes de l’écran. Une lettre choisit la colonne, une lettre suivante déclenche l’effet ; et la boîte elle-même est la liste des raccourcis, rien à mémoriser à l’avance — c’est cette grammaire que l’accueil écrit en clair pour qui ouvre Atlas la première fois. La table complète, colonne par colonne, est dans Le clavier.

Raccourcis

Touche Effet
Espace ouvre la boîte des raccourcis, en bas à droite de l’écran
Espace p t ouvre le Tableau, et le referme — un seul geste dans les deux sens
Espace p c ouvre Config, et la referme
Espace g m montre le panneau Git, et le masque — il reste actif sans feature
Échap referme la page ouverte (Tableau ou Config) et revient à la carte, ou à l’accueil

Ce qu’Atlas ne fait pas

  • Il ne se met jamais à jour tout seul : atlas update est toujours une commande que tu tapes, jamais un automatisme derrière ton dos.
  • Il n’installe jamais le plugin IA à ta place : atlas init le dit explicitement, c’est atlas plugin install qui le fait, à part.
  • Il ne fait pas git init, ne fusionne jamais une branche (pull --ff-only uniquement, le refus de git rendu tel quel) et ne supprime jamais une branche ni un worktree — il montre la commande, il ne la lance pas.
  • Il ne copie aucun fichier de stack dans ton workspace : les stacks vivent dans l’outil.
  • Il ne devine jamais un id de feature : sans branche qui le porte nulle part, la carte reste vide et le dit, plutôt que d’afficher autre chose à la place.
  • Sans feature, il ne fait pas semblant : les gestes qui n’ont rien à lire sont atténués avec leur raison, jamais grisés en silence.

Limites connues

  • atlas update et atlas promote ne sont éprouvés que sous Linux : la façon dont ils retrouvent le binaire fraîchement installé suppose une disposition de fichiers qui ne tient pas encore sous Windows.
  • Le paquet est privé : sans le registre et un jeton configurés, atlas update échoue et Config › Atlas ne peut pas dire s’il existe une version plus récente — il le dit honnêtement (« je n’ai pas pu regarder »), il n’affirme jamais « à jour » par défaut.
  • L’accueil montre la colonne de chaque feature sans lire l’archivage ni l’hébergeur : elle peut être en retard sur celle du Tableau, qui, lui, les lit.
