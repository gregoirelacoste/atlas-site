Prise en main

Installer Atlas, lancer une instance, déclarer ton premier projet et ta première feature — de l'écran d'accueil jusqu'à ta première carte.

Installer Atlas, lancer une instance, déclarer ton premier projet et ta première feature — de l’écran d’accueil jusqu’à ta première carte.

Atlas reconstruit, pour une feature à la fois (un ticket : PROJ-412, FOO-42…), la carte de son code : quelle entrée, quelles méthodes appelées, à travers combien de services — pour que tu valides plutôt que tu ne relises fichier par fichier. Cette page t’amène du paquet installé à cette première carte ; le reste de la documentation part de là (voir le README de cette doc).

Installer le paquet

Atlas est un outil de bureau local : rien à déployer, une instance par projet qui écoute sur 127.0.0.1, mono-utilisateur, mono-machine. Chaque instance sert à la fois l’API et la page web sur son propre port. Il se distribue comme un paquet npm global, @gregoirelacoste/atlas — privé, hébergé sur GitHub Packages via le dépôt de distribution gregoirelacoste/atlas-dist (il ne contient aucun code, il ne fait que porter le droit d’installer).

Deux façons de l’obtenir :

  • On te donne un .tgz (le fichier que produit npm run pack, pour quelqu’un qui n’a pas encore accès au registre) :

    npm i -g /chemin/absolu/vers/atlas-x.y.z.tgz

    ⚠️ Le chemin doit être absolu (ou commencer par ./). Un chemin relatif comme dist-pkg/atlas-0.1.10.tgz est lu par npm comme un dépôt GitHub du même nom, et échoue sur « Repository not found ».

  • Tu as accès au registre — il faut le déclarer une fois, avec un jeton (PAT classique, portée read:packages) :

    npm config set @gregoirelacoste:registry https://npm.pkg.github.com
npm config set //npm.pkg.github.com/:_authToken <ton PAT>
npm i -g @gregoirelacoste/atlas@latest

Les deux posent une commande atlas dans ton PATH. Une fois qu’elle existe, tu n’auras plus jamais à retaper ces commandes toi-même : c’est ce que fait atlas update (plus bas).

Vérifier ce qui tourne

atlas version   # la version de l'instance du projet courant (ou, sans instance, celle installée sur le disque)
atlas status    # les instances en marche : projet, adresse, pid, mémoire

atlas version imprime un JSON brut — au minimum version, et selon l’origine du paquet commit, date, branch. atlas status ressemble à ceci :

● boutique ★ — http://127.0.0.1:3030 · pid 48213 · 352 Mo
    /home/moi/dev/boutique
★ = projet par défaut (`atlas start` sans argument)

— ou ○ aucune instance en marche. C’est la première chose à taper si tu ne sais plus quelle version tu as sous les yeux : le commit dit exactement ce qui tourne, pas une branche.

Rester à jour

atlas update

Une seule commande, pour tout le monde : elle installe la dernière version publiée (@gregoirelacoste/atlas@latest), redémarre toutes les instances en marche, et rafraîchit le plugin IA s’il est déjà installé. Si elle échoue, c’est presque toujours le registre ou le jeton : elle te redonne alors les deux lignes npm config set ci-dessus.

Atlas ne se met jamais à jour tout seul. Quand une version plus récente existe, Config › Atlas te le dit (trois états : à jour, une version existe, ou « je n’ai pas pu regarder » avec sa raison) ; c’est toujours toi qui tapes atlas update.

Si tu es dans un clone du dépôt Atlas lui-même, atlas update te prévient avant d’agir : il installerait la dernière version publiée, pas ton code en cours. atlas promote fait ce second geste — il n’apparaît dans atlas help que là où il peut servir, c’est-à-dire près d’un clone.

Une instance par projet

Atlas tourne en instances : un petit serveur local par projet, qui sert l’API et la page web sur son propre port. Une instance sert un seul projet, fixé à son démarrage : plusieurs projets s’ouvrent côte à côte, un onglet et une session de code chacun, sans que rien écrit pour l’un n’atterrisse dans l’autre.

atlas                    # ouvre le projet du dossier courant (démarre son instance si besoin)
atlas start [projet]     # démarre un projet — sans argument, le projet par défaut
atlas status             # les instances en marche, leur adresse, leur mémoire
atlas stop [projet]      # en arrête une ; `--all` les arrête toutes

Chaque projet garde son adresse, dans la plage 3030–3049 ; un port pris se dit et passe au suivant. Une instance n’écoute que ta machine, et s’arrête seule après une heure sans onglet ni session (réglable dans Config › Atlas). Le détail — la plage, atlas ports, les journaux — est dans La ligne de commande. Ce que l’écran retient « sur cette machine » (thème, taille, interligne, contraste, panneaux, plis) se retient par projet : ton navigateur le range par adresse.

⚠️ Tu travailles à distance (SSH, conteneur, VS Code Remote, WSL2) : en SSH, redirige la plage entière, pas un seul port, sinon le deuxième projet ne s’ouvre pas. VS Code Remote et les conteneurs de dev redirigent d’eux-mêmes ; WSL2 rend localhost accessible depuis Windows.

Le workspace : le dossier qui héberge tes repos

Atlas analyse un chapeau : le dossier qui héberge côte à côte les repos d’un même projet — ou un repo seul, qui est alors son propre chapeau. Sa configuration vit dans un sous-dossier .atlas-workspace/, trouvé par remontée depuis le dossier où tu lances atlas — exactement comme git trouve son .git/. Tu peux donc lancer atlas depuis n’importe quel sous-dossier du chapeau, pas seulement à sa racine.

Les repos membres sont auto-découverts : tout sous-dossier direct du chapeau qui contient un .git en est un, sans rien à déclarer un par un. Le détail — exclure un repo, forcer un motif de branche, une ligne de production par repo — est dans Configurer un projet.

atlas init lancé dans un repo (un .git à la racine, aucun sous-dossier qui en porte un) en fait son propre membre, repos: [{ "name": "<dossier>", "path": "." }], et le dit. Sans aucun repo, il nomme ce qui manque.

atlas init : déclarer un projet

atlas init [DIR] [--stack a,b] [--ia claude,gemini] [--yes]

Dans un terminal, atlas init pose trois questions et fait tout d’une traite : ton IA de code (à cocher : le choix de ta machine, sinon Claude Code ; ou Gemini CLI, Codex, Cursor), le chapeau (le dossier courant d’office), puis ta stack (à cocher : ce que tes dépendances prouvent ; sur un workspace existant, elle se change dans Config › Projet). Il crée le workspace, branche chaque IA choisie ; fermer l’entrée abandonne tout. Ton choix vit dans Config › Atlas. Sans terminal ou avec --yes, rien n’est demandé.

La première fois (aucun .atlas-workspace/ là), atlas init crée project.json (les règles du projet), un dossier features/ vide, un .gitignore et un ESPACES.md — pour que versionner ce dossier soit sûr, et pour rappeler qui écrit quoi dedans. Si .atlas-workspace/ existe déjà, atlas init le dit et n’écrase rien. Un aperçu :

✓ stacks DÉTECTÉES dans 2 repo(s) : nest, react, typescript  (dépendances déclarées)
✓ ligne de base : `develop` — détectée dans 2 repo(s) (`base` dans project.json, éditable dans Config › Projet)
✓ /home/toi/mon-chapeau/.atlas-workspace créé (project.json + features/ + .gitignore + ESPACES.md)

Les stacks — ce qu’Atlas sait d’un framework — s’activent seules : à chaque chargement, Atlas lit les dépendances de tes repos membres et allume ce qu’elles prouvent (quinze livrées, le JavaScript pur compris — voir Les stacks et project.json). --stack a,b, ou une coche qui diffère de la détection, force une décision : ajouter une stack que rien ne prouve, ou en refuser une ; une stack inconnue est refusée, avec la liste de celles qui existent.

atlas init détecte aussi trois choses et les écrit comme des décisions, modifiables ensuite : les repos qui rendent une interface, ce qui fait une feature ici (un jeton de ticket dans le nom des branches, ou bien chaque branche), et la ligne de base — la branche à laquelle une feature est comparée. En cas de désaccord entre repos, rien n’est écrit et il le dit.

atlas init ne branche une IA que si tu l’as choisie — à la question, par --ia ou --yes — parce que ça touche ta configuration globale de session de code (voir Brancher l’IA). Codex et Cursor n’ont pas été éprouvés par Atlas : leurs gestes s’impriment, à lancer toi-même. Il ne fait pas non plus git init, et il ne copie aucun fichier de stack dans ton workspace — elles vivent dans l’outil et suivent ses mises à jour.

Partager cette config avec l’équipe se fait en versionnant .atlas-workspace/ (le .gitignore posé protège déjà ce qui doit rester personnel — les fils que tu as ouverts, la branche que tu lis) ; un collègue la reçoit avec git clone <url> .atlas-workspace au lieu de relancer atlas init.

Le registre des projets

Atlas garde la liste des projets que tu as ouverts dans ~/.config/atlas/config.json (ou $XDG_CONFIG_HOME/atlas/config.json) — l’équivalent des « projets récents » d’un IDE, rangé hors de tout workspace. Il retient aussi l’adresse de chaque projet et le projet par défaut — celui que démarre atlas start sans argument (au départ, le premier enregistré). Tu le gères depuis Config › Projet, chapitre « Projets connus » : chaque projet y dit s’il tourne ; « Ouvrir » l’ouvre dans un nouvel onglet (l’onglet où tu es ne change jamais de projet), « en faire le défaut » le choisit comme défaut. Le header de chaque onglet dit son projet.

L’accueil : l’écran sans feature

atlas ouvre le navigateur sans feature. Ce que tu vois alors n’est pas une carte vide, c’est une page d’accueil — et c’est aussi ce que tu retrouves en quittant une feature (le bouton ⊘ tous les repos du panneau Git). De haut en bas :

  • la promesse, en titre : « Relire et endosser le code d’une feature, flux par flux. » — un flux est un chemin d’appel complet, de l’entrée jusqu’au bout ; endosser, c’est dire « j’ai relu cette ligne et je la prends à mon compte ». Sous elle : « La carte d’un ticket à travers ses repos : ce qui a changé, qui l’appelle, et un rond par symbole à endosser. »
  • la touche maîtresse en une phrase — « Espace ouvre la boîte des raccourcis : une lettre choisit une colonne, la suivante agit. Échap ferme. » — suivie des sept colonnes de l’écran avec leur lettre : disposition, volet gauche, Arbre, recherche, Git, recette, pages ;
  • cinq gestes cliquables, avec leur touche ;
  • les dernières features ;
  • un pied : « Espace pour commencer ».

Les cinq gestes, dans l’ordre où la page les pose :

Touche Le geste, tel qu’il est écrit Sans feature
Espace p t « Choisir une feature — le Tableau » actif
Espace s g « Chercher dans le contenu des fichiers » atténué — « sans feature »
Espace s f « Ouvrir un fichier par son nom » atténué — « sans feature »
Espace g l « Les repos du chapeau — le panneau Git » actif
Espace p c « Config — projet, repos, IA » actif

Un geste qui ne peut rien faire ici n’est ni caché ni gris muet : il est atténué avec sa raison en clair, et son clic ne fait rien. Les deux qui le sont cherchent dans les fichiers de la feature ouverte. Cliquer un geste actif joue exactement le même accord que la touche : la page ne fait rien que le clavier ne fasse.

Sous les gestes, Dernières features liste jusqu’à six features, la dernière poussée d’abord (le même ordre que le Tableau ; celles que rien ne date passent après). Chaque carte porte son id, son titre, sa colonne (le mot du Tableau ; un tiret hors colonne) et l’âge de la dernière poussée. Cette liste ne paie ni l’historique git ni l’hébergeur : la colonne affichée y vaut donc « En cours » pour une feature que le Tableau rangerait plus loin — c’est lui qui tranche. Elle a ses trois états : en cours de chargement, l’erreur en clair (« pas pu lister : … »), ou « aucune feature déclarée — le Tableau pour en déclarer une ». toutes les features → ouvre le Tableau.

Deux choses restent à l’écran sur l’accueil. Le header, qui affiche « aucune feature » et les deux boutons de page. Et le panneau Git, en bas : c’est le seul panneau qui parle encore de quelque chose, puisque sans feature il liste tous les repos du chapeau.

⚠️ Une page ouverte à ta dernière visite garde la main : si tu as quitté Atlas sur le Tableau ou sur Config, tu les retrouves au démarrage, et c’est Échap qui les referme sur l’accueil.

Choisir ou déclarer ta première feature

Depuis l’accueil, ▦ Tableau (Espace p t) montre toutes les features du projet, rangées en colonnes par ce qu’il reste à faire ; un clic sur l’une d’elles charge sa carte. Le détail des colonnes est dans Le Tableau.

Si ta feature n’existe nulle part encore, la colonne Déclarée porte un bouton ＋ : c’est le seul endroit du produit où une feature peut naître sans qu’une branche existe déjà. Il te demande un identifiant, un titre (optionnel), puis Déclarer. Deux saisies sont acceptées : un id de ticket (PROJ-412), ou un nom de branche collé — feat/login-bug déclare login-bug, jamais feat-login-bug. À l’ouverture du formulaire, Atlas cherche déjà sur origin les branches qui portent un identifiant, pour te les proposer en autocomplétion ; s’il n’a pas pu les lire, il le dit et propose de réessayer plutôt que de déclarer à l’aveugle.

Si l’id que tu tapes correspond à une branche déjà trouvée sur origin, ses repos sont pré-déclarés — la feature se lit alors directement sur refs, sans rien avoir à sortir localement. Si l’id n’existe encore nulle part, Atlas pose une spec vierge (ticket.md) à côté : tu es en train de créer le ticket, pas de reprendre du code. Et si l’id existe déjà, « Déclarer » ne renvoie pas une erreur : Atlas rouvre simplement la feature qui existe.

Ta première carte

Ce qu’il faut pour qu’une carte s’affiche : au moins un repo du chapeau doit porter une branche que ton projet reconnaît comme celle de cette feature — un nom qui contient l’id exact du ticket (feat/PROJ-412-paging convient, PROJ-41 ne matche jamais PROJ-412), ou, si le projet compte ses features par branche, la branche elle-même. Cette branche est alors comparée à la ligne de base : celle déclarée pour la feature, sinon celle du projet, sinon la variable d’environnement BASE, sinon develop (Configurer un projet).

Tant qu’aucune branche ne porte l’id nulle part, la feature reste sur « Déclarée » : ce n’est pas un retard, c’est l’état normal d’un ticket qu’on vient d’ouvrir — et si tu ouvres quand même sa carte, l’Arbre le dit plutôt que de rester silencieux : « Aucun fichier touché : le diff avec est vide — la branche n’a pas encore de commit. Rien à lire, et ce n’est pas un défaut de détection. »

Le tour de l’écran

Une fois une feature ouverte, l’écran se partage en quatre zones fixes, plus deux pages qui les remplacent entièrement — et, sans feature, l’accueil décrit plus haut.

Le volet gauche : six onglets à plat, sur un ou deux rangs selon la place.

Famille Onglets Ce qu’ils montrent
Relecture Relecture ce qu’il te reste à relire, en lignes — voir Relire et endosser
Fichiers Fichiers · Inventaire l’explorateur du chapeau avec le diff marqué en place, et son jumeau chiffré par famille — voir Fichiers et Inventaire
Parcours Ticket · Parcours · Journal la spec et ce qu’on a compris, les étapes cliquables du flux, et tous les fils par date — voir Ticket, fils et Journal

Au centre, la vue d’ensemble ; Espace a a montre l’Arbre, tout le diff — voir L’Arbre.

Le Code, à droite, fermé tant que rien n’y est ouvert : la source live du nœud sélectionné, avec ses liens et ses fils de conversation — voir Le Code.

Le panneau Git, en bas de l’écran (Espace g l pour le montrer, rejoué pour le masquer) : l’état local de tes checkouts, les branches et la lignée du ticket, la revue des merge ou pull requests — voir Le panneau Git.

Le header, une ligne : le projet, l’id de la feature (PROJ-412), sa branche entière, sa nature, sa colonne au Tableau et, si ses repos divergent, « pas au même endroit » en rouge. Un drapeau workspace s’allume quand ton partage est bloqué ou en retard d’un jour. À droite : code | recette, Tableau, Config. Ce qui charge s’y nomme (« ⟳ carte de PROJ-412 »), sans rien bloquer. Version, commit et lien vers ce manuel : Config › Atlas.

Deux boutons du header ouvrent des pages qui remplacent la carte entière (Arbre, Code, volet gauche et panneau Git masqués le temps qu’elles sont ouvertes) :

  • Tableau — toutes les features du projet d’un coup d’œil. Détail : Le Tableau.
  • Config — trois vues : Feature (les repos et branches de la feature ouverte), Projet (les projets connus et les réglages du projet de l’onglet, dont la ligne de base et ce qui fait une feature), Atlas (le thème, la taille, l’interligne, le contraste, la largeur du Code, les instances, la version et le commit qui tournent, brancher ton IA). Détail : Configurer un projet et Brancher l’IA.

Une touche maîtresse pilote tout l’écran

Atlas se pilote entier depuis une seule touche : Espace ouvre une boîte en bas à droite, qui liste les colonnes de l’écran. Une lettre choisit la colonne, une lettre suivante déclenche l’effet ; et la boîte elle-même est la liste des raccourcis, rien à mémoriser à l’avance — c’est cette grammaire que l’accueil écrit en clair pour qui ouvre Atlas la première fois. La table complète, colonne par colonne, est dans Le clavier.

Raccourcis

Touche Effet
Espace ouvre la boîte des raccourcis, en bas à droite de l’écran
Espace p t ouvre le Tableau, et le referme — un seul geste dans les deux sens
Espace p c ouvre Config, et la referme
Espace g l montre le panneau Git sur Local, et le masque — il reste actif sans feature
Échap referme la page ouverte (Tableau ou Config) et revient à la carte, ou à l’accueil

Ce qu’Atlas ne fait pas

  • Il ne se met jamais à jour tout seul : atlas update est toujours une commande que tu tapes, jamais un automatisme derrière ton dos.
  • Il n’installe jamais le plugin IA à ta place : atlas init le dit explicitement, c’est atlas plugin install qui le fait, à part.
  • Il ne fait pas git init, ne fusionne jamais une branche (pull --ff-only uniquement, le refus de git rendu tel quel) et ne supprime jamais une branche ni un worktree — il montre la commande, il ne la lance pas.
  • Il ne copie aucun fichier de stack dans ton workspace : les stacks vivent dans l’outil.
  • Il ne devine jamais un id de feature : sans branche qui le porte nulle part, la carte reste vide et le dit, plutôt que d’afficher autre chose à la place.
  • Sans feature, il ne fait pas semblant : les gestes qui n’ont rien à lire sont atténués avec leur raison, jamais grisés en silence.
  • Un onglet ne change jamais de projet, et une instance ne sert jamais qu’un projet : il n’existe aucun geste qui ferait écrire un projet dans un autre. Un autre projet s’ouvre dans un autre onglet.

Limites connues

  • atlas update et atlas promote ne sont éprouvés que sous Linux : la façon dont ils retrouvent le binaire fraîchement installé suppose une disposition de fichiers qui ne tient pas encore sous Windows.
  • Le paquet est privé : sans le registre et un jeton configurés, atlas update échoue et Config › Atlas ne peut pas dire s’il existe une version plus récente — il le dit honnêtement (« je n’ai pas pu regarder »), il n’affirme jamais « à jour » par défaut.
  • L’accueil montre la colonne de chaque feature sans lire l’archivage ni l’hébergeur : elle peut être en retard sur celle du Tableau, qui, lui, les lit.
