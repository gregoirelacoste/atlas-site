Ce que l'IA lit et écrit

Les douze outils du serveur MCP, un par un : ce qu'Atlas rend à ta session de code, ce qu'elle a le droit d'écrire dans la carte, et les quatre espaces qu'aucun outil n'atteint.

Les douze outils du serveur MCP, un par un : ce qu’Atlas rend à ta session de code, ce qu’elle a le droit d’écrire dans la carte, et les quatre espaces qu’aucun outil n’atteint.

Brancher le plugin et le serveur MCP est décrit dans Brancher l’IA — cette page-ci suppose que c’est fait, et dit ce qui passe par le tuyau. Le vocabulaire y est celui du produit : une feature est un ticket et le code qui le porte ; un nœud est une ligne de la carte (un symbole, un fichier) ; un fil est une conversation ancrée, posée sur la ligne ou le symbole dont elle parle ; endosser un nœud, c’est le relire et le valider (Relire et endosser).

Ce que l’IA peut lire

Six outils, et une clé commune : un ref, l’identité exacte d’un symbole, écrite repo::file::symbol. Le digest la rend, sources la consomme, les fils s’y ancrent.

outil arguments ce qu’il rend
features merged (facultatif) les features qu’Atlas connaît ici : id, repos, branches ; avec merged, l’état d’archivage
brief feature, base la feature en une page de texte — le même contenu qu’atlas brief
digest feature, base la carte aplatie : un nœud par ligne, plus les repos résolus et les compteurs
sources feature, refs, mode, base le code de N symboles en un appel, en diff (l’outil annonce 60 refs au plus)
refs feature, base les refs git qui font foi par repo : branche résolue, base, commit d’origine du diff, feature mergée ou non
guide moment (facultatif) les consignes d’Atlas pour un moment — voir Brancher l’IA

Ce que porte chaque nœud du digest, au-delà de son nom et de sa couche :

  • fils: N — N conversations parlent déjà de ce symbole ; le contenu se demande à sources ;
  • annotated, announced (une intention posée en codant que personne n’a confrontée au diff), stale (le fichier a bougé depuis), aside (mis de côté), dead (non atteint), declaredTypes (les types qu’un fichier de contrat déclare) ;
  • crit: [{ who, crit }] — la note de criticité que chaque relecteur a posée en endossant, de 1 à 4, nommée par personne, jamais fondue en un chiffre moyen ;
  • aRepondre: true — un nœud noté 4 sans aucun fil ;
  • unsureBy: [{ who, at }] — qui a posé ? sur ce nœud (« je n’ai pas compris ce que ça fait »), nommé, jamais compté ; aExpliquer: true quand aucun message de l’IA n’est plus récent que ce ? ;
  • tests — les tests qui atteignent ce nœud, en trois états : les phrases des cas de test · [] = la convention de test est active et rien n’atteint ce nœud, un fait · absent = aucune stack de test active, on n’a pas pu regarder. testsClass: N dit que des cas éprouvent la classe sur une méthode hors du diff ; quatreSansTest: true marque un nœud noté 4 que rien n’atteint ;
  • compris, à la racine — le fil de feature entier : ce qu’on a compris du problème (cause racine, décision), un seul par feature, auquel on ajoute au lieu de le réécrire. Voir Ticket, fils et Journal ;
  • counts — les mêmes chiffres agrégés par identité, jamais par occurrence : nodes, todo, fils, aRepondre, aExpliquer, quatreSansTest… C’est le reste-à-faire d’un skill.

sources rend le code en mode hunks (par défaut : la signature et les fenêtres autour des changements) ou full (le symbole entier), et avec lui les fils ancrés sur ces symboles, la note crit et les unsureBy de chaque ref. Chaque fil dit s’il a vieilli : stale: true (le fichier a bougé depuis ce qui a été dit), false (intact), null (indécidable), et hypothese: true quand le message a été posé avant que ce code existe. Les tests, eux, ne passent pas par sources.

Ce qui ne sort jamais vers l’IA : un endossement sans note (un 0 nu ne lui dit rien) et ce que tu as lu — les fils que tu as ouverts, le rang que tu as cliqué sur une branche. Poser un chiffre, c’est parler à l’IA ; relire, non.

Ce que l’IA peut écrire

Six portes, et rien d’autre. Cinq écrivent dans le dossier de la feature (.atlas-workspace/features/<ID>/) ; la sixième sort d’Atlas.

outil ce qu’il écrit où
declare ouvre la feature : id, title, repos membres (omis, Atlas inscrit ceux qui portent déjà le ticket) feature.json
annotate la parole : intent, goal, unsure en codant, did/does à la relecture — et, séparément, la structure : drop, layer, group overlay.json
comment ouvre un fil (à la ligne : file + side + line + witness ; ou sur le symbole entier : ref seule ; ou sur la feature : ticket: true), répond dedans (thread), range un fil à elle (archive + why), cite des precedents comments.json
parcours les steps et son évaluation des criteres (yes/no/partial + les refs qui le prouvent) parcours.json
plan les nœuds planned — le pseudo-code d’avant le code, qui s’éteint tout seul quand le vrai symbole arrive plan.json
publish publie un fil (thread) sur la review de son repo — GitLab comme GitHub ; mode: general quand l’hébergeur refuse l’ancre chez l’hébergeur

Quatre choses que les outils tiennent à la place des consignes :

  • la forme des messages : la première ligne seule et ≤ 90 caractères (c’est elle que le Journal affiche), le message entier ≤ 350 caractères et ≤ 4 lignes. Au-delà, l’écriture est refusée, et le refus nomme ce qu’il y a à retirer. did et does sont bornés à 300 caractères chacun ;
  • l’anti-doublon : un second fil sur la même ancre est refusé, et un fil que tu as résolu ne se rouvre pas. La feature n’a qu’un seul fil de feature : le second appel te renvoie au premier ;
  • l’ancre à la ligne se vérifie à l’écriture : le témoin — le contenu exact de la ligne visée — doit se retrouver dans ce qu’Atlas lit, pas dans ce que ton IA a sous les yeux. S’il n’y est pas, le fil est refusé, et le refus dit ce qu’Atlas lit (le working tree du chapeau, ou origin/<branche>) et les deux sorties : pousser, ou ancrer par ref seule ;
  • la date : Atlas date lui-même ce que l’IA écrit, contre le commit courant. C’est de là que vient la péremption automatique de ce qui a été dit.

Ranger (archive) n’est pas supprimer : le fil reste lisible, se remet d’un geste, et rien ne part vers l’hébergeur. Un fil où tu as répondu est refusé à l’archivage — c’est là que vivent tes corrections.

La frontière

Quatre choses n’ont aucun outil, et c’est la garantie :

  • ton endossement et ta note de criticité — voir Relire et endosser ;
  • ta spec, ticket.md, dès qu’elle est remplie. declare peut y poser un gabarit vide quand aucune branche ne porte encore le ticket, jamais par-dessus un fichier existant ; l’import Jira de /atlas:start-feature n’écrit qu’une fois, sur une spec absente ou vierge ;
  • résoudre un fil, et le supprimer ;
  • le code des repos analysés.

Cette frontière tient par deux choses, jamais une seule : l’absence d’outil côté MCP, et disallowed-tools: Write Edit dans les skills qui n’ont plus rien à écrire à la main (as-coded, parcours, review, answer) — sans quoi l’édition de fichier serait le chemin de contournement. Seul /atlas:start-feature garde l’écriture de fichier, pour l’import unique de la spec.

Ce n’est pas un bac à sable : Bash reste accordé aux skills, pour git et les recherches cross-repo. Ce qu’Atlas tient est une discipline outillée — le chemin normal existe ou n’existe pas.

publish est d’une autre nature : public, chez tes collègues, sous ton nom et sans mention de l’outil, et Atlas ne sait pas défaire — il n’existe aucune suppression. C’est le seul outil dont la description retient au lieu d’inviter : il ne s’appelle que si tu le demandes explicitement. Il n’est dans les allowed-tools d’aucun skill, et il ne faut l’y mettre dans aucun des tiens : la demande d’autorisation de ton client est le garde-fou qui reste, et il vit hors d’Atlas. Le fil de feature, lui, ne se publie pas du tout : il n’a pas d’ancre chez l’hébergeur, et l’outil le dit.

Ce qui déclenche quoi

Ta note de criticité n’est pas un classement : chaque cran se définit par ce qu’il déclenche chez les skills, et un chiffre n’achète jamais moins d’attention qu’un 0 nu.

note ce que l’IA en fait
1 « rien à craindre — l’IA relit à plat, et conteste si elle n’est pas d’accord »
2 « ordinaire — l’IA relit à plat »
3 « à creuser — l’IA cherche les modes d’échec de ce nœud, et la garde en face de chacun »
4 « critique — l’IA remonte le fil jusqu’à l’entrée, et répond toujours »

Et les conséquences directes, côté skills :

  • un 4 sans aucun fil est un reste-à-faire : review et answer ouvrent un fil dessus après avoir remonté le flux jusqu’à l’entrée, même pour dire « rien trouvé, voici ce que j’ai vérifié » ;
  • un 4 que rien ne teste est le finding qui remonte en tête de la review ;
  • un nœud sans test ([]) n’est relevé ailleurs que s’il est sur une frontière — un contrat, un appel inter-services, une entrée HTTP : le dire partout ne dirait plus rien. Un nœud testé, les skills en lisent les phrases avant le code, et citent ce que le test garantit — et ce qu’il ne garantit pas ;
  • un ? appelle une explication dans un fil sur le nœud, en langage produit. L’IA ne retire jamais un ? : c’est toi qui dis « compris », en endossant.

Le brief : la feature en une page

À coller quelque part — une review, un message, ou l’entrée d’un autre agent :

atlas brief PROJ-412                # la feature en une page, sur la sortie standard
atlas brief PROJ-412 --base master  # contre une autre base

Il rend, dans l’ordre : ce que ça fait (la spec et ses critères), ce qu’on a compris (le fil de feature, le plus récent en tête), de quoi c’est fait, par où ça passe, ce que ça peut casser, ce qu’Atlas n’a pas pu prouver, ce que l’IA n’a pas pu vérifier, ce qui a été annoncé sans être relu, et l’état de l’endossement. C’est le même contenu que l’outil brief.

Les précédents : ce qu’une review passée a coûté

Un finding se répète : le même type de nœud, le même oubli, d’une feature à l’autre. Atlas sait retrouver, pour chaque nœud de ta carte, un fil ouvert par l’IA dans une autre feature sur un nœud du même type — et lui rendre ce qui s’est passé ensuite.

atlas precedents --build          # construit ou rafraîchit l'index, et dit ses chiffres
atlas precedents --build --full   # le reconstruit sans réutiliser l'index d'avant
atlas precedents PROJ-412         # les précédents de cette feature, nœud par nœud
atlas precedents PROJ-412 --json  # la même réponse, brute

C’est une passe explicite, jamais un calcul de la carte. --build rejoue la carte de chaque feature qui porte un fil ouvert par l’IA, à sa fourche et à son sommet : des dizaines de cartes, des minutes. Le mettre sur le chemin d’un appel normal ferait payer ce prix à chaque ouverture de feature ; on le lance quand on veut, et on attend. Le résultat s’écrit dans .atlas-workspace/precedents.json, partagé avec l’équipe comme le reste de la configuration projet.

Le rafraîchissement est incrémental : une feature dont les sommets de branche et le fichier de conversations n’ont pas bougé garde ses entrées telles quelles ; une feature qui a reçu un fil de plus, ou dont une branche a avancé, est rejouée. --full ignore l’index d’avant — après un changement de règle, pas au quotidien.

La construction imprime ce qu’elle a vu : combien de fils ont pu être rattachés à un type de nœud, la part suivie d’un changement dans sa fenêtre, les réponses humaines, les types de nœud sur lesquels l’IA a récidivé — et les features qu’elle n’a pas pu rejouer, avec la raison.

Servis par nœud, les précédents rendent au plus un fil, avec ses faits :

ce qui revient ce que ça veut dire
l’attaque la première ligne du finding passé, et sa clé <feature>::<fil>
la réponse humaine la première ligne de la première réponse, s’il y en a eu une — ou « sans réponse humaine »
le code changé · inchangé · pas pu regarder, dans la fenêtre close de sa feature
l’endossement d’après quelqu’un a endossé ce nœud après le fil, avec sa note s’il en a posé une
les tests combien atteignaient le nœud avant, combien après
l’ancre aujourd’hui intacte · rebougée depuis · n’atterrit plus · non vérifiée

Ce n’est pas un jugement. Atlas ne dit pas « ce finding avait raison », ni « celui-ci s’applique ici » : « merci, corrigé » n’est pas une contestation, et un code qui bouge n’est pas une preuve. Les faits sortent, l’IA juge — et les skills les lisent après leurs propres checks, pour ne pas s’y conformer d’avance. Le tri est borné : au plus un précédent par nœud, jamais deux fois le même fil, au plus trois par type de nœud.

Quand un finding cite un précédent, il passe la clé exacte rendue par la commande (precedents: ["PROJ-380::t22c9dcec"]). Une clé absente de l’index est refusée à l’écriture : on ne cite que ce qui a été servi. Le fil de feature, lui, n’est jamais un précédent — il conclut une feature, il ne juge aucun nœud.

⚠️ Sans atlas precedents --build, il n’y a pas d’index — et « pas d’index » n’est pas « aucun précédent ». Les skills sautent l’étape et le disent dans leur restitution ; l’index ne se rafraîchit jamais tout seul. La commande ne tranche pas non plus : « aucun — aucun fil passé sur un nœud de ce type ; ou l’index est à rafraîchir ».

Ce qu’Atlas ne fait pas

  • Il n’écrit jamais dans le code des repos analysés, ni ne crée de branche, ni ne commite pour toi. Une correction proposée par l’IA reste une donnée dans un fil.
  • Il ne laisse pas l’IA toucher à ta validation ni à ta spec remplie : ces espaces n’ont pas d’outil, et aucun réglage ne les ouvre.
  • Il ne publie rien tout seul. Aucun skill n’a le droit de publier ; l’outil ne s’appelle que sur ta demande explicite, et une note publiée ne se supprime pas.
  • Il ne juge pas un précédent à ta place : l’index se construit sur commande, et ne rend que des faits.
  • Il ne dit pas à l’IA ce que tu as lu. Un endossement sans note, les fils que tu as ouverts, le rang que tu as cliqué sur une branche : rien de tout ça ne sort.

Limites connues

  • publish parle aux deux hébergeurs, GitLab et GitHub, par le même chemin que le bouton ↗ Publier… de l’écran — mais il n’a jamais été éprouvé en vrai, sur aucun des deux : publier écrirait chez de vraies personnes, et Atlas ne sait pas retirer une note. Le reste (la carte, les fils, le brief) est indifférent à l’hébergeur. ⚠️ Sa description, lue par ton IA, dit encore « la merge request » : le mot est en retard sur ce que l’outil fait.
  • L’index des précédents est une photo. Il est invalidé quand les fils ou les branches bougent, mais il ne se reconstruit que sur atlas precedents --build.
  • Les tests n’ont trois états que si une convention de test est active dans le projet. Sans stack de test, le champ est absent — ce qui veut dire « on n’a pas pu regarder », jamais « non testé ».
  • Ce que l’IA écrit peut finir public. Les fils qu’elle rédige sont publiables tels quels, sous ton nom et sans mention de l’outil : c’est pour ça que ses consignes lui demandent d’écrire chaque fil comme s’il devait être lu par tes collègues.
