Ce que l'IA lit et écrit

Les douze outils du serveur MCP, un par un : ce qu'Atlas rend à ta session de code, ce qu'elle a le droit d'écrire dans la carte, et les quatre espaces qu'aucun outil n'atteint.

Les douze outils du serveur MCP, un par un : ce qu’Atlas rend à ta session de code, ce qu’elle a le droit d’écrire dans la carte, et les quatre espaces qu’aucun outil n’atteint.

Brancher le plugin et le serveur MCP est décrit dans Brancher l’IA — cette page-ci suppose que c’est fait. Le vocabulaire y est celui du produit : une feature est un ticket et le code qui le porte ; un nœud est une ligne de la carte (un symbole, un fichier) ; un fil est une conversation ancrée sur la ligne ou le symbole dont elle parle ; endosser un nœud, c’est le relire et le valider (Relire et endosser).

Ce que l’IA peut lire

Cinq outils, et une clé commune : un ref, l’identité exacte d’un symbole, écrite repo::file::symbol.

outil arguments ce qu’il rend
features merged (facultatif) les features qu’Atlas connaît ici : id, repos, branches ; avec merged, l’archivage
brief feature, base la feature en une page — le même contenu qu’atlas brief
digest feature, base la carte aplatie : un nœud par ligne, les repos résolus, les compteurs
sources feature, refs, mode, base le code de N symboles en un appel, en diff (60 refs au plus)
refs feature, base les refs git qui font foi par repo : branche, base, commit d’origine du diff, feature mergée ou non

Ce que porte chaque nœud du digest, au-delà de son nom et de sa couche :

  • fils: N — N conversations parlent déjà de ce symbole ; le contenu vient de sources ;
  • annotated, announced (une intention annoncée en codant, jamais confrontée au diff), stale (le fichier a bougé depuis), aside (mis de côté), dead (non atteint) ;
  • crit: [{ who, crit }] — la note de criticité posée par chaque relecteur en endossant, de 1 à 4, nommée par personne, jamais fondue ; aRepondre: true = un 4 sans aucun fil ;
  • unsureBy: [{ who, at }] — qui a posé ? sur ce nœud, nommé, jamais compté ; aExpliquer: true quand aucun message de l’IA n’est plus récent que ce ? ;
  • tests — les tests qui atteignent ce nœud, en trois états : les phrases des cas · [] = la convention de test est active et rien n’atteint ce nœud, un fait · absent = aucune stack de test, on n’a pas pu regarder ;
  • compris, à la racine — le fil de feature entier, un par feature, auquel on ajoute au lieu de le réécrire (Ticket, fils et Journal) ;
  • counts — les mêmes chiffres agrégés par identité, jamais par occurrence.

sources rend le code en mode hunks (par défaut : la signature et les fenêtres autour des changements) ou full, et avec lui les fils ancrés sur ces symboles, la note crit et les unsureBy de chaque ref. Chaque fil dit s’il a vieilli : stale: true (le fichier a bougé depuis), false, null (indécidable), hypothese: true (posé avant que ce code existe).

Ce qui ne sort jamais : un endossement sans note, et ce que tu as lu — les fils ouverts, le rang cliqué sur une branche. Poser un chiffre, c’est parler à l’IA ; relire, non.

Ce que l’IA peut écrire

Sept portes. Cinq écrivent dans le dossier de la feature (.atlas-workspace/features/<ID>/), une dans l’index des précédents, la dernière sort d’Atlas.

outil ce qu’il écrit où
declare ouvre la feature : id, title, repos membres (omis : ceux qui portent le ticket) feature.json
annotate la parole : intent, goal, unsure en codant, did/does à la relecture — et, à part, la structure : drop, layer, group overlay.json
comment ouvre un fil (à la ligne : file + side + line + witness ; sur le symbole : ref ; sur la feature : ticket: true), répond (thread), range le sien (archive + why), cite des precedents comments.json
parcours les steps et son évaluation des criteres (yes/no/partial + les refs qui le prouvent) parcours.json
plan les nœuds planned — le pseudo-code, qui s’éteint quand le vrai symbole arrive plan.json
sonde ce qu’un précédent servi a donné : ecarte (il n’a servi à rien) ou manque (il en aurait fallu un ici) precedents.json
publish publie un fil (thread) sur la review de son repo — GitLab comme GitHub ; mode: general si l’hébergeur refuse l’ancre chez l’hébergeur

Quatre choses que les outils tiennent à la place des consignes :

  • la forme des messages : première ligne seule et ≤ 90 caractères (c’est elle que le Journal affiche), message entier ≤ 350 caractères et ≤ 4 lignes, did et does ≤ 300 chacun. Au-delà, l’écriture est refusée et le refus nomme ce qu’il y a à retirer ;
  • l’anti-doublon : un second fil sur la même ancre est refusé, un fil que tu as résolu ne se rouvre pas, et la feature n’a qu’un seul fil de feature ;
  • l’ancre à la ligne se vérifie à l’écriture : le témoin — le contenu exact de la ligne visée — doit se retrouver dans ce qu’Atlas lit, pas dans ce que ton IA a sous les yeux. Sinon le fil est refusé, et le refus dit ce qu’Atlas lit et les deux sorties : pousser, ou ancrer par ref ;
  • la date : Atlas date ce que l’IA écrit contre le commit courant — de là vient sa péremption.

Ranger n’est pas supprimer : le fil reste lisible et se remet d’un geste. Un fil où tu as répondu est refusé à l’archivage : c’est là que vivent tes corrections.

La frontière

Quatre choses n’ont aucun outil, et c’est la garantie : ton endossement et ta note de criticité (Relire et endosser) · ta spec, ticket.md, dès qu’elle est remplie — declare peut y poser un gabarit vide, jamais par-dessus un fichier existant · résoudre un fil, et le supprimer · le code des repos analysés.

Elle tient par deux choses : l’absence d’outil côté MCP, et l’interdiction de l’écriture de fichier (Write, Edit) dans les skills qui n’ont plus rien à écrire à la main. Deux la gardent : celui qui ouvre une feature (l’import unique de la spec) et celui qui code dans ta session, à qui le droit de publier et de déclarer est retiré nommément (Brancher l’IA). Ce n’est pas un bac à sable : Bash reste accordé, pour git et les recherches cross-repo.

publish est d’une autre nature : public, sous ton nom, sans mention de l’outil. Ne le mets dans les allowed-tools d’aucun de tes skills — la demande d’autorisation de ton client est le garde-fou qui reste, et il vit hors d’Atlas. Le fil de feature, lui, n’a pas d’ancre chez l’hébergeur : il ne se publie pas, et l’outil le dit.

Ce qui déclenche quoi

Chaque cran de la note de criticité se définit par ce qu’il déclenche chez les skills, et un chiffre n’achète jamais moins d’attention qu’un 0 nu — le tableau des quatre crans est dans Relire et endosser.

Un 4 sans aucun fil est un reste-à-faire : la review en ouvre un, même pour dire « rien trouvé, voici ce que j’ai vérifié ». Un 4 que rien ne teste remonte en tête des findings ; un nœud sans test n’est relevé ailleurs que s’il est sur une frontière. Un ? appelle une explication dans un fil sur le nœud, en langage produit — et l’IA ne retire jamais un ? : c’est toi qui dis « compris », en endossant.

Le brief : la feature en une page

atlas brief PROJ-412 (avec --base <branche> si besoin) imprime le même contenu que l’outil brief — à coller dans une review, un message, ou l’entrée d’un autre agent. Il rend, dans l’ordre : ce que ça fait (la spec et ses critères), ce qu’on a compris, de quoi c’est fait, par où ça passe, ce que ça peut casser, ce qu’Atlas n’a pas pu prouver, ce que l’IA n’a pas pu vérifier, ce qui a été annoncé sans être relu, l’endossement.

Les précédents : ce qu’une review passée a coûté

Un finding se répète d’une feature à l’autre. Un précédent est un fil passé, ancré à un nœud d’une autre feature, avec ce qui s’est passé ensuite.

Deux bouches l’ouvrent, à des conditions différentes. Un fil ouvert par l’IA entre toujours : c’est elle qui a parlé, et ce qu’elle a dit est le fait. Un fil ouvert par un humain — la règle posée en review, celle qui n’est écrite ni dans le code ni dans le ticket — n’entre que s’il a eu une suite : une réponse humaine, une réplique de l’IA, un code qui a bougé dans la fenêtre de sa feature, ou un endossement posé après ; une question jamais reprise n’apprend rien. atlas precedents PROJ-412 marque chaque précédent servi « ouvert par l’humain » ou « ouvert par l’IA ». Le fil de feature, lui, n’est jamais un précédent : il ne juge aucun nœud.

Construire l’index

atlas precedents --build                     # construit ou rafraîchit l'index, et dit ses chiffres
atlas precedents --build --full              # le reconstruit sans réutiliser l'index d'avant
atlas precedents --build --out /tmp/x.json   # un index CANDIDAT ailleurs, le workspace intact
atlas precedents PROJ-412 [--json]           # les précédents de cette feature, nœud par nœud

C’est une passe explicite, jamais un calcul de la carte : --build rejoue la carte de chaque feature qui porte un fil ancré à un nœud, à sa fourche et à son sommet — des dizaines de cartes, des minutes. Le résultat s’écrit dans .atlas-workspace/precedents.json, partagé, et il est incrémental : une feature dont les sommets de branche et le fichier de conversations n’ont pas bougé garde ses entrées telles quelles. --full ignore l’index d’avant.

--out écrit un index candidat ailleurs : même build, seule la destination change — de quoi mesurer une autre clé sans toucher à l’index de l’équipe. Un candidat ne porte ni ce qui a été servi ni les sondes ; déposé à la place de l’index du projet, Atlas refuse de le servir.

Ce qui est servi, et par quelle clé

Sur chaque nœud, Atlas rend au plus un précédent. Le filtre est d’abord structurel : même type de nœud — repo, couche, famille, classe, déclencheur, sortie, contrats consommés (les types qu’il partage avec d’autres) ; soit tout, soit au moins deux de ces traits qui s’accordent, jamais la couche seule. Parmi ceux qui passent, la proximité départage : un contrat commun pèse le plus lourd, et le même fichier pèse autant qu’un contrat commun — puis le déclencheur et la sortie, puis la couche, la famille, la classe. À proximité égale, le plus récent. Chaque ligne servie affiche sa proximité et dit « même fichier » le cas échéant ; le tri est borné à un précédent par nœud, jamais deux fois le même fil, trois au plus par type de nœud.

ce qui revient ce que ça veut dire
l’attaque la première ligne du fil passé, sa clé <feature>::<fil>, et qui l’a ouvert
les deux voix la première réponse d’un humain (ou « sans réponse humaine ») ; et, sur un fil ouvert par un humain, la réplique de l’IA
le code changé · inchangé · pas pu regarder, dans la fenêtre close de sa feature
l’endossement d’après quelqu’un a endossé ce nœud après le fil, avec sa note
les tests combien atteignaient le nœud avant, combien après
l’ancre aujourd’hui intacte · rebougée depuis · n’atterrit plus · non vérifiée

Ce n’est pas un jugement : « merci, corrigé » n’est pas une contestation, et un code qui bouge n’est pas une preuve. Un finding qui cite un précédent passe la clé exacte rendue par la commande (precedents: ["PROJ-380::t22c9dcec"]) ; une clé absente de l’index est refusée à l’écriture. Et ce qui est servi se note : Atlas consigne par feature quel précédent est parti vers quel nœud, quand, et combien de fois — c’est ce registre qui rend la sonde possible.

La sonde : ce qu’un précédent a donné

sonde est la seule écriture qui ne parle pas de ton code mais de l’index. Deux formes, exactement une par appel : ecarte (« tu l’as lu et il n’a servi à rien »), avec la clé du précédent et une raison parmi hors-sujet (« il parle d’autre chose »), deja-su (« tu l’avais déjà vu ailleurs ») et perime (« le code lui a donné tort ») ; ou manque (« il en aurait fallu un ici »), avec 2 à 5 mots — ceux du problème, pas ceux du code — qu’on aurait cherchés. Mélanger les deux formes est refusé, et sans index la sonde l’est aussi.

Les gardes sont strictes : une sonde contrôle Atlas, et ne vaut rien si elle raconte un service qui n’a pas eu lieu. On ne sonde que ce qu’on a reçu, au nœud où on l’a reçu : un ecarte sur un précédent servi ailleurs dans la même feature est refusé en le nommant, un précédent jamais servi ici aussi ; seul un service trop ancien pour qu’Atlas sache à quel nœud il est parti passe — on ne refuse pas sur une ignorance. Le nœud doit être un repo::file::symbol complet, et pour un manque il doit exister dans la carte et pouvoir recevoir un précédent : ni un renvoi « voir ↑ », ni une ligne de tests, ni un nœud seulement prévu ; carte illisible, refus qui le dit.

Elle s’ajoute à precedents.json, sur un rail à part, en append-only, et n’est jamais resservie comme savoir : elle est la liste de travail du build suivant, et les premières paires du contrôle humain.

La chronologie : une ligne par index

Chaque atlas precedents --build ajoute une ligne à l’index : rien ne s’édite, rien ne se réécrit, rien ne se supprime. Ce n’est pas un score — ni note globale, ni flèche verte, ni niveau. On lit une progression, ligne après ligne, et elle peut baisser : c’est ce qui la rend croyable. Chaque nombre porte son dénominateur, et ce qui n’est pas mesuré le dit au lieu d’afficher zéro.

ce que la ligne porte ce que ça dit
durée, dont la mesure ce que le build a coûté, et si la mesure se met à coûter cher
précédents combien d’ouverts par l’IA, combien par l’humain — le total est la somme
features rejouées pour cause de règle · gardées telles quelles · non rejouées
cibles les précédents porteurs de savoir humain et d’une suite ; à côté, ce que ce build a écarté faute de suite
population combien de questions posées à l’index, et ce qu’il a fallu lire : features, casiers de curation, parcours — les sidecars illisibles dits
rappel, par relation par le fichier, par le contrat, par la route (« pas pu regarder » : elle n’est pas dans l’index) — avec ses paires et ses questions
fuites, largeur, servis, tokens la cible sortie depuis un nœud sans rapport ; les candidats laissés par question ; la médiane des précédents par feature servie ; les tokens — « pas pu regarder »
effet les findings servis sont-ils suivis d’un changement plus souvent que les autres ? — « pas encore d’historique » ou « pas pu regarder », jamais zéro
contrôle humain l’accord du dernier contrôle, ou « pas encore fait »
manqués nommés chaque question qui avait une bonne cible et à qui le tri a servi autre chose, avec sa raison
cibles perdues ce qu’on retrouvait au build d’avant et plus maintenant — et, à part, ce qui est sorti de l’index
coupe temporelle le rappel des cibles ouvertes après le dernier changement de clé, face à celles d’avant

Les manqués sont la liste de travail du build suivant : « cette question, ces cibles, ce qui a été servi à la place », avec une raison que la structure sait lire — « deux souvenirs aussi proches l’un que l’autre : rien ne les départage, Atlas a pris le plus récent », « un souvenir du même fichier est passé devant »… La ligne en nomme cinq, dit son plafond, et compte les raisons sur tous les manqués. La coupe temporelle garde contre l’auto-notation : une clé se conçoit sur ce qui existait avant sa date et se juge sur ce qui est arrivé après ; au-delà de dix points d’écart, la ligne le dit. Enfin, deux builds ne se comparent qu’à terrain égal : si la population ou le nombre de cibles a bougé, la ligne dit « la population a changé » au lieu de parler de pertes.

Ce qu’on en fait : après un build, on lit la lecture qu’il imprime — chaque mesure avec sa direction par rapport à la ligne d’avant — puis, au quotidien, la même dans Config › Projet, chapitre « Chronologie » (Configurer un projet). On regarde les manqués, et de temps en temps on joue un contrôle humain.

Le contrôle humain de « voisin »

Toute la mesure repose sur une définition — deux nœuds sont voisins s’ils sont dans le même fichier, ou s’ils partagent un contrat — que personne n’a validée. Sans contrôle, on optimise une convention.

atlas precedents --controle   # 30 paires : tu dis si la cible aurait dû être servie

Le tirage passe les sondes d’abord, moitié au plus, puis va au sort. Atlas montre la question, le type du nœud, l’attaque du fil et ce qu’on y a répondu — jamais son propre avis, qui ferait de la question une confirmation. Tu réponds o, n ou ?, et le résultat s’écrit dans .atlas-workspace/controles/<date>.json, un contrôle par jour (La ligne de commande pour le reste).

Le build suivant lit ce fichier et pose l’accord sur sa ligne : « pas encore fait », un accord chiffré, ou « pas pu regarder ». Les deux populations restent séparées — un désaccord sur une paire venue d’une sonde est attendu, puisqu’un skill l’avait déjà écartée. Seul le tirage au sort juge la définition, et sous 70 % d’accord la ligne écrit ⚠ la définition de « voisin » est contestée. Rien ne change tout seul : la définition se change à la main.

⚠️ Sans atlas precedents --build, il n’y a pas d’index — et « pas d’index » n’est pas « aucun précédent ». La commande elle-même ne tranche pas : « aucun — aucun fil passé sur un nœud de ce type ; ou l’index est à rafraîchir ».

Ce qu’Atlas ne fait pas

  • Aucun outil n’écrit dans le code des repos analysés, ne crée de branche ni ne commite.
  • Il ne laisse pas l’IA toucher à ta validation ni à ta spec remplie : ces espaces n’ont pas d’outil, et aucun réglage ne les ouvre.
  • Il ne publie rien tout seul : aucun skill n’a le droit de publier.
  • Il ne juge pas un précédent à ta place : l’index se construit sur commande et ne rend que des faits ; une sonde ne change jamais ce qu’il servira demain.
  • Il ne dit pas à l’IA ce que tu as lu : un endossement sans note, les fils ouverts, le rang cliqué sur une branche ne sortent pas.

Limites connues

  • Une note publiée ne se retire pas : publish passe par le même chemin que le bouton ↗ Publier… de l’écran, et il n’existe aucune suppression.
  • L’index des précédents est une photo : invalidé quand les fils ou les branches bougent, il ne se reconstruit que sur atlas precedents --build.
  • Deux écritures simultanées sur l’index se recouvrent, et la dernière gagne : évite de lancer un build pendant qu’une session travaille sur une feature.
  • Le rappel par la route n’est pas mesuré — la relation n’est pas dans l’index, et la ligne le dit. Même chose pour les tokens servis et pour l’effet.
  • Ce que l’IA écrit peut finir public : ses consignes lui demandent d’écrire chaque fil comme s’il devait être lu par tes collègues.
