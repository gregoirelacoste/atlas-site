Les stacks et project.json

D'où vient ce qu'Atlas reconnaît dans ton code — les couches, les points d'entrée, les contrats, les appels réseau, les tests : ce que l'outil embarque, et ce que ton project.json ajoute, refuse ou corrige.

D’où vient ce qu’Atlas reconnaît dans ton code — les couches, les points d’entrée, les contrats, les appels réseau, les tests : ce que l’outil embarque, et ce que ton project.json ajoute, refuse ou corrige.

Atlas est générique : le moteur ne connaît aucun framework. Ce qu’il sait d’un framework vient d’une stack ; ce qu’il sait de ton projet, de .atlas-workspace/project.json (où il vit, ce qui s’en partage : Configurer un projet). Cette page dit quelle clé change quoi, et quel motif gagne quand deux se disputent un fichier.

Trois mots du produit reviennent : une couche (controller, service, repo…) est ce que dit la couleur de la pastille d’un symbole dans l’Arbre ; un flux est un chemin d’exécution complet, d’un point d’entrée jusqu’au bout de ce qu’il appelle ; un angle mort est un endroit où le moteur dit qu’il ne sait pas, au lieu de deviner.

Les quinze stacks livrées

Une stack est ce qu’Atlas sait d’un framework : quels suffixes font un controller, quelles formes ouvrent une entrée, quels appels sont réseau. Elles sont embarquées dans Atlas, suivent ses mises à jour, et chacune se prouve seule par une dépendance d’un package.json de ton chapeau.

stack ce qui la prouve ce qu’elle apporte
typescript typescript, ou la seule présence d’un package.json le langage : familles (test, type, const, helper, config, mock…), enveloppes (Promise, Partial, Date…), fetch comme appel réseau, setInterval (seul ou window.setInterval) comme entrée ⏱ CRON, addEventListener comme entrée ⚡ ; les *.json et *.d.ts rangés d’office
nest @nestjs/core entrées par décorateur (Post, Get, Cron, OnEvent, hooks de cycle de vie), couches controller/repo, préfixe et version de route, appels HttpService.*, modules rangés d’office
angular @angular/core composants, directives, pipes, inject(X) qui type un champ, appels HttpClient.*, templates .component.html
graphql graphql .graphql traité comme contrat, schema.graphql rangé d’office
jest jest, vitest, jasmine-core ou mocha les noms des cas de test — les quatre partagent la même API, d’où une seule stack
react react événements JSX (onClick), familles composant/hook/page/contexte, enveloppes React
next next entrées par export (export async function PATCH dans un route.ts) et route tirée du chemin du fichier, événements JSX
vue vue le porteur .vue : son script est lu comme du code, son balisage donne les entrées ⚡
nuxt nuxt entrées par wrapper (defineEventHandler), route tirée du chemin sous server/api, $fetch comme appel réseau, porteur .vue
svelte svelte le porteur .svelte, la couche controller sur +server.ts, les stores en couche repo
express express entrées par appel (app.get('/x', fn)), couches routes/controllers/repositories, middlewares transverses
fastify fastify idem, sur un récepteur typé FastifyInstance, hooks transverses
hono hono idem, sur un récepteur Hono
koa koa, @koa/router idem, sur un récepteur Router
axios axios les appels d’un module importé (axios.patch(url)) comptent comme appels réseau

La stack typescript couvre aussi le JavaScript pur : un projet sans TypeScript a son manifeste, donc ses familles, enveloppes et appels fetch.

Trois listes décident lesquelles sont actives

liste qui l’écrit ce que c’est
(aucune clé) Atlas ce que les dépendances PROUVENT : les dependencies ⊕ devDependencies de tous les package.json membres, comparées aux signatures du tableau ci-dessus
recognizers toi ce que le projet AJOUTE en plus
excludeRecognizers toi ce que le projet REFUSE, même prouvé (un framework installé pour l’outillage)
recognizersActive Atlas la liste dérivée : prouvées ⊕ ajoutées − refusées. Ne l’écris pas : elle est recalculée à chaque chargement

Un refus l’emporte sur un ajout. La première ligne se redérive à chaque chargement : une stack neuve d’Atlas s’active seule sur un workspace existant. atlas init --stack nest,angular est une décision : il écrit recognizers avec ce que tu demandes et excludeRecognizers avec ce qu’il a détecté en plus. Sans --stack, il n’écrit ni l’une ni l’autre (la ligne de commande).

Une copie maison s’ajoute, elle ne remplace pas. Un .atlas-workspace/stack/<id>.json est fusionné par-dessus la stack livrée du même id — le log le dit (atlas logs) — et n’est lu que si cet id est actif : un id inconnu de l’outil doit figurer dans recognizers. La bonne place d’une personnalisation reste project.json, qui fusionne aussi.

Les quatre formes d’un point d’entrée

Une entrée est le départ d’un flux. Rien n’en est une sans règle déclarée — il n’y a aucun défaut. Quatre formes, et une cinquième pour la route :

forme ce qui la déclare exemple
décorateur ou nom de méthode {decorator} ou {method} + kind @Post(), onModuleInit
appel {call: {method, recvFrom, routeArg, handlerArg}} app.get('/x', fn)
export {export: {name, file}} export async function PATCH dans route.ts
wrapper {wrapper} — un appel sans récepteur export default defineEventHandler(fn)
(la route) {routeFromPath: {root, strip, param, verbInName, prefix}} app/api/todos/[id]/route.ts → /api/todos/:id

Le récepteur doit être celui que la règle exige. Dans la forme appel, recvFrom en a trois :

recvFrom ce qu’il exige exemple
une liste de noms un récepteur typé par une de ces fabriques (const app = express()) ou par un paramètre annoté (app: FastifyInstance) app.get('/x', fn)
[] aucun récepteur : une fonction globale setInterval(purge, ms)
["*"] n’importe quel récepteur, mais il en faut un : le nom de la méthode suffit, parce que c’est celui de la plateforme btn.addEventListener('click', onSave), window.setInterval(sync, ms)

Dans la première forme, un récepteur sans type ne donne pas d’entrée, et l’angle mort « entrée sans type » le dit (Quand Atlas ne voit pas). Une règle ["*"] qui déclare aussi routeArg est refusée au chargement (« n’importe quel récepteur » plus « une route à lire » ferait de cache.get('k', fn) un endpoint), et le log du démarrage le dit : [atlas] entrée refusée : … (atlas logs). setTimeout n’est pas déclaré, exprès : presque jamais un minuteur.

Une route se lit dans une chaîne écrite. Quand la règle déclare routeArg (les stacks express, fastify, hono et koa le font), cet argument doit être écrit dans l’appel : un littéral ('/todos'), un template (`${prefix}/todos`) ou une concaténation qui contient une chaîne : byId.get(id) n’est ni entrée, ni angle mort.

Un handler écrit sur place n’a de nœud que si un nom l’identifie — sa route, ou son wrapper. el.addEventListener('click', () => …) n’a que addEventListener, commun au fichier : pas de nœud (angle mort « handler sur place » si le diff le touche) ; nomme la fonction. Un handler-nœud possède ses appels : todosRoutes(app) ne porte pas son ⇄. Sans nœud, ses appels restent à la fonction englobante. handlerArg vaut le dernier argument par défaut (un middleware sur place est écarté).

Un handler passé par un wrapper se lit comme nu, sans rien déclarer : app.post('/x', journalise(async (req) => …)) a son nœud, nommé par sa route. Un niveau, une fonction ; au-delà, angle mort « wrapper non lu ». Un wrapper de la stack reste à sa règle.

Une route venue du chemin est complète : jamais d’aveu …/, aucun routePrefix à déclarer.

Les clés de project.json

Identité et périmètre

clé ce qu’elle change défaut
name le nom affiché dans le registre et l’en-tête de la config le nom du dossier
stack une étiquette libre, affichée sous le nom (nest · angular) ce que atlas init a détecté
featureId ce qui fait une feature : "ticket" ou "branch" "ticket"
commitTypes les types de commit ajoutés aux conventionnels (["hotfix"]) absente = les conventionnels
domainesSensibles les domaines sensibles (nom, mots) absente
vocabulaire le vocabulaire du projet (mot, definition, noms) absente
frontRepos une expression régulière testée sur le nom d’un repo. Sans effet sur la carte : voir ci-dessous front|web|app|pwa|-ui|admin, ou les repos dont une dépendance prouve un front
exclude les repos retirés de la découverte (Configurer un projet) []
repos[] les overrides par repo (branch, routePrefix, productionBase — Configurer un projet) []
recognizers · excludeRecognizers les stacks ajoutées / refusées absentes
base la ligne de base à laquelle une feature se compare (Configurer un projet) develop, ou BASE de l’environnement
precedents { "serveImports": false } ne sert plus les précédents importés (Les précédents). Seul false les retire ; "false" entre guillemets vaut le défaut, et atlas precedents le dit absente = servis

repoPrefix, recognizersActive et baseActive, dans la config servie à l’écran, sont des faits dérivés (le préfixe commun des noms de repos, la liste active, la base retenue) : les écrire à la main ne fait rien.

« Front » est une propriété du FICHIER, plus du repo

frontRepos reste affiché dans Config › Projet, où l’écran dit lui-même qu’il est « Sans effet ». Un fichier est front s’il est un porteur (.vue, .svelte), s’il a un template frère (user.component.html à côté du .ts) ou s’il porte une entrée ⚡ lue dans du JSX ou du balisage ; sinon il se lit comme du back.

Palette (le goût)

clé ce qu’elle change
layers[] les couches : key (ctrl, svc, repo, m2m, help, contract), label, color (seule sa teinte compte), icon, default: true si rien ne matche : la pastille de l’Arbre
fileTypes[] l’icône d’un fichier par suffixe (match, default: true pour le reste) ; ses couleurs ne sont plus lues

Reconnaissance (projet ⊕ stacks)

Toutes ces clés ont la même double nature : ce que ton project.json écrit et ce que les stacks actives apportent — les deux listes concaténées et dédupliquées, la tienne d’abord.

clé (projet) son équivalent en stack ce qu’elle change à l’écran
layers[].match layers[] ({match, layer}) range un symbole dans une couche → la couleur de sa pastille
entries[] entries[] les quatre formes ci-dessus, avec leur kind (http, cron, hook, ui, m2m) : ce qui fait d’une méthode un point d’entrée, donc le départ d’un flux, avec son déclencheur (▶ HTTP, ⏱ CRON)
families[] families[] {key, match} : le nom compté dans l’Inventaire. Une famille ne porte aucune couche, donc aucune couleur — mais deux clés changent l’Arbre, test et mock (voir plus bas)
contractFiles[] contractFiles[] les fichiers non lus comme du code traités comme surface publique par leur suffixe (.graphql) → une ligne ◇ contrat dans l’Arbre. Le code, lui, est jugé par son contenu
crossCutting[] crossCuttingFiles[] l’infra transverse (guards, interceptors, pipes, filtres, middlewares, hooks) : elle sort du niveau 0 et s’ancre sous l’entrée qu’elle protège ; famille transverse
m2mCalls[] m2mCalls[] l’appel réseau se reconnaît au type du récepteur, en <TypeInjecté>.<verbe> (HttpService.post, ou *.post pour tout récepteur) : c’est le motif de l’injection de dépendances
m2mModules[] m2mModules[] l’appel réseau se reconnaît au module importé : [{ "module": "axios", "methods": ["get","post"] }]. Un sous-chemin du même paquet compte ; un paquet dont le nom commence pareil, non
m2mFunctions[] m2mFunctions[] l’appel réseau est une fonction libre : ["fetch"], ["$fetch"]. Le verbe vient de l’option method du second argument ; sans option c’est un GET, qui est le défaut de la plateforme
uiEvents uiEvents ce qui, parmi les attributs d’une balise, est un événement : {attrPrefix: "on"} (onClick → click) ou {attrs: [...]}. Non déclaré, aucune entrée ⚡ n’est tirée d’un attribut
carriers[] carrier les porteurs : {id, match} — les fichiers qui embarquent leur script (.vue, .svelte)
fieldInjectors[] idem les fonctions d’injection dont l’argument nomme le type d’un champ (private x = inject(Service)) : sans elles, aucun appel qui part de ce champ n’est résolu. = new X() n’a rien à déclarer
routePrefixDecorators[] idem les décorateurs de classe dont le 1er argument porte un préfixe de route (Controller) — c’est ce qui reconstruit l’URL d’un endpoint
routeVersionDecorators[] idem les décorateurs portant la version d’un endpoint (Version) : elle s’affiche en qualificatif (· v5), jamais comme un segment d’URL
behaviorDecorators[] idem les décorateurs de classe qui disent « comportement » (Component, Injectable, Module…) : une telle classe n’est jamais une classe-donnée. Rien de déclaré → angle mort « stack à déclarer »
selectorDecorators[] idem les décorateurs de classe portant un selector rendu (Component, Directive) : sans eux, aucun composant front n’est relié à sa balise (angle mort « selectors à déclarer »)
componentSuffixes[] idem les suffixes retirés du libellé d’un composant (user.component.ts → user). Cosmétique
tests tests les noms du framework de test : case, group, caseSkipped, groupSkipped, globals (jest, expect, vi) et testInfra (jest.config, setup-jest…). C’est ce qui range les tests sous la méthode que leur corps appelle. Rien de déclaré → angle mort « tests à déclarer »
builtinTypes[] idem les enveloppes, qui entourent une donnée sans en être une (Promise, Partial, Observable, NextResponse) : sans elles, Promise<OrderDto> nommerait deux données. Rien de déclaré → aucune chip « prend / rend », angle mort « enveloppes à déclarer »
plugins[] templateParser un plugin de framework : {id, match} — voir plus bas
defaultSetAside[] defaultSetAside[] les fichiers rangés d’office : ils sortent de ce qu’il te reste à relire, sous « 🗂 N de côté » par repo. « De côté » répond à dois-je le valider ?, pas à qu’est-ce que c’est ? — un module rangé d’office reste un module dans l’Inventaire

Déclarer des tests, ranger un dossier

Des fichiers de test que ta stack ne voit pas. Dans projet-api, déclare les scripts scripts/verify-*.ts comme tests :

{ "families": [{ "key": "test", "match": ["scripts/verify-"] }] }

Le motif s’apparie comme sous-chaîne du chemin, sans casse. Ces fichiers ne sont plus lus comme du code — ni symboles, ni arêtes, ni racines, ni poids dans Relecture — et ne comptent plus dans la recherche des appelants hors du diff, plafonnée à 24 fichiers (angle mort « fichiers (cap) »).

Ce que ça ne fait pas : sans framework de test actif (stack jest), Atlas ne connaît pas les noms des cas (it, describe). Chaque fichier reste un nœud-fichier hors flux, sans ligne 🧪 — mais sans rond non plus (la pastille qui dit s’il te reste à le valider) —, et l’angle mort « tests à déclarer » reste affiché, à raison. Avec un framework de test, ils deviennent des lignes 🧪 (Fichiers et Inventaire).

Un dossier entier de côté. defaultSetAside: ["fixtures/"] range tout ce que le dossier contient, à toute profondeur, en tête de chemin comme plus bas (src/fixtures/…) — jamais un fichier fixtures.ts. Un fichier de côté n’est pas lu : il reste visible au grain fichier sous « 🗂 N de côté », sans symbole ni entrée, et la carte se calcule plus vite.

⚠️ Deux écritures voisines n’apparient rien, sans un mot : fixtures sans le / final (lu comme un nom de fichier) et ./fixtures/ (un chemin vu par Atlas ne commence jamais par ./). Un / seul est ignoré.

Quel motif gagne

liste forme du motif qui gagne
layers[].match sous-chaîne de chemin + nom de la classe, insensible à la casse la première couche déclarée dont un motif matche ; sinon la couche default. Sans aucune couche configurée, un repli reconnaît .controller.ts / …Controller et /repositories/ / .repo.ts, le reste tombe en svc
families[].match suffixe (.module.ts) ou sous-chaîne du chemin (/migrations/), sans casse le suffixe d’abord, le plus long ensuite. -routing.module.ts bat .module.ts ; foo.service.spec.ts est un test, pas un service. L’ordre de déclaration n’arbitre rien
entries[] décorateur, méthode, appel, export ou wrapper le premier motif qui répond — une règle maison l’emporte donc sur celle du framework
contractFiles · crossCutting suffixe le premier qui matche
fileTypes[].match suffixe le premier type dont un motif matche ; l’entrée default sert de repli
plugins[].match · carriers[].match suffixe tout plugin dont un motif couvre le fichier le parse — d’où la fusion par id, qui garantit qu’un parseur n’y figure qu’une fois
defaultSetAside *.module.ts = suffixe ; fixtures/ = un dossier ; sinon un chemin exact, une fin de chemin, ou un nom de fichier exact. Une étoile ailleurs qu’en tête (vite.config.*) ne matche rien le premier qui matche
testInfra nom de fichier sans extension : égal, ou suivi d’un point (jest.config couvre jest.config.ts) le premier qui matche

Un motif vide dans une famille est ignoré (il matcherait tout). Les listes fusionnées sont dédupliquées : une stack déclarée deux fois rend exactement ce qu’elle rend une fois.

Les plugins de framework

Un plugin apporte la connaissance d’une syntaxe que le langage ne sait pas lire. Trois existent : angular-template (les bindings d’événement d’un .component.html), vue-sfc et svelte-sfc, qui sortent en plus le script du fichier aux lignes d’origine. Ce sont les entrées ⚡ sous un composant.

Le plugin sait parser, la config dit sur quels fichiers : la stack (templateParser, carrier) ou ton project.json (plugins: [{ "id": "angular-template", "match": [".component.html"] }], ou carriers: [...]). Les deux se fondent par id, motifs unis : un parseur ne tourne jamais deux fois sur un fichier. Un id inconnu est ignoré ; un plugin qui ne sait pas extraire de script n’est jamais porteur. Les balises d’éléments custom (avec un tiret) se lisent sans plugin.

Avant d’ajouter une règle

D’abord : pourquoi le moteur ne le sait-il pas tout seul ? La structure bat une liste de noms — la couche inter-service se déduit du type injecté, pas d’un nom de fichier qui colorerait aussi les DTO voisins. Ensuite : une règle vraie de ton framework va dans une stack, une règle vraie de ton projet dans project.json.

Le mode d’emploi, c’est l’écran : le seau non-classé de l’Inventaire dit ce qu’aucune règle ne reconnaît, et les angles morts nomment la déclaration qui manque (« préfixe à déclarer », « tests à déclarer », « enveloppes à déclarer », « entrée sans type »…).

Ce qu’Atlas ne fait pas

  • Il ne copie plus les stacks dans ton workspace, et n’écrase jamais un stack/<id>.json posé.
  • Il ne valide pas project.json contre un schéma : une clé mal orthographiée est ignorée sans un mot ; les tableaux ci-dessus sont la seule liste des noms qui agissent.
  • Il n’exécute rien pour un id inconnu : un plugins[].id inconnu est ignoré, un stack/<id>.json d’id inactif jamais lu.
  • Il ne déduit pas une entrée d’un nom : sans récepteur typé, pas de racine, un angle mort à la place. Seule une règle ["*"] accepte un récepteur quelconque, déclarée méthode par méthode.
  • Il ne versionne pas ton casier local (ce que tu as vu et ton rang de branche, à toi seul) : le .gitignore posé par atlas init l’exclut (Configurer un projet).

Limites connues

  • Une route rangée dans une constante n’est pas lue. app.get(ROUTES.list, fn) n’a pas de chaîne écrite : pas d’entrée ; sur un récepteur typé, l’angle mort « route en constante » le dit.
  • Un project.json illisible ne dit rien à l’ouverture. Un JSON cassé fait retomber Atlas sur une config minimale — aucune couche, aucun rangé d’office — et la carte s’affiche quand même, sans couleurs. Le seul endroit qui le signale est la page Config, à l’enregistrement : « project.json illisible ».
  • Un seul langage lu. Atlas lit .ts, .tsx, .mts, .cts, .js, .jsx, .mjs, .cjs, plus le script embarqué dans un .vue ou un .svelte. Un projet écrit dans un autre langage apparaît dans le diff, fichier par fichier, sans arêtes ni entrées.
  • La couche m2m reste à toi. Aucune stack ne la définit : elle dépend du nom de tes clients internes. Sans une règle layers[].match dans ton project.json, la couleur inter-service n’est jamais attribuée.
