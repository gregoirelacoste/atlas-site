Les stacks et project.json

D'où vient ce qu'Atlas reconnaît dans ton code — les couches, les points d'entrée, les contrats, les appels réseau, les tests : ce que l'outil embarque, et ce que ton project.json ajoute, refuse ou corrige.

D’où vient ce qu’Atlas reconnaît dans ton code — les couches, les points d’entrée, les contrats, les appels réseau, les tests : ce que l’outil embarque, et ce que ton project.json ajoute, refuse ou corrige.

Atlas est générique : le moteur ne connaît aucun framework. Ce qu’il sait d’un framework vient d’une stack ; ce qu’il sait de ton projet vient d’un fichier, .atlas-workspace/project.json. Où vit ce dossier, ce qui s’y partage et ce qui s’édite depuis l’écran sont dans Configurer un projet ; cette page-ci dit quelle clé change quoi, et quel motif gagne quand deux se disputent le même fichier.

Trois mots du produit reviennent : une couche (controller, service, repo…) est ce que dit la couleur de la pastille d’un symbole dans l’Arbre ; un flux est un chemin d’exécution complet, d’un point d’entrée jusqu’au bout de ce qu’il appelle ; un angle mort est un endroit où le moteur dit qu’il ne sait pas, au lieu de deviner.

Les quinze stacks livrées

Une stack est ce qu’Atlas sait d’un framework : quels suffixes font un controller, quelles formes ouvrent une entrée, quels appels sont des appels réseau. C’est de l’outil, pas du projet : les stacks sont embarquées dans Atlas et suivent ses mises à jour. Chacune se prouve seule, par une dépendance déclarée dans un package.json de ton chapeau.

stack ce qui la prouve ce qu’elle apporte
typescript typescript, ou la seule présence d’un package.json le langage : familles (test, type, const, helper, config, mock…), enveloppes (Promise, Partial, Date…), fetch comme appel réseau, setInterval comme entrée ⏱ CRON
nest @nestjs/core entrées par décorateur (Post, Get, Cron, OnEvent, hooks de cycle de vie), couches controller/repo, préfixe et version de route, appels HttpService.*, modules rangés d’office
angular @angular/core composants, directives, pipes, inject(X) qui type un champ, appels HttpClient.*, templates .component.html
graphql graphql .graphql traité comme contrat, schema.graphql rangé d’office
jest jest, vitest, jasmine-core ou mocha les noms des cas de test — les quatre partagent la même API, d’où une seule stack
react react événements JSX (onClick), familles composant/hook/page/contexte, enveloppes React
next next entrées par export (export async function PATCH dans un route.ts) et route tirée du chemin du fichier, événements JSX
vue vue le porteur .vue : son script est lu comme du code, son balisage donne les entrées ⚡
nuxt nuxt entrées par wrapper (defineEventHandler), route tirée du chemin sous server/api, $fetch comme appel réseau, porteur .vue
svelte svelte le porteur .svelte, la couche controller sur +server.ts, les stores en couche repo
express express entrées par appel (app.get('/x', fn)), couches routes/controllers/repositories, middlewares transverses
fastify fastify idem, sur un récepteur typé FastifyInstance, hooks transverses
hono hono idem, sur un récepteur Hono
koa koa, @koa/router idem, sur un récepteur Router
axios axios les appels d’un module importé (axios.patch(url)) comptent comme appels réseau

Une bibliothèque HTTP est une stack comme une autre : axios se prouve seul, sur un projet front comme sur un back. Et la stack typescript couvre aussi le JavaScript pur — un projet sans TypeScript a son manifeste, donc ses familles, ses enveloppes et ses appels fetch.

Trois listes décident lesquelles sont actives

liste qui l’écrit ce que c’est
(aucune clé) Atlas ce que les dépendances PROUVENT : les dependencies ⊕ devDependencies de tous les package.json membres, comparées aux signatures du tableau ci-dessus
recognizers toi ce que le projet AJOUTE en plus
excludeRecognizers toi ce que le projet REFUSE, même prouvé (un framework installé pour l’outillage)
recognizersActive Atlas la liste dérivée : prouvées ⊕ ajoutées − refusées. Ne l’écris pas : elle est recalculée à chaque chargement

Un refus l’emporte sur un ajout. Et parce que la première ligne se redérive à chaque chargement, une stack arrivée dans une version récente d’Atlas s’active toute seule sur un workspace existant. atlas init --stack nest,angular est une décision : il écrit recognizers avec ce que tu demandes et excludeRecognizers avec ce qu’il a détecté en plus. Sans --stack, il n’écrit ni l’une ni l’autre (la ligne de commande).

Une copie maison s’ajoute, elle ne remplace pas. Un .atlas-workspace/stack/<id>.json est fusionné par-dessus la stack livrée du même id — Atlas le dit dans son log (atlas logs) — et il n’est lu que si cet id est actif : pour un id inconnu de l’outil, aucune dépendance ne peut le prouver, donc sans entrée dans recognizers le fichier n’est jamais lu. La bonne place d’une personnalisation reste de toute façon project.json, qui fusionne aussi.

Les quatre formes d’un point d’entrée

Une entrée est le départ d’un flux. Rien n’en est une sans règle déclarée — il n’y a aucun défaut. Quatre formes, et une cinquième pour la route :

forme ce qui la déclare exemple
décorateur ou nom de méthode {decorator} ou {method} + kind @Post(), onModuleInit
appel {call: {method, recvFrom, routeArg, handlerArg}} app.get('/x', fn)
export {export: {name, file}} export async function PATCH dans route.ts
wrapper {wrapper} — un appel sans récepteur export default defineEventHandler(fn)
(la route) {routeFromPath: {root, strip, param, verbInName, prefix}} app/api/todos/[id]/route.ts → /api/todos/:id

Deux précisions qui décident de ce que tu vois :

  • Le récepteur d’une entrée par appel doit être typé. Soit par sa fabrique (const app = express()), soit par un paramètre annoté (app: FastifyInstance) — recvFrom liste les noms admis. Sans type, pas d’entrée : une racine de flux ne se gagne pas sur un nom de méthode. Atlas le dit alors par l’angle mort entry-untyped (Quand Atlas ne voit pas). Un recvFrom: [] — liste vide — dit « aucun récepteur » : la fonction est globale, comme setInterval.
  • Une route venue du chemin est complète. Elle ne porte jamais l’aveu …/ et ne demande aucun routePrefix : il n’y a rien à déclarer devant. handlerArg vaut le dernier argument par défaut, ce qui écarte un middleware écrit sur place ; et si l’argument désigné est un nom de fonction, le déclencheur va à la fonction nommée, cherchée dans le fichier puis dans ses imports — y compris hors du diff.

Les clés de project.json

Identité et périmètre

clé ce qu’elle change défaut
name le nom affiché dans le registre et l’en-tête de la config le nom du dossier
stack une étiquette libre, affichée sous le nom (nest · angular) ce que atlas init a détecté
featureId ce qui fait une feature : "ticket" ou "branch" (voir Configurer un projet) "ticket"
frontRepos une expression régulière testée sur le nom d’un repo. Sans effet sur la carte : voir ci-dessous front|web|app|pwa|-ui|admin, ou les repos dont une dépendance prouve un front
exclude les repos retirés de la découverte (Configurer un projet) []
repos[] les overrides par repo (branch, routePrefix, productionBase — Configurer un projet) []
recognizers · excludeRecognizers les stacks ajoutées / refusées absentes

repoPrefix et recognizersActive apparaissent dans la config servie à l’écran : ce sont des faits dérivés (le préfixe commun des noms de repos, la liste active). Les écrire à la main ne fait rien.

« Front » est une propriété du FICHIER, plus du repo

frontRepos reste lu, servi et affiché dans Config › Projet, où l’écran le dit lui-même : « Sans effet […] : un fichier est front par ce qu’il porte […], plus par le nom de son repo. » Le lecteur juge désormais fichier par fichier, sur trois preuves :

  1. le fichier est un porteur — il embarque son script (.vue, .svelte) ;
  2. il a un template frère — user.component.ts à côté de user.component.html ;
  3. il porte une entrée ⚡ — un événement lu dans du JSX ou dans le balisage d’un porteur.

Sinon il se lit comme du back : entrées, arêtes, racines normales. C’est ce qui rend un mono-repo lisible : dans un projet Next ou Nuxt où le front et l’API vivent dans le même dépôt, les endpoints ne partent plus sous des nœuds de composant.

Palette (le goût)

clé ce qu’elle change
layers[] les couches : key (ctrl, svc, repo, m2m, help, contract), label, color, icon, default: true pour celle qui s’applique quand rien ne matche. C’est la couleur de la pastille dans l’Arbre
fileTypes[] l’icône et les couleurs d’un fichier par suffixe (match), avec un default: true pour le reste

Reconnaissance (projet ⊕ stacks)

Toutes ces clés ont la même double nature : ce que ton project.json écrit et ce que les stacks actives apportent — les deux listes concaténées et dédupliquées, la tienne d’abord.

clé (projet) son équivalent en stack ce qu’elle change à l’écran
layers[].match layers[] ({match, layer}) range un symbole dans une couche → la couleur de sa pastille
entries[] entries[] les quatre formes ci-dessus, avec leur kind (http, cron, hook, ui, m2m) : ce qui fait d’une méthode un point d’entrée, donc le départ d’un flux, avec son déclencheur (▶ HTTP, ⏱ CRON)
families[] families[] {key, match} : le nom compté dans l’Inventaire. Inerte pour l’Arbre — une famille ne porte aucune couche, donc en ajouter une ne change aucune couleur
contractFiles[] contractFiles[] les fichiers non lus comme du code traités comme surface publique par leur suffixe (.graphql) → une ligne ◇ contrat dans l’Arbre. Le code, lui, est jugé par son contenu
crossCutting[] crossCuttingFiles[] l’infra transverse (guards, interceptors, pipes, filtres, middlewares, hooks) : elle sort du niveau 0 et s’ancre sous l’entrée qu’elle protège ; famille transverse
m2mCalls[] m2mCalls[] l’appel réseau se reconnaît au type du récepteur, en <TypeInjecté>.<verbe> (HttpService.post, ou *.post pour tout récepteur) : c’est le motif de l’injection de dépendances
m2mModules[] m2mModules[] l’appel réseau se reconnaît au module importé : [{ "module": "axios", "methods": ["get","post"] }]. Un sous-chemin du même paquet compte ; un paquet dont le nom commence pareil, non
m2mFunctions[] m2mFunctions[] l’appel réseau est une fonction libre : ["fetch"], ["$fetch"]. Le verbe vient de l’option method du second argument ; sans option c’est un GET, qui est le défaut de la plateforme
uiEvents uiEvents ce qui, parmi les attributs d’une balise, est un événement : {attrPrefix: "on"} (onClick → click) ou {attrs: [...]}. Non déclaré, aucune entrée ⚡ n’est tirée d’un attribut
carriers[] carrier les porteurs : {id, match} — les fichiers qui embarquent leur script (.vue, .svelte)
fieldInjectors[] idem les fonctions d’injection dont l’argument nomme le type d’un champ (inject, pour private x = inject(Service)) : sans elles, ces champs n’ont pas de type, donc aucun appel qui part d’eux n’est résolu. = new X() est du langage, il n’a rien à déclarer
routePrefixDecorators[] idem les décorateurs de classe dont le 1er argument porte un préfixe de route (Controller) — c’est ce qui reconstruit l’URL d’un endpoint
routeVersionDecorators[] idem les décorateurs portant la version d’un endpoint (Version) : elle s’affiche en qualificatif (· v5), jamais comme un segment d’URL
behaviorDecorators[] idem les décorateurs de classe qui disent « ceci est du comportement » (Component, Controller, Injectable, Module, Resolver…) : une classe qui en porte un n’est jamais comptée comme une classe-donnée. Rien de déclaré → angle mort behavior-decorators-undeclared
selectorDecorators[] idem les décorateurs de classe portant un selector rendu (Component, Directive) : sans eux, aucun composant front n’est relié à sa balise (angle mort component-selectors-undeclared)
componentSuffixes[] idem les suffixes retirés du libellé d’un composant (user.component.ts → user). Cosmétique : non déclaré, le libellé garde le nom de fichier entier
tests tests les noms du framework de test, par forme : case, group, caseSkipped, groupSkipped, plus globals (jest, expect, vi — un appel dont ils sont le récepteur n’éprouve rien) et testInfra (jest.config, setup-jest…). C’est ce qui fait apparaître les tests sous la méthode que leur corps appelle. Rien de déclaré → angle mort test-convention-missing
builtinTypes[] idem les enveloppes — les noms qui entourent une donnée sans en être une (Promise, Array, Partial côté langage ; Observable, Ref, NextResponse côté frameworks). C’est ce qui permet de lire les types d’une signature : sans eux, Promise<OrderDto> nommerait deux données au lieu d’une. Rien de déclaré nulle part → Atlas se tait (aucune chip « prend / rend », aucune encre sur la signature dans le Code) et pose l’angle mort builtin-types-missing
plugins[] templateParser un plugin de framework : {id, match} — voir plus bas
defaultSetAside[] defaultSetAside[] les fichiers rangés d’office : ils sortent de ce qu’il te reste à relire, sous « 🗂 N de côté » par repo. « De côté » répond à dois-je le valider ?, pas à qu’est-ce que c’est ? — un module rangé d’office reste un module dans l’Inventaire

Quel motif gagne

liste forme du motif qui gagne
layers[].match sous-chaîne de chemin + nom de la classe, insensible à la casse la première couche déclarée dont un motif matche ; sinon la couche default. Sans aucune couche configurée, un repli reconnaît .controller.ts / …Controller et /repositories/ / .repo.ts, le reste tombe en svc
families[].match suffixe (.module.ts) ou segment de chemin (/migrations/) le suffixe d’abord, le plus long ensuite. -routing.module.ts bat .module.ts ; foo.service.spec.ts est un test, pas un service. L’ordre de déclaration n’arbitre rien
entries[] décorateur, méthode, appel, export ou wrapper le premier motif qui répond — une règle maison l’emporte donc sur celle du framework
contractFiles · crossCutting suffixe le premier qui matche
fileTypes[].match suffixe le premier type dont un motif matche ; l’entrée default sert de repli
plugins[].match · carriers[].match suffixe tout plugin dont un motif couvre le fichier le parse — d’où la fusion par id, qui garantit qu’un parseur n’y figure qu’une fois
defaultSetAside *.module.ts = suffixe ; sinon un chemin exact, une fin de chemin, ou un nom de fichier exact. ⚠️ Une étoile ailleurs qu’en tête (vite.config.*) ne matche rien le premier qui matche
testInfra nom de fichier sans extension : égal, ou suivi d’un point (jest.config couvre jest.config.ts) le premier qui matche

Un motif vide dans une famille est ignoré (il matcherait tout). Les listes fusionnées sont dédupliquées : une stack déclarée deux fois rend exactement ce qu’elle rend une fois.

Les plugins de framework

Le cœur est générique ; un plugin apporte la connaissance d’une syntaxe que le langage ne sait pas lire. Trois existent : angular-template (les bindings d’événement d’un .component.html), vue-sfc et svelte-sfc. Les deux derniers tiennent deux rôles à la fois : sortir le script du fichier — aux lignes d’origine, pour que poids, empreintes et ancres restent justes — et lire son balisage. Ce sont les entrées ⚡ que tu vois sous un composant dans l’Arbre.

Le plugin sait parser, la config dit sur quels fichiers. Deux chemins d’activation : la stack (angular déclare templateParser, vue et svelte déclarent en plus carrier) ; et ton project.json, qui peut écrire plugins: [{ "id": "angular-template", "match": [".component.html"] }] ou carriers: [...] pour viser d’autres fichiers. Les deux se fondent par id et leurs motifs s’unissent : un parseur n’est jamais inscrit deux fois, donc jamais exécuté deux fois sur le même fichier. Un id inconnu d’Atlas est ignoré ; un plugin qui ne sait pas extraire de script n’est jamais retenu comme porteur. L’extraction des balises d’éléments custom (celles qui contiennent un tiret) est, elle, générique.

Avant d’ajouter une règle

Deux questions, dans cet ordre :

  1. pourquoi le moteur ne le sait-il pas tout seul ? La structure bat toujours une liste de noms : la couche inter-service se déduit du type injecté, pas d’un motif de nom de fichier — qui colorerait aussi les DTO du même dossier. Si le moteur peut le prouver, la règle est une dette ;
  2. par quel chemin quelqu’un l’activera-t-il ? Une règle vraie de ton framework va dans une stack ; une règle vraie de ton projet va dans project.json.

Le mode d’emploi de ce fichier, c’est l’écran : le seau non-classé de l’Inventaire dit ce qu’aucune règle ne reconnaît, et les angles morts nomment la déclaration qui manque (route-prefix-unresolved, behavior-decorators-undeclared, component-selectors-undeclared, test-convention-missing, builtin-types-missing, entry-decorator-unresolved, entry-untyped).

Ce qu’Atlas ne fait pas

  • Il ne copie plus les stacks dans ton workspace, et n’écrase jamais un stack/<id>.json posé.
  • Il ne valide pas project.json contre un schéma : une clé mal orthographiée est ignorée sans un mot. Les tableaux ci-dessus sont la seule liste des noms qui font quelque chose.
  • Il n’exécute rien pour un id qu’il ne connaît pas : un plugins[].id inconnu est ignoré, et un stack/<id>.json dont l’id n’est pas actif n’est jamais lu.
  • Il ne colore rien à partir d’une famille : une famille se compte dans l’Inventaire, elle ne porte aucune couche.
  • Il ne déduit pas une entrée d’un nom : sans récepteur typé, pas de racine — un angle mort à la place.

Limites connues

  • Un project.json illisible ne dit rien à l’ouverture. Un JSON cassé fait retomber Atlas sur une config minimale — aucune couche, aucun rangé d’office, aucune palette — et la carte s’affiche quand même : les pastilles perdent leur couleur, presque tout tombe sur la couche par défaut. Le seul endroit qui le signale est la page Config, à l’enregistrement : « project.json illisible ».
  • Un seul langage lu. Atlas lit .ts, .tsx, .mts, .cts, .js, .jsx, .mjs, .cjs, plus le script embarqué dans un .vue ou un .svelte. Un fichier de déclaration .d.ts n’est pas lu comme du code. Un projet écrit dans un autre langage apparaît dans le diff, fichier par fichier, sans arêtes ni entrées.
  • La couche m2m reste à toi. Aucune stack ne la définit : elle dépend du nom de tes clients internes. Sans une règle layers[].match dans ton project.json, la couleur inter-service n’est jamais attribuée.
