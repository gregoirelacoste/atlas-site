Déposer une recette

Ce que le test rend à Atlas, et sous quelle forme : le dépôt, les lieux de code, le rattachement d'une requête par sa route, les frontières hors carte, les secrets filtrés, les écarts d'environnement. Pour qui écrit le test ou le script — un humain, un outil d'intégration, ou l'IA de ta session.

Ce que le test rend à Atlas, et sous quelle forme : le dépôt, les lieux de code, le rattachement d’une requête par sa route, les frontières hors carte, les secrets filtrés, les écarts d’environnement. Pour qui écrit le test ou le script — un humain, un outil d’intégration, ou l’IA de ta session.

Le vocabulaire, une fois. Une recette est un passage de test sur une feature — le ticket qu’Atlas suit —, ouverte, déposée puis fermée par atlas recette (La recette dit la demande, l’ouverture et la relecture). Sa carte est le chemin d’appels qu’Atlas reconstruit, faite de nœuds — une ligne par symbole, identifié par son repo, son fichier et son nom. Le chapeau est le dossier qui héberge tous les repos du projet ; une feature n’en porte souvent qu’une partie.

Un dépôt ne fait que rapporter. Atlas le lit, le vérifie élément par élément, en retire les secrets et le range dans la recette ouverte ; ce qu’il refuse, il le dit, ligne par ligne, et le reste passe. Rien de ce que tu déposes n’endosse un nœud ni ne modifie le code.

Le format

atlas recette depose PROJ-412 resultat.json
mon-script-e2e | atlas recette depose PROJ-412 -

Un dépôt est un objet JSON. Tous les champs sont facultatifs, et tu déposes autant de fois que tu veux pendant la recette : chaque dépôt s’ajoute aux précédents. Déposer sans recette ouverte est refusé.

champ forme ce qu’il porte
contexte { ou, donnees, par, forme } l’environnement, en mots : déclaré, filtré, jamais vérifié
observe ["projet-api", …] les repos où le test a réellement relevé les passages dans le code
observeReseau ["projet-web", …] les repos dont tout le trafic réseau a été capté (un proxy, un journal HTTP complet)
etapes [{ n, titre, verdict, note?, preuve?, contreEpreuve? }] le verdict d’une étape, par son numéro et son titre
passages [{ lieu, etape?, recu?, rendu?, dureeMs? }] ce qu’un endroit du code a reçu, et rendu
requetes [{ etape?, methode, url, statut?, dureeMs?, enTetes?, envoye?, recu?, de?, lieux? }] une requête vue par le test ; de = le repo qui l’a émise
captures [{ fichier, etape?, legende?, lieux? }] une capture d’écran, sur la machine qui teste

Un exemple complet :

{
  "observe": ["projet-api"],
  "etapes": [
    { "n": 1, "titre": "Le client voit ses crédits", "verdict": "ok", "preuve": "solde 3 → 2", "contreEpreuve": "vue" },
    { "n": 3, "titre": "Paiement refusé", "verdict": "pas-lance", "note": "paiement de test coupé" }
  ],
  "passages": [
    { "lieu": "projet-api/src/clients/clients.service.ts:48", "etape": 1, "recu": { "id": 7 }, "dureeMs": 12 }
  ],
  "requetes": [
    { "etape": 1, "methode": "get", "url": "/clients/7/credits", "statut": 200, "de": "projet-web",
      "lieux": ["projet-api/src/clients/clients.controller.ts:31"] }
  ],
  "captures": [
    { "fichier": "captures/credits.png", "etape": 1, "legende": "le solde après rechargement" }
  ]
}

La réponse dit ce qui a été pris, une ligne ✗ par élément refusé, et les secrets filtrés.

Un lieu : repo/chemin:ligne

C’est la seule façon de désigner du code dans une recette. Le chemin commence par le nom du repo, tel que la feature le connaît ; une colonne après la ligne (:48:5) est tolérée. Atlas en déduit le nœud, en deux temps :

  1. il cherche le symbole qui englobe cette ligne dans le code testé — au commit relevé à l’ouverture, ou dans la copie de travail si elle était modifiée ;
  2. si ce symbole est un nœud de la carte, le lieu s’y rattache ; sinon, il se rattache au nœud-fichier s’il existe ; sinon, il est refusé.

Jamais un lieu n’est posé sur un autre symbole du même fichier, sous prétexte qu’il est voisin. Les refus nomment la cause :

ce que tu as écrit pourquoi c’est refusé
src/clients/clients.service.ts:48 le chemin ne commence pas par un repo de la feature — la raison liste ceux qu’elle connaît
autre-repo/src/x.ts:12 ce repo n’est pas dans la feature — sauf s’il est membre du chapeau et que le lieu est celui d’une requête : il devient une frontière hors carte (plus bas) ; sur un passage ou une capture, refusé, et la raison dit pourquoi. Un repo inconnu du chapeau est refusé, la raison nomme les deux listes
projet-api/src/x.ts il manque :ligne
projet-api/src/x.ts:0 une ligne commence à 1
un chemin qui contient .. ou commence par / après le repo chemin invalide
une ligne dans un fichier que la carte ne connaît pas « … n’est pas un nœud de la carte de cette feature »
une ligne d’un fichier qui n’est pas du code (un template, un JSON) elle vise le nœud-fichier ; refusée s’il n’est pas sur la carte
un etape inconnu, un statut ou dureeMs qui n’est pas un nombre le champ est ignoré et le refus le dit ; l’élément est gardé

Un lieu refusé n’emporte pas le reste du dépôt, ni la requête. Carte illisible au dépôt : aucun lieu rattaché, un refus le dit, les verdicts restent.

Une requête se pose aussi par sa route

Une requête n’a pas besoin de lieu pour atteindre la carte : Atlas connaît la route de chaque entrée HTTP (▶) et de chaque appel réseau (⇄) de la carte, et la confronte à la méthode et à l’URL rapportées. Ce calcul se fait à la relecture, jamais au dépôt : une recette déjà déposée en profite sans rien refaire, et un dépôt de requêtes sans lieu ne recalcule pas la carte.

  • L’entrée qui la reçoit : même verbe, et la route est la fin exacte du chemin de l’URL (un :id de la route accepte n’importe quelle valeur). Une ressemblance de fin de chemin ne suffit pas.
  • La version : une entrée déclarée en v5 exige un segment /v5/ dans l’URL — /v3/… ne s’y pose jamais. Une entrée sans version atteinte par une URL qui en porte une, devant sa route, est posée version non confrontée ; un v2 écrit dans la route elle-même est confronté par elle.
  • L’appel qui l’émet : seulement si la requête dit de, le repo qui l’a émise. La route seule ne dit pas qui l’a envoyée — un harnais de test et l’app peuvent appeler la même. Sans de, aucun appel n’est posé par la route.
  • Deux candidats, aucun : deux entrées (ou deux appels du même repo) qui conviennent ne posent rien ; la requête dit ambigu entre … et les nomme.
  • Un statut de 400 ou plus : la requête se lit sur l’entrée, avec son statut, mais l’entrée ne compte pas traversée — elle a répondu sans faire son travail. Sans autre passage, elle se lit atteinte, N requêtes refusées, jamais « non traversé » tout court.
  • La preuve la plus forte gagne : une entrée dont la version est confrontée écarte celle qui ne déclare pas de version sur la même route ; l’ambiguïté ne se dit qu’entre candidats de même force.

Chaque rattachement dit son témoin : lieu du test, par la route, ou les deux. Un lieu d’entrée (ou d’appel) qui n’est pas celle que la route désigne la contredit : il ne pose rien, et le désaccord se compte. Un lieu sur un autre nœud (un service) ne contredit jamais rien.

Une requête qu’aucun nœud ne porte n’est pas jetée : elle reste un échange hors carte, groupé par méthode et chemin, compté, et show nomme les plus fréquents. À l’écran, le Passage d’une requête dit son témoin, et la tête de l’Arbre et l’onglet Recette comptent les échanges hors carte (La recette, « Dans l’écran »).

Les frontières hors carte

Le lieu d’une requête vers un repo membre du chapeau qui ne porte pas le ticket — l’API qu’appelle ton app, par exemple — n’est plus refusé : il est gardé tel quel en frontière hors carte, sans nœud ni rond, jamais vérifié (la carte ne lit pas ce repo), nommé avec sa requête et compté.

Les verdicts, en trois états

Un verdict vaut ok, ko ou pas-lance. Tout critère testable dans le contexte se teste ; pas-lance dit pourquoi dans note, ou il est refusé. Une étape passée dit sa preuve et si elle a été vue en échec (vue · pas-vue · impossible) : l’onglet le montre. Le verdict le plus récent fait foi.

Sont refusés : un numéro absent de la demande, un titre qui ne correspond plus (le ticket a changé depuis que le test a été écrit : un numéro seul se décale), un verdict hors des trois valeurs, et toute étape manuelle, qui ne se clôt par aucun dépôt.

observe : « rien rapporté » n’est pas « non traversé »

Un nœud sans passage ne veut pas dire la même chose selon que quelqu’un regardait ou non. observe nomme les repos où ton test a vraiment relevé les passages — une sonde, des traces, un journal. Pour un nœud de ces repos, l’absence de passage se lit non traversé ; ailleurs, rien rapporté. Ne mets un repo dans observe que si c’est vrai : sinon, chaque nœud que ton test n’a pas instrumenté se lirait comme du code que la recette n’a pas atteint. Un repo qui n’est pas dans la feature est refusé.

observeReseau : le réseau vu en entier

observeReseau nomme les repos dont ton test a capté tout le trafic réseau. Pour ces repos, une entrée ▶ ou un appel ⇄ de la carte sans aucune requête se lit non traversé (réseau). Les autres nœuds du même repo — un service interne — restent rien rapporté : le réseau ne dit rien de ce qui ne passe pas par lui. Sans ce champ, rien n’est déduit.

Les captures

fichier : une image sur la machine qui teste. Atlas la copie dans la recette — png · jpg · jpeg · webp · gif, 5 Mo au plus ; sinon refusée, avec son nom.

Les secrets

Tout ce qui entre traverse le filtre avant d’être écrit, refus compris.

ce qu’Atlas filtre comment
un champ dont le nom contient password, passwd, pwd, secret, token, authorization, cookie, apikey, privatekey ou credential sa valeur devient ‹filtré› — casse, tirets, points et soulignés ignorés : X-API-Key et client_secret sont pris
un jeton au format JWT, ou Bearer …, où qu’il soit écrit remplacé par ‹filtré›, même au milieu d’une note
clé=valeur avec un nom sensible, dans une URL, un corps de formulaire ou une note la valeur devient ‹filtré›
un corps enregistré en texte qui contient du JSON lu comme du JSON, filtré champ par champ, et gardé lisible

recette.sensibles dans project.json ajoute des noms (iban, numeroSecu), jamais à la place.

Atlas dit ce qu’il a retiré : secrets filtrés : Authorization ×1 · password ×2. Le nom du champ et le nombre, jamais la valeur, ni dans la réponse, ni dans la recette.

⚠️ Le filtre juge un nom : tokenCount sera filtré, un numéro de carte sous valeur non — déclare-le dans sensibles.

Les écarts d’environnement

Tester oblige souvent à réparer quelque chose qui n’est pas le code de la feature : une variable posée à la main, un rôle ajouté à un compte, une migration rejouée. C’est un écart, et il se consigne :

atlas recette ecart PROJ-412 "variable PAIEMENT_URL posée à la main" --peut-masquer oui

--peut-masquer oui : ce changement a pu faire réussir ce qui aurait échoué en vrai — ces écarts-là sont nommés, précédés de ⚠, à chaque relecture. Le texte passe par le filtre des secrets.

Ce qu’Atlas ne fait pas

  • Il ne devine pas un lieu : un chemin sans repo, une ligne hors carte, un symbole voisin — refusés, avec leur raison.
  • Il ne déduit jamais un émetteur, une version ni une observation : de, observe et observeReseau se déclarent ; ce qui n’est ni déclaré ni prouvé par la carte se dit, jamais deviné.
  • Il ne vérifie pas une frontière hors carte : la carte ne lit pas ce repo, le lieu est gardé tel que le test l’a écrit.
  • Il ne stocke pas le rattachement par la route : il le recalcule à chaque relecture, contre la carte du moment.
  • Il ne recopie jamais un secret retiré, ni dans la recette, ni dans ses refus, ni dans ce qu’il dit avoir filtré.

Limites connues

  • Un lieu se rattache à la carte d’aujourd’hui : un symbole renommé ou retiré depuis l’ouverture fait refuser le lieu.
  • Seules les entrées que la carte étiquette se trouvent par la route : une entrée que la feature ne touche pas porte rarement sa route sur la carte, et une requête qui la vise reste un échange hors carte.
  • Les échanges hors carte se groupent par chemin, un identifiant compté comme * : /dossiers/12 et /dossiers/13 font une ligne ×2 — un regroupement pour lire, qui ne rattache rien.
  • Une capture est jugée par l’extension de son nom.
  • Le filtre juge des noms et deux formes de jeton : une valeur sensible sous un nom ordinaire passe, tant que tu ne déclares pas ce nom dans sensibles.
