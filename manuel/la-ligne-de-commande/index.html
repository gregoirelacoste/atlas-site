La ligne de commande

Toutes les commandes de l'exécutable atlas : ouvrir une carte, déclarer un projet, piloter le daemon, se mettre à jour, brancher ton IA. Pour chacune : ce qu'elle fait, ce qu'elle écrit, ce qu'elle ne fait pas.

Toutes les commandes de l’exécutable atlas : ouvrir une carte, déclarer un projet, piloter le daemon, se mettre à jour, brancher ton IA. Pour chacune : ce qu’elle fait, ce qu’elle écrit, ce qu’elle ne fait pas.

Cette page ne couvre pas l’installation du paquet ni le premier atlas init — voir Prise en main. Elle ne couvre pas non plus le détail de .atlas-workspace/ et de ses clés — voir Configurer un projet et Les stacks et project.json — ni ce qu’une IA fait une fois branchée — voir Brancher l’IA. Ici : la commande, ses arguments, sa sortie, et rien d’inventé — tape atlas help pour la même liste, en plus court.

Quelques mots avant la liste : une feature est le ticket (ou la fonctionnalité) qu’Atlas suit une à la fois, et sa carte le flux d’appels qu’il en reconstruit. Le daemon est le process qui tourne en arrière-plan et sert à la fois l’API et la page web. Un workspace — ou chapeau — est le dossier qui héberge plusieurs repos d’un même projet, sous .atlas-workspace/ ; le registre est la liste des projets connus, tenue hors de tout workspace. Le plugin pose les skills Atlas dans Claude Code ; MCP est le protocole par lequel un client IA interroge Atlas.

Toutes les commandes, d’un coup d’œil

Commande À quoi elle sert
atlas démarre le daemon si besoin, ouvre la carte du projet du dossier courant
atlas init déclare un dossier comme projet Atlas
atlas start démarre le daemon
atlas stop l’arrête
atlas restart l’arrête puis le redémarre
atlas status l’état et la version de l’instance qui tourne
atlas version la version de l’instance, en JSON
atlas logs suit les journaux du daemon
atlas update installe la dernière version publiée
atlas promote (contributeurs d’Atlas) installe TON code dans TON instance
atlas plugin [install] branche les skills Atlas sur ta session de code
atlas mcp le serveur que ton IA interroge (lancé par elle, pas à la main)
atlas guide [MOMENT] le mode d’emploi d’Atlas pour un skill de review maison
atlas brief <TICKET> la carte d’une feature en une page de texte
atlas precedents --build reconstruit l’index des reviews passées
atlas precedents <TICKET> ce qu’une review passée dit sur cette feature
atlas claude (contributeurs d’Atlas) une session Claude Code isolée aux skills d’Atlas
atlas help cette liste

-h et --help sont les mêmes que help. Toute commande inconnue affiche commande inconnue : …, réimprime cette aide et sort en erreur.

Ouvrir une carte

atlas   # démarre le daemon si besoin, active le projet du dossier courant, ouvre le navigateur

Tapée sans argument (ou avec open), atlas fait trois choses dans l’ordre : elle démarre le daemon s’il ne répond pas déjà ; elle cherche un .atlas-workspace/ en remontant depuis le dossier courant — comme git remonte à son .git/ — et si elle en trouve un, elle bascule le daemon sur ce projet ; puis elle ouvre le navigateur sur la carte.

⚠️ Cette bascule est un effet de bord réel, pas un détail d’affichage : un daemon ne sert qu’un projet actif à la fois. Taper atlas dans un autre chapeau change ce que voit quiconque a déjà la page ouverte ailleurs — y compris atlas brief ou atlas precedents lancés depuis un troisième dossier, qui font la même bascule en silence (leur sortie part sur stderr, pas sur le texte qu’ils produisent). Si aucun .atlas-workspace/ n’est trouvé, rien ne bascule : Atlas garde le dernier projet actif du registre.

Si aucun navigateur ne peut s’ouvrir (poste sans interface), la commande imprime l’URL au lieu d’échouer. Elle n’écrit rien de nouveau elle-même : au plus le pidfile et le journal du daemon qu’elle vient de démarrer (voir plus bas), et l’enregistrement du projet détecté dans le registre — détaillé dans Prise en main.

Déclarer un projet

atlas init                        # déclare le dossier courant
atlas init /chemin/vers/chapeau   # déclare un autre dossier
atlas init --stack nest,angular   # force les stacks au lieu de les laisser se déduire

atlas init crée .atlas-workspace/ dans le dossier cible : project.json, un dossier features/ vide, un .gitignore (pour que versionner ce dossier soit sûr) et ESPACES.md (qui écrit quoi dedans). Le détail de ce que contient project.json — couches, familles, repos exclus — est dans Les stacks et project.json ; le déroulé complet du premier lancement (détection des stacks, des repos front, déclaration de la première feature) est dans Prise en main.

Ce qui est propre à la commande elle-même :

  • DIR est optionnel (défaut : le dossier courant) et doit déjà exister sur le disque, sinon la commande sort en erreur.

  • --stack a,b accepte aussi --stack=a,b ; une stack inconnue (ni détectée, ni dans la liste livrée) fait échouer la commande en listant les stacks disponibles. Quinze sont livrées : angular, axios, express, fastify, graphql, hono, jest, koa, nest, next, nuxt, react, svelte, typescript, vue.

  • Sans --stack, elle n’écrit aucune liste de stacks : elle imprime ce que les dépendances prouvent, et le serveur le redérive à chaque chargement. Avec --stack, ton choix gagne : il est écrit tel quel, et ce qui était détecté en plus est écrit comme un refus. La commande signale l’écart sans rien changer.

  • Un projet en JavaScript pur est reconnu : la seule présence d’un package.json prouve le langage, donc les familles de fichiers et les appels fetch fonctionnent sans TypeScript.

  • Elle lit les branches des repos membres pour écrire ce qui fait une feature ici — un jeton de ticket dans le nom, ou bien chaque branche — et la ligne de base du projet. Deux décisions, modifiables ensuite depuis Config › Projet (Configurer un projet).

  • Les stacks se prouvent par les dépendances de tous les paquets d’un dépôt à espaces de travail, pas seulement de sa racine : un package.json de racine qui ne déclare rien ne fait pas conclure « aucune stack ».

  • Elle refuse de s’exécuter sur le repo d’Atlas lui-même — un garde-fou contre un .atlas-workspace/ parasite niché dans l’outil, pas dans ton projet.

  • Si .atlas-workspace/ existe déjà, elle le dit et n’écrase rien — ni project.json, ni une stack déposée à la main — mais elle continue quand même : elle réenregistre le projet dans le registre si le daemon tourne.

  • Elle ne fait pas git init, ne crée aucune branche, et n’installe pas le plugin IA : ce dernier geste touche ta configuration Claude Code, pas ce projet, et se prend à part avec atlas plugin install (plus bas).

Ce qu’elle imprime, sur un chapeau à un repo :

✓ stacks DÉTECTÉES dans 1 repo(s) : fastify, typescript  (dépendances déclarées)
✓ features par BRANCHE : aucun jeton de ticket dans 4 branche(s) — chaque branche est une feature,
  nommée par son dernier segment (`featureId: "branch"`, éditable dans Config › Projet)
✓ ligne de base : `master` — détectée dans 1 repo(s) (`base` dans project.json, éditable dans Config › Projet)
✓ ~/dev/atlas-ws/.atlas-workspace créé (project.json + features/ + .gitignore + ESPACES.md)
  · stacks actives : fastify, typescript (prouvées par les dépendances — re-dérivées à chaque chargement)

La ligne de base est détectée par repo : la branche que désigne origin/HEAD quand ce n’est pas une feature, sinon la première présente parmi develop, master, main. Deux cas ne s’écrivent pas, et se disent : ⚠ bases hétérogènes quand les repos ne sont pas d’accord — la déclaration reste à toi, par projet ou par feature —, et ⚠ aucune ligne de base détectée quand aucun repo n’en montre ; Atlas cherchera alors develop, et le dira repo par repo.

Le daemon

atlas start     # démarre le daemon (port 3030 par défaut)
atlas stop      # l'arrête
atlas restart   # stop puis start
atlas status    # état + version de l'instance qui tourne
atlas version   # la version, en JSON brut
atlas logs      # suit les journaux (20 dernières lignes, puis en direct)

Le daemon sert l’API et la page web sur le même port — jamais deux process. atlas start ne fait rien s’il répond déjà (« atlas déjà en marche ») au lieu de tenter un second lancement ; sinon il le démarre détaché, capable de survivre à la fermeture du terminal, puis attend jusqu’à 30 secondes qu’il réponde avant d’abandonner.

atlas stop envoie un signal d’arrêt propre et attend jusqu’à 10 secondes ; passé ce délai, elle force l’arrêt. Si rien ne répond sur le port, elle le dit et nettoie le pidfile sans rien tuer. Et si quelque chose répond sur le port mais que le pidfile ne porte pas ce process — un daemon lancé autrement, par npm run dev par exemple — elle refuse de tuer à l’aveugle : elle te dit d’arrêter ce process là où tu l’as lancé.

atlas status affiche ● en marche avec l’adresse et, quand elle le connaît, le pid du process qu’elle a lancé (elle peut répondre sans pid si le daemon vient d’ailleurs), suivi de la version en JSON. Sans daemon, elle affiche ○ arrêté — jamais un troisième état ici, la question est binaire.

atlas version répond selon ce qu’elle a pu voir, de la source la plus fiable à la moins précise : si le daemon répond, c’est lui qui donne la version qui tourne réellement ; sinon, si un paquet est installé, la version vient du fichier écrit par ce paquet à sa fabrication ; si aucun des deux n’existe (aucun daemon, aucun paquet buildé), elle rend {"version":"?"}. Elle ne dit jamais si cette version est la dernière disponible — savoir si tu es en retard est une question différente, posée par atlas update (juste après) ou affichée par Config › Atlas en trois états (à jour, une version existe, ou « je n’ai pas pu regarder » — voir Configurer un projet) ; atlas version dit ce qui tourne, jamais si c’est suffisant.

atlas logs affiche les 20 dernières lignes puis suit le fichier en direct (l’équivalent d’un tail -f), sans dépendre d’aucun outil système. Sans journal (daemon jamais lancé), elle le dit et s’arrête.

Le port se règle avec ATLAS_PORT (ou PORT), défaut 3030 ; pidfile et journal sont indexés par port dans le dossier d’état d’Atlas (~/.local/state/atlas/, ou $XDG_STATE_HOME/atlas) — deux instances sur deux ports coexistent sans se marcher dessus. start, stop, restart et status pilotent le daemon lui-même, quel que soit le dossier où tu te trouves ; c’est atlas (sans argument) qui, lui, bascule le projet actif sur ce daemon.

Se mettre à jour

atlas update                        # installe la dernière version PUBLIÉE, redémarre, rafraîchit le plugin
atlas promote                       # (contributeurs d'Atlas) reconstruit TON code, l'installe, redémarre
atlas promote --from ~/dev/atlas    # depuis un dossier qui n'est pas ton clone courant

Les deux commandes se ressemblent — même fin (redémarrage, rafraîchissement du plugin, affichage de la version) — et ne servent pas la même personne :

atlas update atlas promote
pour qui tout le monde, y compris un contributeur seulement un contributeur, dans un clone du dépôt Atlas
installe quoi la dernière version publiée au registre npm ton code local, empaqueté puis installé
trouvée où n’importe où remonte depuis le dossier courant jusqu’à trouver un clone du dépôt Atlas
en échec dit qu’il manque le registre et le jeton, avec les deux lignes npm config set à taper dit qu’aucun clone n’est trouvable ; --from CHEMIN en donne un explicitement

atlas promote n’apparaît dans atlas help que si un tel clone existe à portée — elle reste tapable sinon, juste absente de l’aide, pour ne pas annoncer une capacité que tu ne peux pas utiliser.

⚠️ Depuis un clone du dépôt Atlas, atlas update fait ce qu’elle dit, pas ce qu’on croit vouloir : elle prévient (« ceci installe la dernière version PUBLIÉE, pas ton code ») puis installe quand même la version publiée — qui peut être en dessous du code que tu viens d’écrire. C’est atlas promote qu’il faut taper pour tester son propre code.

Les deux commandes écrivent : elles installent un paquet npm en global (donc hors d’Atlas et hors de ton projet), redémarrent le daemon par le binaire global fraîchement posé, et — seulement si le plugin Claude Code est déjà installé — le rafraîchissent (plugin update ou une réinstallation complète selon que le numéro de version suffit à prouver la différence). Ni l’une ni l’autre ne touche un repo analysé, une branche, ou .atlas-workspace/.

Brancher ton IA

atlas plugin            # affiche les deux commandes à lancer, sans les exécuter
atlas plugin install    # les exécute : branche les skills Atlas sur ta session de code

Le plugin installe les skills Atlas dans Claude Code — les trois qu’on retape le plus souvent sont /atlas:as-coded, /atlas:review et /atlas:answer. Sans argument, atlas plugin imprime les deux commandes Claude Code à taper (elles marchent aussi en /plugin … dans une session déjà ouverte) — elle n’exécute rien elle-même. install les exécute : elle écrit dans ta configuration Claude Code globale, jamais dans ce projet ni dans un repo. Si le plugin est déjà posé, install ne répond pas juste « déjà installé » : elle le réinstalle entièrement (elle ne peut pas se fier au numéro de version pour savoir s’il y a du neuf) — le même geste que fait atlas promote en fin de parcours, pas celui, plus léger, d’atlas update.

atlas init ne fait jamais ce geste à ta place — c’est délibéré, un plugin touche ta session entière, pas seulement ce projet. Ce que le plugin permet une fois posé — les skills, le serveur MCP, ce qu’une IA peut écrire et ce qu’elle ne peut pas — est dans Brancher l’IA et Ce que l’IA lit et écrit.

Les commandes qui servent l’IA

Cinq commandes ne sont pas pensées pour être tapées de mémoire tous les jours : elles sont la surface par laquelle une IA (ou un skill que tu écris toi-même) parle à Atlas.

atlas mcp                          # le serveur MCP — lancé par ton client IA, pas à la main
atlas guide review                 # le mode d'emploi d'Atlas pour un skill de review maison
atlas brief PROJ-412                # la carte d'une feature, en une page de texte
atlas precedents --build           # reconstruit l'index des reviews passées
atlas precedents PROJ-412 --json    # ce que les reviews passées disent, ligne par ligne, sur cette feature

atlas mcp démarre le serveur MCP (le protocole qui laisse un client IA interroger Atlas) sur l’entrée/sortie standard — ce n’est pas une commande qu’on tape : c’est ton client IA qui la lance lui-même, une fois branché. Elle résout le projet actif depuis le dossier où la session a été ouverte, avec une garde stricte : si le daemon sert déjà un autre projet que celui de cette session, elle refuse de répondre plutôt que de rendre une carte plausible et fausse. Elle n’écrit rien elle-même — ce que les outils qu’elle expose peuvent écrire (des annotations, des fils de conversation, jamais ta validation ni le code) est détaillé dans Ce que l’IA lit et écrit.

atlas guide [MOMENT] imprime, sur la sortie standard, le mode d’emploi d’Atlas pour un moment donné — aujourd’hui review et answer — à coller dans un skill de review maison qui doit continuer à écrire dans Atlas (fils, notes) sans passer par les skills d’Atlas eux-mêmes. Sans argument, elle liste les moments disponibles. Elle ne fait que lire des fichiers du plugin ; rien n’est écrit.

atlas brief <TICKET> imprime, sur la sortie standard, la carte d’une feature réduite à du texte — de quoi la coller dans une revue, un message, ou la donner à lire à un agent qui n’ouvre pas Atlas. --base <branche> force la branche de comparaison pour cet appel. Elle démarre le daemon si besoin (en silence, sur l’erreur standard, pour ne pas polluer le texte produit) et active le projet du dossier courant — le même effet de bord que atlas tout court. Elle laisse jusqu’à 5 minutes avant d’abandonner : une grosse feature multi-repos peut prendre du temps, et une réponse lente n’est pas une panne.

atlas precedents a deux visages. Un précédent est le souvenir de ce qu’une review a déjà dit sur un nœud du même genre (une méthode, un contrat…) ailleurs — de quoi éviter de rouvrir un débat déjà tranché. --build [--full] reconstruit cet index des précédents : elle rejoue les features qui ont déjà porté un fil de review, et écrit .atlas-workspace/precedents.json — un fichier partagé, pas seulement local à toi. C’est une passe longue (des dizaines de cartes rejouées, jusqu’à une heure avant qu’Atlas l’abandonne), et elle affiche des chiffres bruts (combien de fils retrouvés, combien suivis d’un changement, combien de réponses humaines) plutôt qu’un jugement : elle sert à savoir si le mécanisme vaut la peine, pas à le lire au quotidien. --full la refait sans repartir de l’index déjà là. atlas precedents <TICKET> — sans --build — lit cet index et sert, pour chaque nœud de cette feature, le précédent le plus proche du même type : ce qu’il disait, si un humain a répondu, si le code a changé après, si les tests ont bougé. --json rend la réponse brute plutôt que le texte mis en forme. Cette seconde forme ne modifie rien.

atlas claude [--dry-run] [ARGS…] ouvre une session Claude Code isolée aux skills d’Atlas — elle ne charge ni les skills, ni le CLAUDE.md du projet que tu es en train de faire relire. Elle n’a de sens que si tu as le dépôt d’Atlas lui-même sur ta machine (elle sert au dogfooding d’Atlas sur son propre code) : si tu utilises Atlas sur ton projet, tu n’en as pas besoin — c’est atlas plugin install, plus haut, qui te concerne. --dry-run affiche la commande qu’elle lancerait sans la lancer. Elle échoue si aucun .atlas-workspace/ n’est trouvable (ni sous le dossier courant, ni comme projet actif du registre) ou si le binaire claude n’est pas dans le PATH.

Variables d’environnement et options globales

Trois seulement changent directement ce que fait une commande de cette page ; la liste complète (jetons GitLab/GitHub, trace de debug…) est dans Configurer un projet.

Variable Effet Défaut
ATLAS_PORT ou PORT le port du daemon — start, stop, status, logs s’appliquent à ce port 3030
ATLAS_WORKSPACE force un workspace au tout premier démarrage du daemon seulement — ensuite le registre décide la remontée depuis le dossier courant
ATLAS_CLAUDE_BIN le binaire lancé par atlas claude et par atlas plugin claude

Aucune option globale (--verbose, --json…) ne s’applique à toutes les commandes : chaque commande a les siennes, listées ci-dessus.

Ce qu’Atlas ne fait pas

  • Aucune commande ne se met à jour toute seule : atlas update est toujours un geste que tu tapes.
  • atlas init ne fait pas git init, ne crée aucune branche, et n’installe pas le plugin IA à ta place.
  • Aucune commande de cette page ne touche un repo analysé : ni son contenu, ni ses branches, ni un dépôt distant. La seule écriture qui sorte d’Atlas est celle des skills une fois branchés (voir Ce que l’IA lit et écrit), jamais celle de la ligne de commande elle-même.
  • atlas mcp ne se tape pas à la main : c’est un serveur de protocole, lancé par ton client IA.
  • Un daemon ne sert jamais deux projets à la fois : toute commande qui parle d’une feature bascule le projet actif plutôt que de répondre sur le mauvais.
  • atlas update ne vérifie pas elle-même si tu es en retard : elle installe directement ce que le registre appelle « la dernière version ». C’est Config › Atlas qui juge, en trois états, s’il vaut la peine de la taper (voir Configurer un projet).

Limites connues

atlas update et atlas promote ne sont éprouvées que sous Linux : la façon dont elles retrouvent le binaire fraîchement installé ne tient pas encore sous Windows (détail dans Prise en main). atlas plugin et atlas claude supposent un binaire claude dans le PATH — sans lui, elles le disent et s’arrêtent, elles ne l’installent pas.
