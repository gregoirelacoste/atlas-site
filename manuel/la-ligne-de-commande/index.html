La ligne de commande

Toutes les commandes de l'exécutable atlas : ouvrir une carte, déclarer un projet, piloter le daemon, se mettre à jour, brancher ton IA, construire et contrôler l'index des précédents — ce que chacune fait, écrit, et ne fait pas.

Toutes les commandes de l’exécutable atlas : ouvrir une carte, déclarer un projet, piloter le daemon, se mettre à jour, brancher ton IA, construire et contrôler l’index des précédents — ce que chacune fait, écrit, et ne fait pas.

Elle ne couvre ni l’installation du paquet (Prise en main), ni les clés de .atlas-workspace/ (Configurer un projet, Les stacks et project.json), ni ce qu’une IA fait une fois branchée (Brancher l’IA). atlas help donne la même liste, en plus court.

Le vocabulaire, une fois : une feature est le ticket qu’Atlas suit un à la fois, et sa carte le flux d’appels qu’il en reconstruit. Le daemon tourne en arrière-plan et sert l’API comme la page web. Un workspace — ou chapeau — héberge plusieurs repos d’un même projet, sous .atlas-workspace/ ; le registre est la liste des projets connus. Le plugin pose les skills Atlas dans Claude Code ; MCP est le protocole par lequel un client IA interroge Atlas.

Toutes les commandes, d’un coup d’œil

Commande À quoi elle sert
atlas démarre le daemon si besoin, ouvre la carte du projet du dossier courant
atlas init déclare un dossier comme projet Atlas
atlas start démarre le daemon
atlas stop l’arrête
atlas restart l’arrête puis le redémarre
atlas status l’état et la version de l’instance
atlas version la version de l’instance, en JSON
atlas logs suit les journaux du daemon
atlas update installe la dernière version publiée
atlas promote (contributeurs d’Atlas) installe TON code dans TON instance
atlas plugin [install] branche les skills Atlas sur ta session de code
atlas mcp le serveur que ton IA interroge (lancé par elle)
atlas brief <TICKET> la carte d’une feature en une page de texte
atlas precedents --build construit ou rafraîchit l’index des reviews passées
atlas precedents --controle le contrôle humain : des paires tirées, tu réponds
atlas precedents <TICKET> ce que les reviews passées disent de cette feature
atlas claude (contributeurs d’Atlas) une session Claude Code isolée à ses skills
atlas help cette liste

-h et --help valent help. Une commande inconnue affiche commande inconnue : …, réimprime cette aide et sort en erreur.

Ouvrir une carte

atlas   # démarre le daemon si besoin, active le projet du dossier courant, ouvre le navigateur

Tapée sans argument (ou avec open), atlas fait trois choses dans l’ordre : elle démarre le daemon s’il ne répond pas déjà ; elle cherche un .atlas-workspace/ en remontant depuis le dossier courant — comme git remonte à son .git/ — et bascule le daemon sur ce projet ; puis elle ouvre le navigateur. Sans navigateur possible (poste sans interface), elle imprime l’URL au lieu d’échouer, et n’écrit rien d’autre que le pidfile, le journal du daemon et le projet dans le registre.

⚠️ Cette bascule est un effet de bord réel, pas un détail d’affichage : un daemon ne sert qu’un projet actif à la fois. Taper atlas dans un autre chapeau change ce que voit quiconque a déjà la page ouverte ailleurs — y compris atlas brief ou atlas precedents lancés depuis un troisième dossier, qui font la même bascule en silence. Si aucun .atlas-workspace/ n’est trouvé, rien ne bascule : Atlas garde le dernier projet actif du registre.

Déclarer un projet

atlas init                        # déclare le dossier courant
atlas init /chemin/vers/chapeau   # déclare un autre dossier
atlas init --stack nest,angular   # force les stacks au lieu de les laisser se déduire

atlas init crée .atlas-workspace/ dans le dossier cible : project.json, un dossier features/ vide, un .gitignore (pour que versionner ce dossier soit sûr) et ESPACES.md (qui écrit quoi dedans) — voir Les stacks et project.json. Propre à la commande :

  • DIR est optionnel (défaut : le dossier courant) et doit déjà exister, sinon elle sort en erreur.
  • --stack a,b accepte aussi --stack=a,b ; une stack inconnue fait échouer la commande en listant les quinze livrées : angular, axios, express, fastify, graphql, hono, jest, koa, nest, next, nuxt, react, svelte, typescript, vue.
  • Sans --stack, elle n’écrit aucune liste de stacks : elle imprime ce que les dépendances prouvent, et le serveur le redérive à chaque chargement. Avec --stack, ton choix gagne : il est écrit tel quel, ce qui était détecté en plus devient un refus, et l’écart est signalé sans rien changer.
  • Elle lit les branches des repos membres pour écrire ce qui fait une feature ici — un jeton de ticket dans le nom, ou bien chaque branche — et la ligne de base du projet. Deux décisions, modifiables ensuite depuis Config › Projet (Configurer un projet).
  • Elle refuse de s’exécuter sur le repo d’Atlas lui-même, et si .atlas-workspace/ existe déjà elle le dit et n’écrase rien — mais elle continue, et réenregistre le projet dans le registre.

Chaque décision s’imprime au passage, une ligne chacune — ✓ stacks DÉTECTÉES…, ✓ features par BRANCHE… ou par TICKET, ✓ ligne de base : …, puis le dossier créé. La ligne de base est détectée par repo : la branche que désigne origin/HEAD quand ce n’est pas une feature, sinon la première présente parmi develop, master, main. Deux cas ne s’écrivent pas et se disent, ⚠ bases hétérogènes et ⚠ aucune ligne de base détectée — Atlas cherchera alors develop, et le dira repo par repo. La déclaration reste à toi.

Le daemon

atlas start     # démarre le daemon (port 3030 par défaut)
atlas stop      # l'arrête
atlas restart   # stop puis start
atlas status    # état + version de l'instance qui tourne
atlas version   # la version, en JSON brut
atlas logs      # suit les journaux (20 dernières lignes, puis en direct)

Le daemon sert l’API et la page web sur le même port — jamais deux process. atlas start ne fait rien s’il répond déjà (« atlas déjà en marche ») ; sinon il le démarre détaché, capable de survivre au terminal, puis attend jusqu’à 30 secondes qu’il réponde.

atlas stop envoie un signal d’arrêt propre et attend jusqu’à 10 secondes ; passé ce délai, elle force l’arrêt. Si rien ne répond sur le port, elle le dit et nettoie le pidfile sans rien tuer. Et si quelque chose répond sans que le pidfile porte ce process — un daemon lancé autrement, par npm run dev — elle refuse de tuer à l’aveugle et te dit de l’arrêter là où tu l’as lancé.

atlas status affiche ● en marche avec l’adresse et, quand elle le connaît, le pid, suivi de la version en JSON ; sans daemon, ○ arrêté — la question est binaire. atlas version répond selon ce qu’elle a pu voir : le daemon s’il répond, sinon le fichier écrit par le paquet installé, sinon {"version":"?"}. Elle ne dit jamais si cette version est la dernière — c’est Config › Atlas qui juge, en trois états (Configurer un projet). atlas logs affiche les 20 dernières lignes puis suit le fichier en direct ; sans journal, elle le dit et s’arrête.

Pidfile et journal sont indexés par port dans le dossier d’état d’Atlas (~/.local/state/atlas/, ou $XDG_STATE_HOME/atlas) : deux instances sur deux ports coexistent sans se marcher dessus. Ces commandes pilotent le daemon lui-même, quel que soit le dossier où tu te trouves ; c’est atlas (sans argument) qui, lui, bascule le projet actif.

Se mettre à jour

atlas update                        # installe la dernière version PUBLIÉE, redémarre, rafraîchit le plugin
atlas promote                       # (contributeurs d'Atlas) reconstruit TON code, l'installe, redémarre
atlas promote --from ~/dev/atlas    # depuis un dossier qui n'est pas ton clone courant

Même fin pour les deux (redémarrage, plugin rafraîchi, version affichée), mais pas la même personne :

atlas update atlas promote
pour qui tout le monde, de n’importe où un contributeur, dans un clone du dépôt Atlas
installe quoi la dernière version publiée au registre npm ton code local, empaqueté puis installé
en échec dit qu’il manque le registre et le jeton, avec les deux lignes npm config set dit qu’aucun clone n’est trouvable en remontant depuis le dossier courant ; --from CHEMIN en donne un

atlas promote n’apparaît dans atlas help que si un tel clone existe à portée — elle reste tapable sinon.

⚠️ Depuis un clone du dépôt Atlas, atlas update fait ce qu’elle dit, pas ce qu’on croit vouloir : elle prévient (« ceci installe la dernière version PUBLIÉE, pas ton code ») puis installe quand même la version publiée — qui peut être en dessous du code que tu viens d’écrire. C’est atlas promote qu’il faut taper pour tester son propre code.

Les deux écrivent : un paquet npm installé en global (hors d’Atlas et hors de ton projet), le daemon redémarré par ce binaire-là, et le plugin rafraîchi — seulement s’il est déjà installé.

Brancher ton IA

atlas plugin            # affiche les deux commandes à lancer, sans les exécuter
atlas plugin install    # les exécute : branche les skills Atlas sur ta session de code

Sans argument, atlas plugin imprime les deux commandes Claude Code à taper (elles marchent aussi en /plugin … dans une session déjà ouverte) — elle n’exécute rien. install les exécute : elle écrit dans ta configuration Claude Code globale, jamais dans ce projet ni dans un repo. Si le plugin est déjà posé, elle le réinstalle entièrement au lieu de répondre « déjà installé » — le numéro de version ne prouve pas qu’il n’y a rien de neuf. Ce qu’il permet est dans Brancher l’IA et Ce que l’IA lit et écrit.

Les commandes qui servent l’IA

Trois commandes ne se tapent pas de mémoire tous les jours : elles sont la surface par laquelle une IA (ou un skill que tu écris toi-même) parle à Atlas.

atlas mcp                 # le serveur MCP — lancé par ton client IA, pas à la main
atlas brief PROJ-412      # la carte d'une feature, en une page de texte
atlas claude --dry-run    # (contributeurs d'Atlas) la session isolée, sans la lancer

atlas mcp démarre le serveur MCP sur l’entrée/sortie standard. Elle résout le projet actif depuis le dossier où la session a été ouverte, avec une garde stricte : si le daemon sert déjà un autre projet que celui de cette session, elle refuse de répondre plutôt que de rendre une carte plausible et fausse. Elle n’écrit rien elle-même — ce que les outils qu’elle expose peuvent écrire est dans Ce que l’IA lit et écrit.

atlas brief <TICKET> imprime, sur la sortie standard, la carte d’une feature réduite à du texte — de quoi la coller dans une revue, ou la donner à lire à un agent qui n’ouvre pas Atlas. --base <branche> force la branche de comparaison pour cet appel. Elle démarre le daemon si besoin (en silence, sur l’erreur standard, pour ne pas polluer le texte produit) et active le projet du dossier courant. Elle laisse jusqu’à 5 minutes avant d’abandonner : une réponse lente sur une grosse feature multi-repos n’est pas une panne.

atlas claude [--dry-run] [ARGS…] ouvre une session Claude Code isolée aux skills d’Atlas — ni les skills, ni le CLAUDE.md du projet que tu fais relire. Elle ne sert qu’à faire relire Atlas par lui-même ; sur ton projet, c’est atlas plugin install qui te concerne. Elle échoue sans .atlas-workspace/ trouvable, ou sans binaire claude dans le PATH.

L’index des précédents

Un précédent est le souvenir de ce qu’une review a déjà dit sur un nœud du même genre — une méthode, un contrat — dans une autre feature. Atlas les sert nœud par nœud, à condition qu’un index existe ; il ne se construit jamais tout seul.

atlas precedents --build                      # construit ou rafraîchit l'index du projet
atlas precedents --build --full               # sans repartir de l'index déjà là
atlas precedents --build --out ~/essai.json   # un index candidat ; le projet intact
atlas precedents --controle                   # le contrôle humain : des paires, tu réponds
atlas precedents PROJ-412 [--json]            # les précédents des nœuds de cette feature

Ce que mesure chaque chiffre rendu ici est dans Ce que l’IA lit et écrit ; ici, ce que tu tapes, ce que tu vois et ce qui est refusé. Sans argument reconnu, la commande imprime ses trois usages et sort en erreur.

Construire — --build

Elle rejoue les cartes des features qui portent un fil — une conversation ancrée sur un nœud —, puis écrit .atlas-workspace/precedents.json : un fichier partagé, comme le reste de la configuration projet. C’est une passe de plusieurs minutes et la commande attend, jusqu’à une heure avant d’abandonner. Si elle abandonne, elle nomme la cause et ajoute que le serveur a pu finir sans elle : regarde atlas logs, ou la chronologie dans Config › Projet — ne la relance pas d’office, l’index est peut-être déjà écrit.

--full refait tout sans réutiliser l’index d’avant — après un changement de règle, pas au quotidien. --out <fichier> écrit un index candidat ailleurs et laisse celui du projet intact : de quoi mesurer sans rien remplacer. Un candidat n’est jamais servi ; mis à la place de l’autre, il est refusé à la lecture, et ça se dit. Les refus tombent avant le build, pas après dix minutes : --out sans chemin derrière (« --out attend un chemin de fichier »), --out pointé sur l’index du projet (« exactement ce que –out sert à ne pas toucher »), --out dans un dossier qui n’existe pas, --out sans --build — lire l’index n’en écrit aucun.

Tu vois d’abord cinq lignes de comptes — précédents :, indexés par origine : (plus les features rejouées, les fils écartés faute de suite, et écrit dans dès que --out est là), suivis d'un changement dans leur fenêtre :, réponse humaine :, récidive par verdict (≥ 2 features) : —, puis une ligne ⚠ … non rejouée : … par feature non rejouée, avec sa raison.

Vient ensuite la chronologie : ▸ chronologie — ce que dit ce build :, la lecture de la ligne ajoutée — une phrase d’accroche, puis une ligne par mesure (la question, le chiffre avec sa fraction, la direction entre crochets et l’écart avec la ligne d’avant) et son explication en dessous —, puis le détail — la ligne de ce build, telle quelle : et …et la précédente :. Sans ligne d’avant, elle le dit ; si la mesure n’a pas pu être faite, une seule ligne, ▸ chronologie : suivie de la raison — l’index, lui, est bien écrit. Une ligne brute tient en une douzaine de sous-lignes : la date et la durée, précédents :, features :, cibles :, population :, rappel —, fuites :, servis par feature :, tokens :, effet :, contrôle humain :, manqués : (suivie de cinq exemples au plus), cibles perdues depuis le build précédent :, coupe temporelle :. La même ligne se relit dans Config › Projet, chapitre Chronologie.

Contrôler — --controle

Servir un précédent suppose une définition de « voisin » qu’Atlas a écrite tout seul. --controle est le geste par lequel un humain la conteste : jusqu’à 30 paires tirées, présentées une à une, et tu dis si la cible aurait dû être servie. Les sondes d’abord — les paires qu’un skill avait écartées, au plus la moitié du tirage —, puis le reste au sort, sur une graine dérivée de l’index : même index et mêmes sondes rendent le même tirage, donc un contrôle se rejoue.

Chaque paire tient en quelques lignes : question : (le nœud, et sa feature), type :, cible : (la clé du fil passé, suivie de [une SONDE : un skill l'avait écartée] quand c’en est une), l’attaque du fil entre guillemets, puis réponse humaine : et réplique de l'IA : s’il y en a eu. Ce qu’Atlas en pense n’est jamais montré : la question deviendrait une confirmation. Tu réponds o (ou oui), n (ou non), ? ou Entrée pour « je ne sais pas » ; toute autre frappe fait reposer la question, et Ctrl-C abandonne sans rien écrire.

Quatre conditions, dites avant de te faire répondre trente fois. Il faut un vrai terminal : dans un tube ou un script, la commande refuse, et rien n’a même été démarré. Il faut un index, et qu’il porte des cibles. Il ne doit pas déjà exister un contrôle daté d’aujourd’hui — Atlas ne remplace pas une décision : il nomme le fichier et te laisse le retirer. Et --controle est un geste à lui seul : y ajouter --build, --full, --out ou un ticket fait échouer la commande.

À la fin, le contrôle s’écrit dans .atlas-workspace/controles/<date>.json — un fichier à toi, daté, signé de l’adresse qui signe tes commits quand git la connaît, et qui se supprime à la main. La commande affiche le chemin, puis l’accord entre Atlas et toi sur deux populations séparées : celle du sort, la seule qui juge la définition, et celle des sondes. Si l’écriture échoue, elle dit combien de réponses sont perdues. Rien ne change dans l’index à ce moment-là : le contrôle ne corrige aucune règle, il pose un chiffre que le prochain atlas precedents --build portera sur sa ligne.

Lire — atlas precedents <TICKET>

Sans --build, la commande lit l’index et sert, pour chaque nœud de cette feature, le précédent le plus proche du même type. Elle n’écrit rien. Une ligne d’en-tête (combien de précédents servis, sur combien de nœuds, la date de l’index), puis par nœud : la référence, l’attaque du fil entre guillemets avec sa clé et qui l’a ouvert — ouvert par l'humain ou ouvert par l'IA —, puis ses faits sur une ligne, détaillés un à un dans Ce que l’IA lit et écrit. Quand l’index ne donne rien, elle ne tranche pas : « aucun — aucun fil passé sur un nœud de ce type ; ou l’index est à rafraîchir ». --json rend la réponse brute.

Variables d’environnement et options globales

Trois seulement changent ce que fait une commande de cette page ; la liste complète (jetons GitLab/GitHub, trace de debug…) est dans Configurer un projet.

Variable Effet Défaut
ATLAS_PORT ou PORT le port du daemon — start, stop, status, logs s’appliquent à ce port 3030
ATLAS_WORKSPACE force un workspace au tout premier démarrage du daemon seulement — ensuite le registre décide la remontée depuis le dossier courant
ATLAS_CLAUDE_BIN le binaire lancé par atlas claude et par atlas plugin claude

Aucune option globale (--verbose, --json…) ne s’applique à toutes les commandes : chaque commande a les siennes, listées ci-dessus.

Ce qu’Atlas ne fait pas

  • Rien ne se met à jour tout seul : atlas update est toujours un geste que tu tapes, et elle ne vérifie pas si tu es en retard — elle installe ce que le registre appelle « la dernière version ». C’est Config › Atlas qui juge, en trois états (Configurer un projet).
  • atlas init ne fait pas git init, ne crée aucune branche, et n’installe pas le plugin IA.
  • Aucune commande de cette page ne touche un repo analysé : ni son contenu, ni ses branches, ni un dépôt distant. La seule écriture qui sorte d’Atlas est celle des skills une fois branchés (Ce que l’IA lit et écrit).
  • atlas mcp ne se tape pas à la main : c’est un serveur de protocole, lancé par ton client IA.
  • Un daemon ne sert jamais deux projets à la fois : toute commande qui parle d’une feature bascule le projet actif plutôt que de répondre sur le mauvais.
  • L’index des précédents ne se rafraîchit jamais tout seul, et aucun contrôle ne le corrige : le contrôle n’écrit que son propre fichier.
  • Aucune commande n’imprime un mode d’emploi d’Atlas à coller dans un skill maison : brancher ton propre skill sur Atlas est un geste que tu écris.

Limites connues

atlas update et atlas promote ne sont éprouvées que sous Linux : la façon dont elles retrouvent le binaire fraîchement installé ne tient pas encore sous Windows (détail dans Prise en main). atlas plugin et atlas claude supposent un binaire claude dans le PATH — sans lui, elles le disent et s’arrêtent, elles ne l’installent pas. atlas precedents --controle n’a pas encore été joué sur un vrai projet : ses gardes ont été éprouvées sur un workspace jetable, pas ses trente questions.
