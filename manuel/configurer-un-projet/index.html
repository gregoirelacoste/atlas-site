Configurer un projet

Tout ce qu'Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s'édite depuis l'écran.

Tout ce qu’Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s’édite depuis l’écran.

Atlas est générique : le moteur ne connaît aucun framework. Ce qui rend juste la carte d’une feature — le chemin que prend un ticket à travers tes repos — vient de ce dossier : quelle couche pour quel fichier (controller, service, repo…), quel décorateur ouvre un point d’entrée, quels fichiers sont des contrats (une surface publique dont d’autres dépendent), et jusqu’à ce qui fait qu’une branche est une feature. L’étalon : atlas init sur un projet neuf doit produire une carte utilisable sans qu’une ligne soit éditée. Ce qui suit sert quand ce n’est pas le cas.

Les règles de reconnaissance elles-mêmes — les stacks livrées, les couches, les familles, les entrées, et la liste complète des clés de project.json — sont sur la page suivante, Les stacks et project.json. L’installation et atlas init sont dans Prise en main ; le plugin IA et le serveur MCP dans Brancher l’IA ; ce que les familles changent aux chiffres dans Fichiers et Inventaire.

Où vit la configuration

Atlas travaille sur un chapeau : le dossier parent qui héberge tes N repos. La config vit dans un .atlas-workspace/ posé à sa racine, et elle est découverte par remontée depuis le dossier courant — comme git trouve son .git/. Lancer atlas depuis n’importe quel sous-dossier d’un repo membre trouve donc le bon workspace. La racine est dérivée (le parent du .atlas-workspace/) : elle ne se règle pas.

À côté, le registre des projets vit sur ta machine, hors de tout projet (Prise en main). Au démarrage, le dernier projet actif l’emporte sur la découverte par le dossier courant, tant qu’il pointe sur un vrai workspace.

Rien n’est mis en cache : la config est relue à chaque appel. Édite project.json, recharge la carte, c’est pris en compte.

Ce qui se partage, ce qui reste à toi

Le workspace contient deux natures, et le critère est le versionnement :

  • la conf projet — vraie pour quiconque ouvre ce projet : elle se commite, et remplace le « envoie-moi ton project.json ». Chez le suivant : git clone <url> .atlas-workspace au lieu d’atlas init ;
  • la conf locale — ce qui n’appartient qu’à toi : jamais commitée.

atlas init pose un .gitignore dans .atlas-workspace/, mais ne fait pas git init : où et comment l’équipe versionne reste sa décision. Quand tu demandes à Atlas de faire un dépôt du workspace (page Config › Projet, « 🤝 Workspace partagé »), il complète ce .gitignore — jamais il ne le réécrit — avec les deux règles qui comptent : features/*/curation/local/ (ce que tu as lu) et features/*/curation.json (l’ancien fichier mono-utilisateur), revérifiées à chaque « ⇧ Partager ». Si tu versionnes à la main, vérifie que la première y est : sans elle, git add -A publierait ta lecture des fils.

L’arborescence

mon-chapeau/
├─ .atlas-workspace/
│  ├─ project.json  stack/<id>.json  precedents.json  ESPACES.md  .gitignore
│  └─ features/PROJ-412/
│     ├─ ticket.md  feature.json  overlay.json  parcours.json  plan.json  comments.json
│     └─ curation/
│        ├─ moi@exemple.com.json        # ce que j'ai relu et validé — partagé
│        └─ local/moi@exemple.com.json  # ce que j'ai lu — jamais partagé
├─ projet-api/                  # repo membre (auto-découvert : il a un .git)
└─ app-front/                   # repo membre

Un espace, un fichier, un propriétaire — c’est ce qui rend le dossier relisible : un diff dit qui a parlé.

fichier à qui quoi commité ?
project.json toi les règles du projet (six réglages s’éditent aussi depuis l’écran) oui
stack/<id>.json toi ce que tu ajoutes à une stack livrée oui
precedents.json Atlas l’index construit par atlas precedents --build oui
features/<ID>/ticket.md toi la spec : objectif, critères, « ne fait pas » oui
features/<ID>/feature.json toi ou l’IA la déclaration : titre, repos membres, branches choisies, une ligne de base d’exception oui
overlay.json · parcours.json · plan.json l’IA ce qu’elle a compris, les étapes, le pseudo-code oui
comments.json les deux la conversation — le rôle de chaque message départage oui
curation/<qui>.json toi tes endossements (ce que tu as relu et validé), tes notes de criticité, tes « pas compris » oui — c’est ce que l’équipe voit
curation/local/<qui>.json toi ce que tu as lu dans les fils, la branche que tu lis non, jamais

Le nom de fichier de ta curation est un slug de ton adresse git (git config user.email) : l’identité se lit dans git, elle ne se déclare pas dans Atlas. Sans identité configurée, Atlas retombe sur un curation.json mono-utilisateur, ignoré par git lui aussi. Et la carte n’est jamais stockée : ce dossier ne contient que ce qui se déclare.

Les repos membres

L’appartenance est auto-découverte : tout sous-dossier du chapeau qui contient un .git est un repo membre. Les dossiers cachés sont ignorés, et la liste est triée pour que l’ordre des bandeaux soit stable. Ajouter un repo au chapeau suffit : aucune liste blanche à tenir.

Deux clés seulement s’en mêlent :

  • exclude — les repos à retirer de la découverte. C’est pour un clone parasite : un repo perso posé là, sans rapport avec le projet. Atlas ne supprime rien sur le disque, il cesse de le lire ;
  • repos[] — des overrides par repo, jamais une liste d’appartenance. Une entrée porte le name du dossier plus, au choix, branch, routePrefix, productionBase.

branch est un motif de branche attendue avec {id} — par exemple feat/{id}, qui reconnaîtra feat/PROJ-412 et rien d’autre dans ce repo. Sans motif, c’est la règle générale de la section suivante qui s’applique.

routePrefix est le préfixe sous lequel les routes de ce repo sont réellement servies (/back-office). Il est déclaré, jamais déduit : un ingress ou un proxy peut le réécrire devant le service, donc le lire dans le code n’en ferait qu’une hypothèse. Sans lui, l’étiquette d’une entrée HTTP reste relative — ▶ GET …/orders/history dans la tête du Code, où le …/ dit « le montage n’est pas lu » — et Atlas pose un angle mort, c’est-à-dire un endroit où le moteur dit qu’il ne sait pas au lieu de deviner. Déclaré, le …/ disparaît : l’URL est exacte.

productionBase est la branche qui porte la production de ce repo, en trois états : un nom, null (« pas d’étape de déploiement ici » — un master abandonné), l’absence (« applique le défaut » : master ou main s’ils existent ici et diffèrent de la ligne d’intégration). C’est ce qui range une feature en « 🚀 À déployer » ou « ✅ Terminé » dans le Tableau.

Ce qui fait une feature

Atlas doit répondre à une question que le code ne porte pas : ce nom de branche désigne-t-il une feature, et laquelle ? C’est une convention d’équipe — elle se déclare, comme le préfixe de route. Une clé, featureId, deux valeurs :

featureId ce qui devient une feature comment elle est nommée
"ticket" — le défaut quand la clé est absente seules les branches dont le nom porte un jeton de la forme PROJ-412 par ce jeton, en majuscules
"branch" toute branche qui n’est pas une ligne par son dernier segment ; un jeton de ticket, s’il y en a un, prime

Le réglage est à l’écran — ⚙️ Config › Projet › ✎ Ce qu’Atlas ne peut pas deviner › « Ce qui fait une feature » —, un déroulant à deux entrées. atlas init détecte et écrit la décision en clair, même quand c’est le défaut : il lit toutes les branches des repos membres, locales et distantes, et pose "ticket" dès qu’au moins une porte un jeton, "branch" si aucune n’en porte. Il ne l’écrit qu’en créant le workspace : sur un .atlas-workspace/ déjà là, il n’écrit rien. Un workspace créé avant ce réglage n’a pas la clé : il est donc en ticket, comme avant.

Mode ticket. Un jeton, c’est au moins deux majuscules, un tiret, des chiffres, et il est borné des deux côtés : feat/PROJ-412_api porte PROJ-412, PROJ-4120 n’est pas PROJ-412. Le reste n’est pas une feature : ces branches n’ont pas de carte dans le Tableau, qui les compte sous ses colonnes (« ⊘ 2 branches sans ticket ignorées par réglage ») — un clic sur cette ligne ouvre ce réglage. Y coller un nom de branche sans jeton est refusé avec sa sortie : Atlas rappelle qu’ici une feature est un jeton, et renvoie vers le réglage qui fait lire toute branche.

Mode branch. Le dernier segment nomme : feat/login-bug et alice/login-bug portent tous deux login-bug, le origin/ est retiré d’abord. Le nom est mis en forme — minuscules, les accents gardent leur lettre (Écran → ecran), le reste devient un tiret. Et il se lit en segment entier, plus strict qu’un ticket : login-bug est porté par feat/login-bug, pas par feat/login-bug-v2. Sans cette borne, une feature au nom court lirait la carte de sa voisine.

⚠️ Passer en branch remplit le Tableau : chaque branche sortie localement ou présente sur origin y devient une carte. Ce n’est pas du bruit à exclure — c’est la dormance à 60 jours qui replie les vieilles (le Tableau).

Jamais une feature, dans les deux modes : les lignes — develop, master, main, la ligne de base, et chaque ligne de production déclarée par repo. Un id qui attraperait l’une d’elles est refusé, y compris wip/develop. Le refus reprend la saisie, puis le dit : nomme une ligne d’intégration : toutes les branches la portent, elle ne peut pas être une feature.

Déclarer : taper, ou coller. Le champ du bouton ＋ du Tableau accepte les deux. Un id tapé passe à sa forme canonique : un ticket en majuscules (proj-412 → PROJ-412), le reste en slug (Login Bug → login-bug). Un nom de branche collé — dès qu’il contient un / — est lu par le même juge que la découverte : feat/login-bug déclare login-bug. Jamais feat-login-bug, une feature qu’aucune branche ne porterait, juste à côté de la vraie.

La ligne de base

C’est d’où part le diff de chaque feature : la branche d’intégration où ton travail finit par rentrer. Son nom est une convention d’équipe — develop chez les uns, master ou main chez les autres, et c’est le défaut de GitHub. Une clé, base, dans project.json.

Quatre niveaux, du plus précis au plus général : la feature (feature.json), le projet (project.json), la variable BASE, puis develop en dernier recours. La feature ne déclare que l’exception : la base du projet n’y est jamais recopiée, sinon un changement ultérieur du projet n’atteindrait plus aucune feature déjà réglée.

atlas init la détecte et l’écrit : par repo, la branche que désigne origin/HEAD si ce n’est pas une feature, sinon la première présente parmi develop, master, main. Si les repos ne sont pas d’accord, rien n’est écrit et la commande le dit — en choisir une ferait partir la moitié des cartes d’une fourche inventée. Sous le champ, la même détection : ce que git montre repo par repo, le verdict (✓ détecté, ⚠ bases hétérogènes, ou aucune ligne), et ce qui est en vigueur. On écrit un nom de branche nu : origin/ est refusé.

Un repo où la base cherchée n’existe pas sort de la carte, et Atlas le dit — il n’en invente jamais une autre. Le panneau Git porte alors une chip <repo> · base <nom> absente, et la carte un angle mort base absente (Quand Atlas ne voit pas). Sans ce refus, Atlas prenait la feature elle-même pour sa base : diff vide, et « mergé » prouvé tout seul.

La page Config

Le bouton ⚙️ Config du header ouvre une page qui remplace la carte — Échap revient. Trois vues, et la dernière ouverte est mémorisée sur cette machine.

vue ce qu’on y fait
Feature par repo : la branche feature (sur quoi on bosse) et la branche de comparaison, plus la comparaison globale. Quand plusieurs branches portent le ticket, elles sont groupées en tête du déroulant. Enregistré dans features/<ID>/feature.json
Projet les projets connus du registre (activer, ajouter, retirer), l’état du workspace partagé et la case « Partager mon travail automatiquement », le résumé de la config du projet actif, et les six réglages éditables
Atlas le thème, la version en trois états (à jour · une version existe · je n’ai pas pu regarder, avec sa raison), comment brancher ton IA, et l’état de l’hébergeur par hôte (jeton trouvé ou non, et d’où il vient)

Les chapitres se plient

Chaque chapitre de la page se plie, et tout arrive replié. Deux exceptions, parce qu’on vient les voir et pas les régler : « 🤝 Workspace partagé » dans la vue Projet, et « Par repo » dans la vue Feature. Ce que tu plies ou déplies est retenu sur cette machine, et un titre porte à droite ce que son repli cacherait quand c’est un fait : le nombre de couches, de repos exclus — ou, sur « Version », un ⬆ v… disponible s’il y a du retard. Le drapeau du workspace, dans le header, ouvre la vue Projet en redépliant son chapitre même si tu l’avais refermé.

Le thème

⚙️ Config › Atlas › « Thème » — trois boutons :

choix ce qu’il fait
Système suit la préférence claire/sombre de ton OS. C’est le défaut, et c’est un choix comme les autres : on peut y revenir
Clair force le clair, même si l’OS est en sombre
Sombre force le sombre, même si l’OS est en clair

Sous les boutons, Atlas dit ce que « Système » donne ici et maintenant (« en ce moment : Sombre »), parce que la préférence de l’OS n’est pas lisible depuis l’écran. Le choix vit dans ce navigateur, sur cette machine — il ne part ni dans project.json, ni chez tes collègues — et il est appliqué avant le premier rendu : pas de flash de page claire au chargement. Le thème a quitté le header : il n’y a plus rien à y chercher.

Les six réglages qu’Atlas ne peut pas deviner

La vue Projet affiche en lecture seule tes couches, tes types de fichiers, tes rangés d’office, tes repos front, les repos membres et les exclus. Le chapitre « Repos front » se lit encore, mais l’écran dit lui-même qu’il ne fait plus rien : « Sans effet […] : un fichier est front par ce qu’il porte […], plus par le nom de son repo. » Un réglage qui ne fait rien se dit plutôt que de disparaître en silence — et le jour où quelque chose sera vraiment une propriété de repo, la clé est là pour la porter (Les stacks et project.json).

Sous ce résumé, une section « ✎ Ce qu’Atlas ne peut pas deviner » : six réglages s’écrivent depuis l’écran, et six raisons différentes de ne pas les déduire.

réglage pourquoi il faut un humain
les familles maison le moteur sait compter un suffixe, pas le nommer. Les motifs non classés qui ont la forme d’un rôle sont proposés : un clic les déclare
ce qui fait une feature la convention que l’équipe écrit dans ses branches ne se lit nulle part dans le code
la ligne de base le nom de la ligne d’intégration est une convention d’équipe, pas un fait du code. Vide = rien de déclaré : Atlas cherche la ligne repo par repo
les repos exclus un clone parasite ne se distingue pas d’un membre par le code
le préfixe de route par repo un ingress peut le réécrire. Vide = route relative
la ligne de production par repo master existe partout ; qu’il soit vivant ne se lit ni dans son nom ni dans sa topologie. Vide = auto, — (ou aucune) = pas d’étape de déploiement ici

Les six sont des chapitres pliables, et le bouton Enregistrer est ancré au pied de la section : il les commande tous les six, quel que soit celui que tu as ouvert. L’écriture est une liste blanche stricte — Atlas relit le fichier du disque, remplace ces clés-là, réécrit : tout ce que tu as édité à la main à côté est préservé. Le reste — couches, types de fichiers, stacks — s’édite dans project.json, clé par clé (Les stacks et project.json). Le message dit alors ✓ enregistré dans project.json, et la carte est rechargée : c’est elle qui prouve que le réglage a pris.

Les variables d’environnement

Elles disent à Atlas où regarder — quel workspace, quel port, quelle ligne de base, quel jeton. Une seule ne produit rien : ATLAS_M2M_DEBUG, qui n’ajoute qu’une trace.

variable ce qu’elle fait défaut
ATLAS_WORKSPACE chemin explicite vers un workspace, lu au démarrage du daemon — et seulement si le registre n’a pas déjà un projet actif valide la remontée depuis le dossier courant
ATLAS_PORT ou PORT le port du daemon (le pidfile et le log sont indexés par port) 3030
BASE la ligne de base, quand ni la feature ni le projet ne la déclarent develop
XDG_CONFIG_HOME où vit le registre des projets ~/.config
XDG_STATE_HOME où vivent le pidfile et les logs ~/.local/state
ATLAS_GITLAB_TOKEN (ou GITLAB_TOKEN, GLAB_TOKEN) · ATLAS_GITLAB_HOST un jeton GitLab explicite, et l’hôte qui le scope le jeton lu dans la config de glab
ATLAS_GITHUB_TOKEN (ou GH_TOKEN, GITHUB_TOKEN) · ATLAS_GITHUB_HOST les mêmes, côté GitHub la config de gh
ATLAS_CLAUDE_BIN le binaire lancé par atlas claude claude
ATLAS_M2M_DEBUG trace l’appariement des appels réseau sur la sortie d’erreur — une trace, rien d’autre éteint

Les quatre variables d’hébergeur ont leur page : GitLab et GitHub.

⚠️ ATLAS_WORKSPACE ne sert pas à changer de projet : le dernier projet actif du registre l’emporte sur elle. Pour changer de projet, la page Config › Projet, ou atlas lancé depuis le nouveau chapeau.

Raccourcis

touche effet
Échap ferme la page Config et revient à la carte
Espace p c ouvre Config, et la referme — un seul geste dans les deux sens, comme le bouton ⚙️ Config
Espace p t traverse Config vers le Tableau, en la refermant au passage

Aucun raccourci ne part d’un champ ou d’un déroulant : Espace y est avalé par le champ, et Config en est pleine. La table entière est dans Le clavier.

Ce qu’Atlas ne fait pas

  • Il ne devine ni un préfixe de route, ni une ligne de production, ni une famille maison : ces trois-là se déclarent, et une déclaration absente se dit à l’écran plutôt que de se combler. Ce qui fait une feature et la ligne de base sont, eux, détectés une fois par atlas init — puis écrits comme des décisions, modifiables.
  • Il ne supprime rien sur le disque : exclure un repo le retire de la carte, pas du chapeau.
  • Il n’écrit jamais ta curation ni ta spec, et l’IA non plus : elle n’a aucun outil pour atteindre curation/, project.json ou le code source des repos (Brancher l’IA).
  • Il ne fait pas de dépôt du workspace sans qu’on le lui demande : atlas init pose le .gitignore, jamais le git init. Une fois le dépôt ouvert, deux gestes partent seuls — un pull --ff-only quand tu as du retard, et un commit + push si tu as coché « Partager mon travail automatiquement », au plus une fois par heure.

Limites connues

  • L’identité est lue à la racine du chapeau, qui n’est pas un dépôt : git remonte donc à ta config globale. Un user.email posé par repo n’est pas vu.
  • GitLab et GitHub valent la même chose — la Revue, la publication, le droit d’écrire, la colonne « en review ». Ce qui reste inégal, et ce qui n’a jamais été éprouvé, est dit dans GitLab et GitHub.
