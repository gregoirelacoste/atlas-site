Configurer un projet

Tout ce qu'Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s'édite depuis l'écran.

Tout ce qu’Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s’édite depuis l’écran.

Atlas est générique : le moteur ne connaît aucun framework. Ce qui rend juste la carte d’une feature — le chemin que prend un ticket à travers tes repos — vient de ce dossier : quelle couche pour quel fichier, quels fichiers sont des contrats (une surface publique dont d’autres dépendent), et jusqu’à ce qui fait qu’une branche est une feature. L’étalon : atlas init sur un projet neuf doit produire une carte utilisable sans qu’une ligne soit éditée. Ce qui suit sert quand ce n’est pas le cas.

Les règles de reconnaissance — stacks livrées, couches, familles, entrées, et la liste complète des clés de project.json — sont sur la page suivante, Les stacks et project.json. L’installation et atlas init : Prise en main ; le plugin IA : Brancher l’IA.

Où vit la configuration

Atlas travaille sur un chapeau : le dossier parent qui héberge tes N repos. La config vit dans un .atlas-workspace/ posé à sa racine, découverte par remontée depuis le dossier courant — comme git trouve son .git/. Lancer atlas depuis n’importe quel sous-dossier trouve donc le bon workspace. La racine est dérivée (le parent du .atlas-workspace/) : elle ne se règle pas.

À côté, le registre des projets vit sur ta machine, hors de tout projet (Prise en main). Au démarrage, le dernier projet actif l’emporte sur la découverte, tant qu’il pointe sur un vrai workspace.

Rien n’est mis en cache : la config est relue à chaque appel — édite project.json, recharge la carte, c’est pris.

Ce qui se partage, ce qui reste à toi

Le workspace contient deux natures, et le critère est le versionnement :

  • la conf projet — vraie pour quiconque ouvre ce projet : elle se commite. Chez le suivant : git clone <url> .atlas-workspace au lieu d’atlas init ;
  • la conf locale — ce qui n’appartient qu’à toi : jamais commitée.

atlas init pose un .gitignore dans .atlas-workspace/, mais ne fait pas git init : versionner reste la décision de l’équipe. Quand tu demandes à Atlas de faire un dépôt du workspace (page Config › Projet, « 🤝 Workspace partagé »), il complète ce .gitignore — jamais il ne le réécrit — avec les deux règles qui comptent : features/*/curation/local/ (ce que tu as lu) et features/*/curation.json (l’ancien fichier mono-utilisateur), revérifiées à chaque « ⇧ Partager ». Si tu versionnes à la main, vérifie que la première y est : sans elle, git add -A publierait ta lecture des fils. Tout le reste part, controles/ compris.

L’arborescence

mon-chapeau/
├─ .atlas-workspace/
│  ├─ project.json  stack/<id>.json  precedents.json  ESPACES.md  .gitignore
│  ├─ controles/2026-01-20.json   # un contrôle humain, daté
│  └─ features/PROJ-412/
│     ├─ ticket.md  feature.json  overlay.json  parcours.json  plan.json  comments.json
│     └─ curation/
│        ├─ moi@exemple.com.json        # ce que j'ai relu et validé — partagé
│        └─ local/moi@exemple.com.json  # ce que j'ai lu — jamais partagé
├─ projet-api/                  # repo membre (auto-découvert : il a un .git)
└─ app-front/                   # repo membre

Un espace, un fichier, un propriétaire : c’est ce qui rend le dossier relisible — un diff dit qui a parlé.

fichier à qui quoi commité ?
project.json toi les règles du projet — six s’éditent depuis l’écran oui
stack/<id>.json toi ce que tu ajoutes à une stack livrée oui
precedents.json Atlas l’index des reviews passées (atlas precedents --build) : les fils ouverts par l’IA et les tiens, plus la chronologie oui
controles/<date>.json toi tes réponses à un contrôle : un par jour, signé de ton adresse git, jamais réécrit oui
features/<ID>/ticket.md toi la spec : objectif, critères, « ne fait pas » oui
features/<ID>/feature.json toi ou l’IA la déclaration : titre, repos membres, branches choisies, la base d’exception oui
overlay.json · parcours.json · plan.json l’IA ce qu’elle a compris, les étapes, le pseudo-code oui
comments.json les deux la conversation — le rôle de chaque message départage oui
curation/<qui>.json toi tes endossements (relu et validé), tes notes de criticité, tes « pas compris » oui — c’est ce que l’équipe voit
curation/local/<qui>.json toi ce que tu as lu dans les fils, la branche que tu lis non, jamais

Le nom de fichier de ta curation est un slug de ton adresse git (git config user.email) : l’identité se lit dans git, elle ne se déclare pas dans Atlas. Sans identité, Atlas retombe sur un curation.json mono-utilisateur, ignoré par git lui aussi. La carte, elle, n’est jamais stockée : ce dossier ne contient que ce qui se déclare.

controles/ n’apparaît qu’après un premier atlas precedents --controle (La ligne de commande) : Atlas te soumet jusqu’à trente paires — un nœud, et un précédent qu’il aurait pu lui servir —, tu dis pour chacune si le rapprochement tenait (oui · non · pas-su), et il écrit tes réponses. Il n’y écrase rien : deux contrôles le même jour, le second refuse en le nommant.

Les repos membres

L’appartenance est auto-découverte : tout sous-dossier du chapeau qui contient un .git est un repo membre, les dossiers cachés exceptés. Ajouter un repo au chapeau suffit : aucune liste blanche à tenir.

Deux clés seulement s’en mêlent :

  • exclude — les repos à retirer de la découverte, pour un clone parasite posé là sans rapport avec le projet. Atlas ne supprime rien sur le disque, il cesse de le lire ;
  • repos[] — des overrides par repo, jamais une liste d’appartenance. Une entrée porte le name du dossier plus, au choix, branch, routePrefix, productionBase.

branch est un motif avec {id} : feat/{id} reconnaîtra feat/PROJ-412 et rien d’autre ici. Sans motif, la règle générale de la section suivante s’applique.

routePrefix est le préfixe sous lequel les routes de ce repo sont réellement servies (/back-office) — déclaré, jamais déduit, parce qu’un ingress peut le réécrire. Sans lui, l’étiquette d’une entrée HTTP reste relative (▶ GET …/orders/history, où le …/ dit « le montage n’est pas lu ») et Atlas pose un angle mort, un endroit où le moteur dit qu’il ne sait pas au lieu de deviner. Déclaré, l’URL est exacte.

productionBase est la branche qui porte la production de ce repo : null y déclare qu’il n’y a pas d’étape de déploiement ici, l’absence applique le défaut (master ou main, s’il existe ici et diffère de la ligne d’intégration). C’est ce qui range une feature en « 🚀 À déployer » ou « ✅ Terminé » dans le Tableau.

Ce qui fait une feature

Atlas doit répondre à une question que le code ne porte pas : ce nom de branche désigne-t-il une feature, et laquelle ? C’est une convention d’équipe, et elle se déclare. Une clé, featureId, deux valeurs :

featureId ce qui devient une feature comment elle est nommée
"ticket" — le défaut quand la clé est absente seules les branches dont le nom porte un jeton de la forme PROJ-412 par ce jeton, en majuscules
"branch" toute branche qui n’est pas une ligne par son dernier segment ; un jeton de ticket, s’il y en a un, prime

Le réglage est à l’écran — ⚙️ Config › Projet › ✎ Ce qu’Atlas ne peut pas deviner › « Ce qui fait une feature », un déroulant à deux entrées. atlas init détecte et écrit la décision en clair, même quand c’est le défaut : il lit les branches des repos membres, locales et distantes, et pose "ticket" dès qu’une porte un jeton, "branch" sinon. Il ne l’écrit qu’en créant le workspace ; un workspace plus ancien se lit en ticket.

Mode ticket. Un jeton, c’est au moins deux majuscules, un tiret, des chiffres, borné des deux côtés : feat/PROJ-412_api porte PROJ-412, PROJ-4120 n’est pas PROJ-412. Le reste n’est pas une feature : ces branches n’ont pas de carte, et le Tableau les compte au lieu de les taire. Y coller un nom de branche sans jeton est refusé avec sa sortie : Atlas renvoie vers le réglage qui fait lire toute branche.

Mode branch. Le dernier segment nomme : feat/login-bug et alice/login-bug portent tous deux login-bug, origin/ retiré d’abord. Le nom est mis en forme — minuscules, les accents gardent leur lettre (Écran → ecran), le reste devient un tiret. Et il se lit en segment entier, plus strict qu’un ticket : login-bug est porté par feat/login-bug, pas par feat/login-bug-v2.

⚠️ Passer en branch remplit le Tableau : chaque branche sortie localement ou présente sur origin y devient une carte. Ce n’est pas du bruit à exclure — c’est la dormance à 60 jours qui replie les vieilles (le Tableau).

Jamais une feature, dans les deux modes : les lignes — develop, master, main, la ligne de base, chaque ligne de production déclarée par repo. Un id qui attraperait l’une d’elles est refusé, wip/develop compris : toutes les branches la portent, elle ne peut pas être une feature.

Déclarer : taper, ou coller. Le champ du bouton ＋ du Tableau accepte les deux : un id tapé passe à sa forme canonique (proj-412 → PROJ-412, Login Bug → login-bug), un nom de branche collé est lu par le juge de la découverte (feat/login-bug déclare login-bug, jamais feat-login-bug).

La ligne de base

C’est d’où part le diff de chaque feature : la branche d’intégration où ton travail finit par rentrer. Son nom est une convention d’équipe — develop chez les uns, master ou main chez les autres. Une clé, base, dans project.json.

Quatre niveaux, du plus précis au plus général : la feature (feature.json), le projet (project.json), la variable BASE, puis develop. La feature ne déclare que l’exception : y recopier la base du projet la figerait au premier changement.

atlas init la détecte et l’écrit : par repo, la branche que désigne origin/HEAD si ce n’est pas une feature, sinon la première présente parmi develop, master, main. Si les repos ne sont pas d’accord, rien n’est écrit et la commande le dit. Sous le champ, la même détection : ce que git montre repo par repo, le verdict (✓ détecté, ⚠ bases hétérogènes, ⚠ aucune ligne détectée), et ce qui est en vigueur. On écrit un nom nu : origin/ est refusé.

Un repo où la base cherchée n’existe pas sort de la carte, et Atlas le dit — il n’en invente jamais une autre. Le panneau Git porte alors une chip <repo> · base <nom> absente, et la carte un angle mort base absente (Quand Atlas ne voit pas).

La page Config

Le bouton ⚙️ Config du header ouvre une page qui remplace la carte — Échap revient. Trois vues ; la dernière ouverte est mémorisée sur cette machine.

vue ce qu’on y fait
Feature par repo : la branche feature et la branche de comparaison, plus la comparaison globale. Plusieurs branches portant le ticket sont groupées en tête du déroulant. Enregistré dans features/<ID>/feature.json
Projet les projets connus du registre (activer, ajouter, retirer), l’état du workspace partagé et la case « Partager mon travail automatiquement », le résumé de la config du projet actif, les six réglages éditables et la chronologie
Atlas quatre chapitres : le thème, la version en trois états (à jour · une version existe · je n’ai pas pu regarder, avec sa raison), « Brancher ton IA sur Atlas » — la commande qui installe le plugin, à copier — et l’hébergeur par hôte (jeton trouvé ou non, d’où il vient)

Les chapitres se plient

Chaque chapitre se plie, et tout arrive replié. Deux exceptions, parce qu’on vient les voir et pas les régler : « 🤝 Workspace partagé » dans la vue Projet, « Par repo » dans la vue Feature. Ce que tu plies est retenu sur cette machine, et un titre porte à droite ce que son repli cacherait quand c’est un fait : le nombre de couches, de repos exclus, un ⬆ v… disponible sur « Version ». Le drapeau du workspace, dans le header, ouvre la vue Projet en redépliant son chapitre.

Le thème

⚙️ Config › Atlas › « Thème » — trois boutons :

choix ce qu’il fait
Système suit la préférence claire/sombre de ton OS — le défaut, et un choix comme les autres
Clair force le clair, quel que soit l’OS
Sombre force le sombre, quel que soit l’OS

Sous les boutons, Atlas dit ce que « Système » donne ici et maintenant (« en ce moment : Sombre »). Le choix vit dans ce navigateur : il ne part ni dans project.json, ni chez les autres.

Les six réglages qu’Atlas ne peut pas deviner

La vue Projet affiche en lecture seule tes couches, types de fichiers, rangés d’office, repos front, repos membres et exclus. « Repos front » se lit encore, mais l’écran dit qu’il ne fait plus rien : « Sans effet […] : un fichier est front par ce qu’il porte […], plus par le nom de son repo. »

Sous ce résumé, une section « ✎ Ce qu’Atlas ne peut pas deviner » : six réglages s’écrivent depuis l’écran, six raisons différentes de ne pas les déduire.

réglage pourquoi il faut un humain
les familles maison le moteur sait compter un suffixe, pas le nommer. Les motifs non classés en forme de rôle sont proposés : un clic les déclare
ce qui fait une feature la convention que l’équipe écrit dans ses branches ne se lit pas dans le code
la ligne de base une convention d’équipe, pas un fait du code. Vide = rien de déclaré : Atlas cherche la ligne repo par repo
les repos exclus un clone parasite ne se distingue pas d’un membre par le code
le préfixe de route par repo un ingress peut le réécrire. Vide = route relative
la ligne de production par repo master existe partout ; qu’il soit vivant ne se lit ni dans son nom ni dans sa topologie. Trois états : un nom, vide = auto, — (ou aucune) = pas d’étape ici

Les six sont pliables, et le bouton Enregistrer, ancré au pied de la section, les commande tous. L’écriture est une liste blanche stricte : Atlas relit le fichier du disque, remplace ces clés-là, réécrit, et ce que tu as édité à la main à côté est préservé. Le reste s’édite dans project.json, clé par clé (Les stacks et project.json). Le message dit ✓ enregistré dans project.json, et la carte est rechargée : c’est elle qui prouve que le réglage a pris.

La chronologie

Dernier chapitre de la vue Projet : « Chronologie », sous-titré « ce que les précédents servis apportent — une ligne par index, et elle peut baisser ». Un précédent, c’est le souvenir d’une review passée qu’Atlas ressert sur un nœud voisin ; le chapitre dit ce que l’usage a accumulé, ligne après ligne — jamais un score.

Il s’ouvre sur une phrase qui explique cette mémoire et ce que mesure une ligne, écrite pour qui n’a jamais ouvert Atlas.

En tête, une phrase d’état :

ce qu’Atlas trouve la phrase
aucun index « aucun index des précédents — lance atlas precedents --build (il construit l’index ET ouvre la chronologie) »
un index, aucune ligne « l’index date du … et ne porte aucune ligne : il a été bâti avant la chronologie — le prochain atlas precedents --build ouvre la série »
des lignes combien de lignes la série porte, et la date de la plus récente
le daemon ne répond pas « je n’ai pas pu lire la chronologie (le daemon ne répond pas) »

En dessous, la lecture de la dernière ligne : un bloc par mesure — la question en mots simples, le chiffre avec sa fraction, un badge de direction par rapport à la ligne d’avant (« ↑ mieux », « ↓ moins bien », « = pareil », « première ligne », « ≠ pas comparable »), l’écart en mots, et une phrase qui dit quoi en faire. Un bloc d’avertissements n’apparaît que s’il y a quelque chose à regarder. La ligne brute de chaque build reste sous un dépliable « détail », replié. Le sens de chaque mesure est dans Ce que l’IA lit et écrit ; la commande qui ajoute une ligne, dans La ligne de commande. Le chapitre est relu à chaque ouverture de la vue Projet ; Atlas n’y calcule rien, il lit le fichier.

Les variables d’environnement

Elles disent à Atlas où regarder — quel workspace, quel port, quelle ligne de base, quel jeton. Aucune ne change ce qu’il produit : ATLAS_M2M_DEBUG n’ajoute qu’une trace.

variable ce qu’elle fait défaut
ATLAS_WORKSPACE chemin explicite vers un workspace, lu au démarrage du daemon si le registre n’a pas déjà un projet actif valide la remontée depuis le dossier courant
ATLAS_PORT ou PORT le port du daemon — pidfile et log sont indexés par port 3030
BASE la ligne de base, quand ni la feature ni le projet ne la déclarent develop
XDG_CONFIG_HOME où vit le registre des projets ~/.config
XDG_STATE_HOME où vivent le pidfile et les logs ~/.local/state
ATLAS_GITLAB_TOKEN (ou GITLAB_TOKEN, GLAB_TOKEN) · ATLAS_GITLAB_HOST un jeton GitLab explicite, et l’hôte qui le scope le jeton lu dans la config de glab
ATLAS_GITHUB_TOKEN (ou GH_TOKEN, GITHUB_TOKEN) · ATLAS_GITHUB_HOST les mêmes, côté GitHub la config de gh
ATLAS_CLAUDE_BIN le binaire lancé par atlas claude claude
ATLAS_M2M_DEBUG trace l’appariement des appels réseau sur la sortie d’erreur éteint

Les quatre variables d’hébergeur ont leur page : GitLab et GitHub.

⚠️ ATLAS_WORKSPACE ne sert pas à changer de projet : le dernier projet actif du registre l’emporte sur elle. Pour en changer : la page Config › Projet, ou atlas lancé depuis le nouveau chapeau.

Raccourcis

touche effet
Échap ferme la page Config et revient à la carte
Espace p c ouvre Config, et la referme — un seul geste dans les deux sens
Espace p t traverse Config vers le Tableau, en la refermant au passage

Aucun raccourci ne part d’un champ ni d’un déroulant, et Config en est pleine. Table entière : Le clavier.

Ce qu’Atlas ne fait pas

  • Il ne devine ni un préfixe de route, ni une ligne de production, ni une famille maison : ces trois-là se déclarent, et une absence se dit plutôt que de se combler. Ce qui fait une feature et la ligne de base sont, eux, détectés une fois par atlas init, puis écrits comme des décisions modifiables.
  • Il ne supprime rien sur le disque : exclure un repo le retire de la carte, pas du chapeau.
  • Il n’écrit jamais ta curation, ta spec ni tes contrôles, et l’IA non plus : elle n’a aucun outil vers curation/, controles/, project.json ou le code des repos (Brancher l’IA).
  • Il ne fait pas de dépôt du workspace sans qu’on le lui demande : atlas init pose le .gitignore, jamais le git init. Une fois le dépôt ouvert, deux gestes partent seuls — un pull --ff-only si tu as du retard, un commit + push si tu as coché « Partager mon travail automatiquement », au plus une fois par heure.
  • Il ne se note pas : la chronologie est une série de lignes, sans seuil ni verdict, et aucune ne s’y ajoute toute seule.

Limites connues

  • L’identité est lue à la racine du chapeau, qui n’est pas un dépôt : git remonte à ta config globale, et un user.email posé par repo n’est pas vu.
  • GitLab et GitHub valent la même chose — Revue, publication, droit d’écrire, colonne « en review ». Ce qui reste inégal, et ce qui n’a jamais été éprouvé, est dans GitLab et GitHub.
