Configurer un projet

Tout ce qu'Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s'édite depuis l'écran.

Tout ce qu’Atlas sait de ton projet tient dans un dossier, .atlas-workspace/. Cette page dit où il est, qui possède quoi dedans, quels repos et quelles branches il regarde, et ce qui s’édite depuis l’écran.

Le moteur ne connaît aucun framework : ce qui rend juste la carte d’une feature — le chemin d’un ticket à travers tes repos — vient de ce dossier. atlas init sur un projet neuf produit une carte utilisable sans qu’une ligne soit éditée.

Les règles de reconnaissance — stacks livrées, couches, familles, entrées, toutes les clés de project.json — sont dans Les stacks et project.json. L’installation et atlas init : Prise en main ; le plugin IA : Brancher l’IA.

Où vit la configuration

Atlas travaille sur un chapeau : le dossier qui héberge tes repos, ou le repo lui-même. La config vit dans un .atlas-workspace/ à sa racine, trouvé par remontée comme git trouve son .git/ ; la racine en est le parent, elle ne se règle pas.

À côté, le registre des projets vit sur ta machine, hors de tout projet (Prise en main). Chaque projet a sa propre instance : un onglet ne règle que le sien.

La config est relue à chaque appel : édite project.json, recharge.

Ce qui se partage, ce qui reste à toi

Le workspace contient deux natures, et le critère est le versionnement :

  • la conf projet — vraie pour quiconque ouvre ce projet : elle se commite. Chez le suivant : git clone <url> .atlas-workspace au lieu d’atlas init ;
  • la conf locale — ce qui n’appartient qu’à toi : jamais commitée.

atlas init pose un .gitignore dans .atlas-workspace/, sans git init (versionner est une décision d’équipe) : il exclut ton casier local (features/*/curation/local/) et l’ancien features/*/curation.json. En faisant un dépôt du workspace (Config › Projet, « Workspace partagé »), puis à chaque « Partager », Atlas ajoute la règle qui manquerait — un init plus ancien n’excluait que la seconde, et git add -A publierait ton casier local. Tout le reste part, controles/ compris.

L’arborescence

mon-chapeau/
├─ .atlas-workspace/
│  ├─ project.json  stack/<id>.json  ESPACES.md  .gitignore
│  ├─ precedents.json  precedents/moi@exemple.com.json
│  ├─ controles/2026-01-20.json   # un contrôle humain, daté
│  └─ features/PROJ-412/
│     ├─ ticket.md  feature.json
│     ├─ comments/  overlay/  plan/  parcours/   # un fichier par personne
│     └─ curation/
│        ├─ moi@exemple.com.json        # ce que j'ai relu et validé — partagé
│        └─ local/moi@exemple.com.json  # fils ouverts, branche lue — jamais partagé
├─ projet-api/                  # repo membre (auto-découvert : il a un .git)
└─ app-front/                   # repo membre

Un espace, un fichier, un propriétaire : un diff dit qui a parlé.

fichier à qui quoi commité ?
project.json toi les règles du projet — dix s’éditent depuis l’écran oui
stack/<id>.json toi ce que tu ajoutes à une stack livrée oui
precedents.json Atlas l’index des reviews passées (atlas precedents --build), reconstruit par chaque poste non
precedents/<qui>.json Atlas les services, les sondes, la chronologie oui
controles/<date>.json toi tes réponses à un contrôle : un par jour, signé de ton adresse git, jamais réécrit oui
features/<ID>/ticket.md toi — l’IA sur ton accord la spec : objectif, critères, « ne fait pas » oui
features/<ID>/feature.json toi ou l’IA la déclaration : titre, repos membres, branches choisies, la base d’exception oui
overlay/<qui>.json · parcours/<qui>.json · plan/<qui>.json l’IA de ta session ce qu’elle a compris, les étapes, le pseudo-code oui
comments/<qui>.json les deux ta part de la conversation (un fichier par personne) oui
curation/<qui>.json toi tes endossements (relu et validé), tes notes de criticité, tes « pas compris » oui — c’est ce que l’équipe voit
curation/local/<qui>.json toi les fils que tu as ouverts, la branche que tu lis non, jamais

Ta curation porte le slug de ton adresse git (git config user.email) : l’identité se lit dans git. Sans identité, Atlas retombe sur un curation.json mono-utilisateur, ignoré par git. La carte n’est jamais stockée : ce dossier ne contient que ce qui se déclare.

controles/ naît au premier atlas precedents --controle (La ligne de commande) : tu y juges jusqu’à trente paires — un nœud et un précédent qu’il aurait pu lui servir — (oui · non · pas-su). Rien n’y est écrasé : un second contrôle le même jour refuse en le nommant.

Les repos membres

L’appartenance est auto-découverte : tout sous-dossier du chapeau qui contient un .git est un repo membre, les dossiers cachés exceptés. Ajouter un repo au chapeau suffit.

Un repo seul est son propre membre, déclaré (atlas init l’écrit) : { "name": "myapp", "path": "." } — un nom déduit du dossier changerait d’un clone à l’autre. Un path absolu, hors du chapeau ou sans .git n’est pas lu, et le serveur le dit. Le .atlas-workspace/ vit alors dans le repo, jamais compté comme diff ni dans ● Local : ignore-le ou versionne-le à part (commité avec le code, il suivrait la branche).

Deux clés seulement s’en mêlent :

  • exclude — les repos à retirer de la découverte (un clone parasite posé là) ;
  • repos[] — des overrides par repo. Une entrée porte le name du dossier plus, au choix, path, branch, routePrefix, productionBase.

branch est un motif avec {id} : feat/{id} reconnaîtra feat/PROJ-412 et rien d’autre ici. Sans motif, la règle générale de la section suivante s’applique.

routePrefix est le préfixe sous lequel les routes de ce repo sont servies (/back-office) — déclaré, jamais déduit : un ingress peut le réécrire. Sans lui, l’étiquette d’une entrée HTTP reste relative (▶ GET …/orders/history, le …/ dit « montage non lu ») et Atlas pose un angle mort — le moteur dit qu’il ne sait pas au lieu de deviner. Déclaré, l’URL est exacte.

productionBase est la branche qui porte la production de ce repo : null y déclare qu’il n’y a pas d’étape de déploiement ici, l’absence applique le défaut (master ou main, s’il existe ici et diffère de la ligne d’intégration). C’est ce qui range une feature en « 🚀 À déployer » ou « ✅ Terminé » dans le Tableau.

Ce qui fait une feature

Ce nom de branche désigne-t-il une feature, et laquelle ? Le code ne le porte pas : c’est une convention d’équipe, elle se déclare par featureId :

featureId ce qui devient une feature comment elle est nommée
"ticket" — le défaut quand la clé est absente seules les branches dont le nom porte un jeton de la forme PROJ-412 par ce jeton, en majuscules
"branch" toute branche qui n’est pas une ligne par son dernier segment ; un jeton de ticket, s’il y en a un, prime

Il se règle dans Config › Projet (« Ce qui fait une feature »). atlas init le détecte et l’écrit, même au défaut — "ticket" dès qu’une branche des membres, locale ou distante, porte un jeton, "branch" sinon — mais seulement en créant le workspace ; un plus ancien se lit en ticket.

Mode ticket. Un jeton : au moins deux majuscules, un tiret, des chiffres, borné des deux côtés — feat/PROJ-412_api porte PROJ-412, PROJ-4120 n’est pas PROJ-412. Les autres branches n’ont pas de carte, et le Tableau les compte au lieu de les taire. Y coller un nom de branche sans jeton est refusé avec sa sortie : le réglage qui fait lire toute branche.

Mode branch. Le dernier segment nomme (origin/ retiré) : feat/login-bug et alice/login-bug portent login-bug. Le nom est mis en forme — minuscules, un accent garde sa lettre (Écran → ecran), le reste devient un tiret — et se lit en segment entier : login-bug est porté par feat/login-bug, pas par feat/login-bug-v2.

⚠️ Passer en branch remplit le Tableau : chaque branche locale ou sur origin y devient une carte. La dormance à 60 jours replie les vieilles (le Tableau).

Jamais une feature : les lignes — develop, master, main, la ligne de base, chaque ligne de production déclarée. Un id qui en attraperait une est refusé, wip/develop compris : toutes les branches la portent, elle ne peut pas être une feature.

Déclarer : taper, ou coller. Le champ du bouton ＋ du Tableau accepte un id tapé, mis en forme (proj-412 → PROJ-412, Login Bug → login-bug), ou un nom de branche collé, lu comme la découverte le lit (feat/login-bug déclare login-bug, jamais feat-login-bug).

La ligne de base

C’est d’où part le diff de chaque feature : la branche d’intégration où ton travail rentre, une convention d’équipe (develop, master, main). Une clé, base, dans project.json.

Quatre niveaux, du plus précis au plus général : la feature (feature.json), le projet (project.json), la variable BASE, puis develop. La feature ne déclare que l’exception.

atlas init la détecte et l’écrit : par repo, la branche que désigne origin/HEAD si ce n’est pas une feature, sinon la première parmi develop, master, main ; des repos en désaccord, rien n’est écrit, et il le dit. Sous le champ, la même détection, son verdict (✓ détecté, ⚠ bases hétérogènes, ⚠ aucune ligne détectée) et ce qui est en vigueur. origin/ est refusé.

Un repo où la base cherchée n’existe pas sort de la carte, et Atlas le dit — il n’en invente jamais une autre. Le panneau Git porte alors une chip <repo> · base <nom> absente, et la carte un angle mort base absente (Quand Atlas ne voit pas).

La page Config

Le bouton Config du header ouvre une page qui remplace la carte. Sa tête porte le titre, les trois vues et « ← Carte · Échap » (le bouton, ou Échap, revient). La dernière vue ouverte est mémorisée sur cette machine.

vue ce qu’on y fait
Feature par repo : la branche feature et la branche de comparaison, plus la comparaison globale. Plusieurs branches portant le ticket sont groupées en tête du déroulant. Enregistré dans features/<ID>/feature.json
Projet les projets connus du registre (leur état, « Ouvrir » dans un nouvel onglet, le projet « par défaut » et « en faire le défaut », ajouter, « Retirer »), l’état du workspace partagé et la case « Partager mon travail automatiquement », le résumé de la config du projet de l’onglet, les dix réglages éditables et la chronologie
Atlas le thème, la taille du texte, l’interligne, le contraste, la largeur du Code, les instances (ports, arrêt sans activité), la version et le commit qui tournent (à jour · une version existe · pas pu regarder, avec sa raison), « Brancher ton IA sur Atlas », l’hébergeur par hôte

Les chapitres se plient

Chaque chapitre se plie, et tout arrive replié sauf « Workspace partagé » (Projet) et « Par repo » (Feature). Le pli est retenu sur cette machine ; un titre dit à droite ce que son repli cache. Le drapeau du workspace, dans le header, ouvre la vue Projet en redépliant son chapitre.

Les réglages d’affichage

Cinq segments de Config › Atlas, appliqués tout de suite et retenus dans ce navigateur, jamais dans project.json ; revenir au défaut efface le choix.

  • Thème — Système (le défaut, un choix : il suit ton OS, et Atlas dit ce qu’il donne), puis un choix par thème livré (Clair, Sombre).
  • Taille du texte — 12 · 13 · 14 · 15 px, 13 par défaut : métadonnées, titres, lignes de l’Arbre et gouttière du Code suivent.
  • Interligne — serré · normal · aéré, normal par défaut : les lignes de l’Arbre, le code et la prose s’espacent ensemble.
  • Contraste — normal · renforcé · fort, normal par défaut : l’à-relire fonce (gras au fort), le relu recule par une encre lisible plutôt que par la transparence, le couloir du contexte se marque, les couleurs de sens se saturent ; aucun texte sous 4,5:1.
  • Largeur du Code — un quart · large, un quart par défaut ; « large » rend au Code tout ce que l’Arbre laisse.

Les dix réglages qu’Atlas ne peut pas deviner

La vue Projet affiche en lecture seule tes couches, types de fichiers, rangés d’office, repos front, repos membres et exclus. Chaque couche montre sa pastille et d’où vient sa couleur : défaut, couleur du projet (sa teinte) ou sans teinte lisible — elle se change à la main (layers[].color). « Repos front » se lit encore, et l’écran le dit sans effet : un fichier est front par ce qu’il porte, plus par le nom de son repo.

Sous ce résumé, une section « Ce qu’Atlas ne peut pas deviner » : dix réglages s’écrivent depuis l’écran, dix raisons de ne pas les déduire.

réglage pourquoi il faut un humain
les familles maison le moteur sait compter un suffixe, pas le nommer. Les motifs non classés en forme de rôle sont proposés : un clic les déclare
ce qui fait une feature la convention que l’équipe écrit dans ses branches ne se lit pas dans le code
les types de commit une convention d’équipe (hotfix/) ne se lit pas dans le code
les domaines sensibles ce qui est risqué par nature chez vous ne se lit pas dans le code
le vocabulaire du projet les mots de l’équipe ne se lisent pas dans le code
la ligne de base une convention d’équipe, pas un fait du code. Vide = rien de déclaré : Atlas cherche la ligne repo par repo
les repos exclus un clone parasite ne se distingue pas d’un membre par le code
le préfixe de route par repo un ingress peut le réécrire. Vide = route relative
la ligne de production par repo master existe partout ; qu’il soit vivant ne se lit ni dans son nom ni dans sa topologie. Trois états : un nom, vide = auto, — (ou aucune) = pas d’étape ici
les précédents importés servir un constat que personne n’a discuté est une décision. Une case, cochée par défaut

La case « Servir aussi les précédents importés d’un ticket » porte son aveu : « un précédent importé est une piste, jamais un verdict » (Les précédents). Une valeur illisible ("false" entre guillemets) vaut le défaut, oui, et l’écran le dit.

« Socle de recette » montre le socle par service, sans l’éditer (La recette).

« Types de commit » montre les types reconnus d’office (feat, fix…) et un champ pour en ajouter (hotfix, en minuscules) : ils font la nature d’une feature (Le Tableau) et le scope d’un commit.

« Domaines sensibles » : un domaine sensible par ligne, un nom (le paiement) et ses mots (stripe, billing) ; un nœud dont le chemin en porte un reçoit une criticité proposée. Mots vides = retiré.

« Vocabulaire du projet » : un mot par ligne — le mot (panier), sa définition en une phrase (200 caractères au plus), les noms du code qui le portent (ShopCart, CartTemplate) ; « Retirer » ou vider le mot l’enlève. À l’ouverture du chapitre, chaque mot dit ce qu’en dit le code : « porté par ShopCart », « aucun code ne porte ce nom » ou « pas pu regarder » (un repo illisible, ou plus de 10 s). Une entrée illisible se dit et ne compte pas ; « Enregistrer » ne réécrit le vocabulaire que si ce chapitre a bougé. Ce que l’IA en reçoit : Brancher l’IA.

Les dix sont pliables ; Enregistrer, au pied de la section, les commande tous. L’écriture est une liste blanche stricte : Atlas relit le fichier du disque, remplace ces clés-là, réécrit — ce que tu as édité à la main à côté est préservé. Le reste s’édite dans project.json (Les stacks et project.json). Le message dit ✓ enregistré dans project.json, et la carte est rechargée : c’est elle qui prouve que le réglage a pris.

La chronologie

Dernier chapitre de la vue Projet. Un précédent est une review passée qu’Atlas ressert sur un nœud voisin ; le chapitre dit ce que l’usage a accumulé, ligne après ligne — jamais un score.

En tête, une phrase d’état :

ce qu’Atlas trouve la phrase
aucun index « aucun index des précédents — lance atlas precedents --build (il construit l’index ET ouvre la chronologie) »
un index, aucune ligne « l’index date du … et ne porte aucune ligne : il a été bâti avant la chronologie — le prochain atlas precedents --build ouvre la série »
des lignes combien de lignes la série porte, et la date de la plus récente
le daemon ne répond pas « je n’ai pas pu lire la chronologie (le daemon ne répond pas) »

Dessous, la lecture de la dernière ligne : par mesure, la question, le chiffre et sa fraction, la direction depuis la ligne d’avant, l’écart et quoi en faire ; la ligne brute sous « détail ». Le sens des mesures : Ce que l’IA lit et écrit.

Les variables d’environnement

Elles disent à Atlas où regarder (workspace, port, ligne de base, jeton) ; aucune ne change ce qu’il produit — ATLAS_M2M_DEBUG n’ajoute qu’une trace.

variable ce qu’elle fait défaut
ATLAS_WORKSPACE le projet que sert une instance (atlas start le pose) la remontée, puis le projet par défaut
ATLAS_PORT force le port d’une instance (PORT : npm run dev seul) le port du projet
BASE la ligne de base, quand ni la feature ni le projet ne la déclarent develop
XDG_CONFIG_HOME où vit le registre des projets ~/.config
XDG_STATE_HOME où vivent le pidfile et les logs ~/.local/state
ATLAS_GITLAB_TOKEN (ou GITLAB_TOKEN, GLAB_TOKEN) · ATLAS_GITLAB_HOST un jeton GitLab explicite, et l’hôte qui le scope le jeton lu dans la config de glab
ATLAS_GITHUB_TOKEN (ou GH_TOKEN, GITHUB_TOKEN) · ATLAS_GITHUB_HOST les mêmes, côté GitHub la config de gh
ATLAS_CLAUDE_BIN le binaire lancé par atlas claude claude
ATLAS_M2M_DEBUG trace l’appariement des appels réseau sur la sortie d’erreur éteint

Les quatre variables d’hébergeur ont leur page : GitLab et GitHub.

⚠️ ATLAS_WORKSPACE ne change pas de projet : le registre l’emporte. Pour en changer : Config › Projet, ou atlas lancé depuis le nouveau chapeau.

Raccourcis

touche effet
Échap ferme la page Config et revient à la carte
Espace p c ouvre Config, et la referme — un seul geste dans les deux sens
Espace p t traverse Config vers le Tableau, en la refermant au passage

Aucun raccourci ne part d’un champ ni d’un déroulant, et Config en est pleine. Table entière : Le clavier.

Ce qu’Atlas ne fait pas

  • Il ne devine ni un préfixe de route, ni une ligne de production, ni une famille maison, ni un mot du projet ou le nom du code qui le porte : ils se déclarent, et une absence se dit plutôt que de se combler. Ce qui fait une feature et la ligne de base sont, eux, détectés une fois par atlas init, puis écrits comme des décisions modifiables.
  • Il ne supprime rien sur le disque : exclure un repo le retire de la carte, pas du chapeau.
  • Il n’écrit jamais ta curation, ta spec ni tes contrôles, et l’IA non plus : elle n’a aucun outil vers curation/, controles/, project.json ou le code des repos (Brancher l’IA).
  • Il ne fait pas de dépôt du workspace sans qu’on le lui demande : atlas init pose le .gitignore, jamais le git init. Branché, il fait un tour par minute (voir Le panneau Git).
  • Il ne se note pas : la chronologie est une série de lignes, sans seuil ni verdict.

Limites connues

  • L’identité est lue à la racine du chapeau, qui n’est pas un dépôt : git remonte à ta config globale, et un user.email posé par repo n’est pas vu.
  • GitLab et GitHub valent la même chose — Revue, publication, droit d’écrire, colonne « en review ». Ce qui reste inégal, et ce qui n’a jamais été éprouvé, est dans GitLab et GitHub.
