Brancher l'IA

Atlas ne lance aucune IA : c'est ta session de code qui l'interroge. Cette page dit comment les mettre en présence — installer le plugin, ouvrir la session au bon endroit, lancer un skill, ou brancher le tien sur Atlas.

Atlas ne lance aucune IA : c’est ta session de code qui l’interroge. Cette page dit comment les mettre en présence — installer le plugin, ouvrir la session au bon endroit, lancer un skill, ou brancher le tien sur Atlas.

Le principe : chacun apporte sa moitié

Atlas n’embarque ni modèle, ni clé d’API, ni agent. Il expose ce qu’il sait à la session que tu lances toi-même, par deux canaux : un plugin (sept procédures qu’on déclenche sur demande) et un serveur MCP (douze outils que le modèle appelle quand il en a besoin).

Ta session apporte le contexte et le droit d’écrire du code ; Atlas, ce qu’une IA n’obtient pas seule, ou pas correctement :

  • le diff exact d’une feature, même sur une branche non sortie ou déjà mergée ;
  • la carte : l’arbre des appels, prouvé par les types, un flux par point d’entrée ;
  • ce que les relecteurs ont endossé, leur note de criticité (1 à 4), ce qu’ils n’ont pas compris ;
  • les fils déjà ancrés sur une ligne ou un symbole, souvent les siens, d’une session oubliée ;
  • les précédents : ce qu’un finding passé, sur un nœud du même type, a donné.

Les outils un par un, ce que chacun rend, ce que l’IA peut écrire et ce qu’elle n’atteint jamais : Ce que l’IA lit et écrit.

Installer

atlas plugin           # imprime les gestes d'installation des quatre clients, sans rien exécuter
atlas plugin install   # Claude Code : les exécute

atlas plugin install enregistre le marketplace atlas puis installe le plugin atlas@atlas. Il pose deux choses : les sept skills (/atlas:ticket, /atlas:resolve, /atlas:review, /atlas:resolve-review, /atlas:as-coded, /atlas:recette, /atlas:answer) et la déclaration du serveur MCP, qui se lance par la commande atlas mcp.

La même commande met à jour (Claude Code copie le plugin), comme atlas update (voir Prise en main).

La portée est ta configuration utilisateur, pas un repo : installé une fois, il sert tous tes projets — et c’est pourquoi atlas init ne l’installe jamais tout seul.

⚠️ Redémarre ta session de code après l’installation comme après une mise à jour. Les plugins se chargent au démarrage : une session ouverte ne verra ni les nouveaux skills, ni les outils.

Le prérequis qui coince : le plugin déclare comment joindre Atlas, il ne le contient pas — la commande atlas doit être dans le PATH de ta session, sinon aucun outil d’Atlas n’apparaît. L’installation a besoin de la commande claude (ou d’un autre binaire désigné par ATLAS_CLAUDE_BIN) ; sans elle, elle échoue en nommant la commande qu’elle n’a pas pu lancer.

Gemini CLI et Codex

Les skills servent tout client qui lit des SKILL.md et un serveur MCP, avec le modèle de ta session : aucun n’en impose un. Le dossier plugin/ est aussi une extension Gemini CLI.

atlas plugin install gemini   # gemini extensions link <atlas>/plugin — lu en place, demande ton accord
atlas plugin install codex    # (ou cursor) imprime les gestes, à lancer toi-même (non éprouvé)

Hors Claude Code, on demande un skill par son nom (« atlas:review PROJ-412 »). ⚠️ Claude Code seul garantit par sa configuration qu’un skill de lecture n’écrit aucun fichier. Ailleurs, le texte du skill le dit et le modèle le tient ; ce qu’aucun outil d’Atlas ne fait (ta spec, ta validation, ton code, publier) reste impossible partout.

Où ouvrir ta session

Le serveur MCP cherche le projet en remontant depuis le dossier courant de la session, exactement comme git remonte jusqu’au .git/ — depuis le chapeau, un repo ou un sous-dossier, il trouve le même .atlas-workspace/, et parle à l’instance de ce projet.

Les refus que tu peux lire, et ce qu’ils veulent dire :

ce que tu lis ce qui se passe ce que tu fais
aucun .atlas-workspace/ au-dessus du dossier de cette session la session est ouverte hors du projet rouvre-la sous le chapeau ou dans un de ses repos
réponse rejetée : elle vient du projet « … » (les deux chemins nommés) l’adresse répond pour un autre projet relance la session ; atlas status dit qui tourne où
ne dit pas quel projet elle sert une instance d’une version antérieure tourne atlas restart --all
l'instance d'Atlas de ce projet ne répond pas elle n’a pas démarré atlas logs <projet>

Le dossier d’ouverture ne change que ce que ta session a sous la main : au chapeau, tous les repos. Le serveur écrit où il se croit sur sa sortie d’erreur au démarrage :

[atlas mcp] prêt — workspace /…/.atlas-workspace · daemon http://127.0.0.1:3030

Les sept skills

Un skill est une procédure complète, qui ne part que sur demande explicite — la tienne, ou celle d’un agent que tu as lancé : un orchestrateur peut enchaîner ticket → resolve → review. Aucun ne se déclenche seul : ils écrivent dans la carte — trois dans tes fichiers. Tous emploient les mots de ton projet plutôt que les noms du code quand ils t’écrivent. Les outils restent disponibles hors des skills.

skill quand le lancer ce qu’il écrit ce qu’il ne touche jamais
/atlas:ticket avant de coder ta spec et ses critères, après ton accord — plus la déclaration de la feature, des fils d’hypothèse ancrés, le pseudo-code et le fil de feature le code, les branches, ton endossement, la coche d’un critère, le parcours
/atlas:resolve pour coder la feature le code des repos et la branche de la feature (un worktree si tu le choisis), plus les intentions, le parcours et les fils de l’épilogue ton endossement, la spec, la merge request, la déclaration d’une feature
/atlas:review après le code, avant de corriger des fils de findings ancrés ligne à ligne, la conclusion dans le fil de feature, et ce que les précédents ont donné le code, ton endossement, la spec, les autres fichiers
/atlas:resolve-review après une review le code des repos, et une réponse dans chaque fil de l’IA : corrigé, ou pourquoi pas ton endossement, la spec, la résolution d’un fil
/atlas:as-coded après les corrections, à la relecture did/does par nœud, le parcours et sa lecture des critères, plus les doutes le code, ton endossement, la spec
/atlas:recette pour tester la recette, par atlas recette le code, ton endossement
/atlas:answer quand des fils ou des ? attendent des réponses dans les fils existants, et des fils neufs là où on lui demande d’expliquer le code, la résolution d’un fil

/atlas:as-coded ne réécrit jamais une intention posée en codant : un écart reste visible, et tu tranches. Son parcours raconte le voyage de la donnée en 3 à 8 étapes cliquables ; il évalue les critères, sans les écrire.

Les six premiers sont des moments : chacun signe son passage, que Relecture liste (Relire et endosser).

/atlas:answer répond aux fils dont le dernier message est de toi, explique les nœuds marqués ?, ouvre un fil sur les nœuds notés 4 qui n’en ont aucun, et ne résout jamais rien : un fil se clôt à la main.

/atlas:ticket — ouvrir la feature, et écrire sa spec

C’est le premier moment, avant qu’une ligne soit écrite. Il ouvre la feature — il la déclare si Atlas ne la connaît pas encore, et l’id vient de toi ou d’une branche qui existe, jamais d’une invention —, puis il lit le terrain : l’entrée réelle de la donnée, la chaîne d’appels existante jusqu’à ses sorties. Un ticket qui ne nomme rien du code produit des nœuds prévus qui n’atterrissent jamais.

Il pose ensuite ses hypothèses là où elles tombent : un fil ancré sur chaque symbole existant qui va bouger, un nœud en pointillé pour ce qui reste à écrire. L’ordre est contraignant, et c’est le seul endroit où il l’est : l’ancrage fait exister les nœuds d’une feature qui n’en avait aucun, et les précédents ne se demandent qu’après, parce qu’un nœud prévu n’en reçoit jamais. Avant de proposer le moindre texte, il écrit une ligne en trois états — oui · non · je n’ai pas pu regarder — sur la spec, le terrain, les précédents et ce qu’Atlas n’a pas pu prouver.

C’est le seul skill qui écrit ta spec — aucun outil d’Atlas n’écrit ticket.md —, dans ta session et avec tes outils, à trois conditions :

  • il te montre le texte entier et pose une question fermée — « je l’écris dans ticket.md ? » —, et n’écrit qu’après ton accord ;
  • sur une spec déjà remplie, il montre d’abord ce qui change : ajouté, retiré, reformulé ;
  • en mode non interactif (claude -p, où personne ne peut répondre), la règle se durcit : il n’écrit que sur une spec absente ou vierge, jamais sur une remplie — il rend le texte proposé et s’arrête.

Sur une spec absente ou vierge qui porte un lien vers ton traqueur, il l’importe une fois — avec l’outil de ta session, Atlas n’en fournit aucun : injoignable, il continue sans et le dit, plutôt que d’écrire une spec fantôme. Un geste ne lui appartiendra jamais : cocher un critère. Il les écrit nus, la coche est ta validation (Ticket, fils et Journal).

Ton refus n’arrête pas le run : le texte reste dans la conversation et le reste se pose quand même — les nœuds prévus, le fil de feature (la cause pressentie, ce qui a été décidé, ce qui reste ouvert), et les sondes — ce qu’il a fait de chaque précédent servi. Il finit par les commandes de branche à lancer toi-même, base mise à jour d’abord ; il ne les lance pas. Et comme /atlas:resolve, il laisse rédiger ton propre skill de projet : /atlas:ticket PROJ-412 avec /mon-ticket.

/atlas:resolve — le seul skill qui écrit du code

Les outils d’Atlas n’écrivent jamais dans tes repos ; ce skill, lui, tourne dans ta session et y écrit comme toi. Ce qu’il apporte n’est pas de savoir coder : c’est ce qui entoure le code.

L’établi, avant tout le reste. Pour chaque repo touché, il te propose un worktree — un second dossier sur le même dépôt, qui laisse ton dossier principal intact — et le recommande quand le repo a des modifications non commitées ou porte une autre feature. Il le crée sous .worktrees/<feature>/<repo> à la racine du projet (rangé à côté des repos, Atlas le prendrait pour un repo de plus), sans dépendances installées ni .env ignoré. Puis il met à jour la ligne de base en avance rapide seulement et crée dessus la branche de la feature, ou reprend celle qui existe. Une mise à jour refusée l’arrête, sans fusion ni rebase.

Le prologue, avant la première ligne. Il lit la carte (jamais un grep pour commencer), les refs qui font foi — contre quelle base tu codes, et si la feature est déjà mergée —, les précédents servis par atlas precedents, le fil de feature (« ce qu’on a compris » : la cause racine, les décisions déjà prises), les tests qui atteignent chaque nœud qu’il va toucher, ta spec, et ce que les relecteurs ont déjà dit dessus — les ? sans réponse, les notes de criticité. Il finit par les angles morts : ce qu’Atlas n’a pas pu prouver, dit avant de coder plutôt que supposé.

Puis il écrit dans le chat une ligne en trois états — oui · non · je n’ai pas pu regarder — avant d’écrire quoi que ce soit, par exemple :

3 précédents · 1 réponse humaine · 0 ? · compris : 1 fil · tests : pas pu regarder · 2 angles morts

0 précédent est un fait, pas pu regarder en est un autre : les confondre fait croire à un terrain propre. Si cette ligne ne peut pas s’écrire, le prologue n’a pas eu lieu et il ne code pas.

Le milieu, le code. Tu peux le confier à ton propre skill de projet, en le nommant dans l’argument : /atlas:resolve PROJ-412 avec /mon-resolve. Le nom est lu, jamais deviné — qu’un skill s’appelle …-resolve ne prouve pas qu’il sait coder. Si l’invocation échoue, resolve le dit en une ligne et passe à sa méthode générique (une étape à la fois, un commit par étape, du plus profond vers l’entrée, les tests d’un nœud lus avant d’y toucher, les conventions prises dans le code voisin). Le cas connu : un skill que son client réserve au clavier (dans Claude Code, disable-model-invocation) ne se charge pas depuis un autre skill — tu le tapes toi-même, le prologue reste dans la conversation.

L’épilogue ne saute jamais, même quand la session a été longue : les intentions nœud par nœud (intent, goal, et unsure pour tout doute qui a survécu), le parcours avec les critères et les refs qui les prouvent, un fil sur ce qui a été décidé — l’arbitrage qu’un relecteur ne retrouvera pas dans le diff —, le fil de feature pour ce qu’on a compris, et les sondes sur les précédents lus.

Deux choses qu’il ne fait jamais, et ce sont les plus importantes. Il n’écrit pas did/does — ce que le code faisait et ce qu’il fait se constatent à la relecture, par /atlas:as-coded : les écrire ici serait un autoportrait, où l’annonce et le constat s’accordent toujours. Et il ne publie rien chez ton hébergeur, ni ne déclare une feature : ces deux outils lui sont explicitement retirés. Il travaille sur une feature qui existe déjà ; si elle n’existe pas, il s’arrête et te renvoie à /atlas:ticket.

/atlas:review — et ce que les précédents ont donné

Il juge : correctness, robustesse, sécurité, cohérence entre services, superflu. Ses findings — ce qu’il reproche, un par fil — arrivent là où on lit, ancrés à la ligne, jamais en rapport à côté, et il ne publie rien. Sa conclusion, elle, va dans le fil de feature : l’unique conversation posée sur la feature entière, et non sur un symbole (Ticket, fils et Journal).

Il lit les précédents après ses propres checks, jamais avant : il juge d’abord à l’aveugle, puis compare. Un précédent qui s’applique est cité dans le finding — c’est la provenance de la règle, et elle s’audite. Un précédent qu’il a lu et écarté, ou un cas qui lui a manqué sur un nœud, il le signale par l’outil sonde : ce n’est pas du savoir, c’est la liste de travail de l’index suivant. Ce que sont les précédents, comment l’index se construit et ce que la sonde écrit sont sur Ce que l’IA lit et écrit.

Entre les skills, un moment sans skill

Pendant que vous codez, l’IA appelle les outils au fil de l’eau — intent (le titre métier d’un nœud), goal (le pourquoi), unsure (le doute), un fil sur un piège repéré. C’est ce moment-là qui rend la relecture utile : intent et does écrits par la même lecture s’accordent toujours et n’apprennent rien ; écrits à deux moments, leur écart est précisément ce qu’Atlas montre.

Le serveur MCP

atlas mcp est un serveur stdio : il n’écoute aucun port, c’est ton client qui le lance au démarrage de la session et lui parle par son entrée standard. Tu ne le tapes jamais à la main.

Il ne calcule rien : il traduit des questions en appels au daemon, qui reste seul à lire git et le code. Il démarre le daemon au lancement si la session est sous un projet Atlas — une session ouverte ailleurs n’allume rien chez toi. Une erreur d’outil revient en texte lisible dans la réponse, pour que le modèle puisse corriger son appel.

Un outil porte deux noms, selon la façon dont Atlas est branché : mcp__plugin_atlas_atlas__digest quand il vient du plugin, mcp__atlas__digest quand tu as déclaré le serveur MCP toi-même. Si tu écris un skill qui pré-accorde des outils, liste les deux formes — c’est ce que font les six skills d’Atlas, ligne par ligne ; un seul nom ne vaut que pour une moitié des installations, sans que rien ne le dise.

⚠️ Dans un skill Claude Code, la liste allowed-tools pré-accorde, elle ne retire rien : tout outil reste appelable. Ce qui retire, c’est disallowed-tools — c’est par là que /atlas:resolve se prive de déclarer une feature.

Brancher ton propre skill sur Atlas

Ton skill de review maison n’a pas à être remplacé par /atlas:review : tu veux qu’il écrive dans Atlas — la carte avant le code, un fil par finding — en gardant ses checks. Ce lien est un geste de toi, pas un mécanisme à configurer. Deux façons, qui se valent :

  • un mot dans le prompt : /mon-review PROJ-412 en postant tes commentaires dans Atlas. Ce que tu écris après la commande arrive à ton skill comme argument — c’est ce mot-là, et rien d’autre, qui décide qu’il entre dans Atlas ;
  • une ligne écrite à la main dans ton skill, dans sa section de process : commence par la carte, puis un fil par finding, ancré à la ligne. Tu l’écris une fois, elle vaut pour tous tes runs.

Ce que ton IA sait faire à ce moment-là ne vient pas de cette ligne : le serveur MCP l’annonce à chaque session, dans ses instructions. D’abord les espaces : qui écrit quoi et par quel outil — les intentions, la structure de la carte, les fils, le parcours, le pseudo-code —, et ce qui n’a aucun outil, ton endossement, ta spec, la résolution d’un fil, le vocabulaire. Puis, si ton projet en déclare, ses mots : les douze premiers et leur définition, ceux de SON projet (vocabulaire du projet). Enfin les moments : quatre lignes, une par situation où une IA entre dans Atlas même en suivant un autre skill — une review (la carte d’abord, un fil par finding, la conclusion dans le fil de feature), une réponse à des fils (dans le fil, jamais un fil neuf), un début de feature, une relecture du diff.

Ces annonces ne suffisent pas à faire écrire un skill maison dans Atlas : le lien reste ton geste, et Atlas ne sert aucun fragment de consignes à coller.

Ce qu’Atlas ne fait pas

  • Il ne lance aucune IA, et n’en appelle aucune. Pas de clé d’API, pas d’agent, pas d’appel sortant vers un modèle : c’est ta session qui parle.
  • Il ne publie rien tout seul. Aucun outil ne publie : c’est ton clic, dans le panneau Code, et une note publiée ne se supprime pas.
  • Il n’écrit ni ton code ni ta spec à ta place sans que tu le demandes. /atlas:resolve est le seul skill qui touche tes repos, /atlas:ticket le seul qui écrit ticket.md — après ton accord —, et aucun des deux ne part si personne ne l’a demandé — toi, ou un agent que tu as lancé.
  • Il ne fusionne rien et ne supprime rien : ni branche, ni worktree.
  • Il ne répond pas sur un autre projet que le tien. Si le daemon sert un autre workspace que ta session, tous les outils refusent en nommant les deux chemins plutôt que de répondre à côté.
  • Il n’installe rien dans ton dos : atlas init ne pose pas le plugin, et rien ne met à jour ta session de code sans que tu la redémarres.

Limites connues

  • Hors Claude Code, un skill ne retire plus rien. Gemini CLI et Codex lisent les procédures, pas les champs qui retirent des outils : ce que le skill s’interdit n’y tient que par son texte.
  • Le plugin est copié, pas lu en place. Tant que tu n’as pas relancé atlas plugin install (ou atlas update) et redémarré la session, tu travailles avec la version précédente des skills, sans aucun signal.
  • La session doit être ouverte sous le projet. La remontée part du dossier courant ; la variable d’environnement que mentionne le refus ne change pas la réponse des outils.
  • Une branche sans commit se lit comme mergée : elle pointe sur la base, et le Tableau peut ranger la feature comme rentrée jusqu’au premier commit.
  • Confier le code à ton skill de projet peut échouer, et c’est une limite de ton client, pas d’Atlas : un skill qui ne se déclenche qu’à la main ne s’invoque pas depuis un autre. /atlas:resolve le dit et bascule sur sa méthode générique — à toi de le taper toi-même si tu tiens à ses conventions.
