Brancher l'IA

Atlas ne lance aucune IA : c'est ta session de code qui l'interroge. Cette page dit comment les mettre en présence — installer le plugin, ouvrir la session au bon endroit, lancer un skill, ou brancher les tiens sur Atlas.

Atlas ne lance aucune IA : c’est ta session de code qui l’interroge. Cette page dit comment les mettre en présence — installer le plugin, ouvrir la session au bon endroit, lancer un skill, ou brancher les tiens sur Atlas.

Le principe : chacun apporte sa moitié

Atlas n’embarque ni modèle, ni clé d’API, ni agent. Il expose ce qu’il sait à la session que tu lances toi-même, par deux canaux : un plugin (cinq procédures qu’on déclenche à la main) et un serveur MCP (douze outils que le modèle appelle quand il en a besoin).

Ta session apporte le contexte : le ticket dont vous parlez, la conversation, le droit d’écrire du code. Atlas apporte ce qu’une IA ne sait pas obtenir seule, ou pas correctement :

  • le diff exact d’une feature — le travail d’un ticket, sur une ou plusieurs branches — même quand la branche n’est pas sortie localement, même quand elle est déjà mergée ;
  • la carte : l’arbre des appels, prouvé par les types et non par les noms, à travers les repos — un flux par point d’entrée, suivi jusqu’à ses sorties ;
  • ce que les relecteurs ont endossé (relu et assumé), la note de criticité qu’ils ont posée, les nœuds — une ligne de la carte, un symbole — qu’ils n’ont pas compris ;
  • les fils : les conversations déjà ancrées — posées sur la ligne ou le symbole dont elles parlent — souvent les siennes, d’une session qu’elle ne se rappelle pas ;
  • les précédents : ce qu’un finding passé, sur un nœud du même type, a donné.

Ce qui passe par ces deux canaux — les outils un par un, ce que chacun rend, ce que l’IA a le droit d’écrire et les espaces qu’elle n’atteint jamais — est sur la page suivante, Ce que l’IA lit et écrit.

Installer

atlas plugin           # imprime les deux commandes d'installation, sans rien exécuter
atlas plugin install   # les exécute

atlas plugin install enregistre le marketplace atlas puis installe le plugin atlas@atlas. Il pose deux choses : les cinq skills (/atlas:start-feature, /atlas:as-coded, /atlas:parcours, /atlas:review, /atlas:answer) et la déclaration du serveur MCP, qui se lance par la commande atlas mcp.

La même commande met à jour. Sur un plugin déjà installé, atlas plugin install ne répond pas « déjà installé » : il réinstalle. C’est nécessaire parce que ton client copie le plugin dans son cache au lieu de le lire en place — sans ce geste, tu codes contre des skills périmés. atlas update fait la même chose après avoir installé une nouvelle version d’Atlas (voir Prise en main).

La portée est celle de ta configuration utilisateur, pas celle d’un repo : tu l’installes une fois et les skills sont là dans toutes tes sessions, quel que soit le projet. C’est pour ça qu’atlas init ne l’installe jamais tout seul — poser un plugin touche ta configuration globale.

⚠️ Redémarre ta session de code après l’installation comme après une mise à jour. Les plugins se chargent au démarrage : une session ouverte ne verra ni les nouveaux skills, ni les outils.

Le prérequis qui coince : le plugin ne contient pas Atlas, il déclare comment le joindre — la commande atlas doit être dans le PATH de ta session. Sans elle, le serveur MCP ne démarre pas et aucun outil mcp__atlas__… n’apparaît. Symétriquement, l’installation a besoin de la commande claude : sans elle, elle échoue en nommant la commande qu’elle n’a pas pu lancer et te renvoie vers la même en slash dans une session ouverte (/plugin marketplace add …) ; tu peux pointer un autre binaire par la variable d’environnement ATLAS_CLAUDE_BIN.

Où ouvrir ta session

Le serveur MCP cherche le projet en remontant depuis le dossier courant de la session, exactement comme git remonte jusqu’au .git/. Depuis le chapeau qui héberge tes repos, depuis un repo, depuis un sous-dossier à cinq niveaux : il trouve le même .atlas-workspace/, et Atlas répond la même chose.

Les trois refus que tu peux lire, et ce qu’ils veulent dire :

ce que tu lis ce qui se passe ce que tu fais
aucun .atlas-workspace/ au-dessus du dossier de cette session la session est ouverte hors du projet rouvre-la sous le chapeau ou dans un de ses repos
le daemon sert un AUTRE projet que cette session (les deux chemins sont nommés) Atlas est mono-projet, et le projet actif a basculé bascule de projet, puis rappelle l’outil — voir Configurer un projet
daemon Atlas injoignable sur … le daemon est arrêté atlas start

Cette garde est rejouée à chaque appel d’outil, pas une fois au démarrage : le projet actif peut changer en cours de session, et répondre quand même donnerait une carte plausible et fausse.

Ce que le dossier d’ouverture change n’est donc pas la réponse d’Atlas, c’est ce que ta session a sous la main : au chapeau, tu as tous les repos d’un coup — la bonne position pour relire une feature qui en traverse plusieurs. Pour vérifier où une session se croit, le serveur l’écrit sur sa sortie d’erreur au démarrage :

[atlas mcp] prêt — workspace /…/.atlas-workspace · daemon http://127.0.0.1:3030

Les cinq skills

Un skill est une procédure complète, qu’on lance à la main. Aucun ne se déclenche tout seul : ils écrivent dans la carte, et écrire sans qu’on l’ait demandé est exactement ce qu’on ne veut pas. Les outils, eux, restent disponibles pendant et en dehors des skills.

skill quand le lancer ce qu’il écrit ce qu’il ne touche jamais
/atlas:start-feature avant de coder la déclaration de la feature, des fils d’hypothèse ancrés, le pseudo-code, éventuellement le parcours attendu le code, les branches, une spec déjà remplie
/atlas:as-coded après le code, à la relecture did et does sur les nœuds, plus les doutes le code, ton endossement, la spec, le parcours
/atlas:parcours après as-coded, ou seul les étapes du flux et sa lecture des critères d’acceptation tout le reste
/atlas:review à la relecture, en parallèle d’as-coded des fils de findings ancrés ligne à ligne, et la conclusion dans le fil de feature le code, ton endossement, la spec, les autres fichiers
/atlas:answer quand des fils ou des ? attendent des réponses dans les fils existants, et des fils neufs là où on lui demande d’expliquer le code, la résolution d’un fil

/atlas:start-feature lit la spec locale (ticket.md) et l’importe de Jira une seule fois si elle est absente ou vierge, trace le flux réel dans le code, puis pose quelques hypothèses là où elles tombent : un fil ancré sur chaque symbole existant qui va bouger, un nœud en pointillé pour ce qui reste à écrire. Il n’amorce qu’une conversation, il ne rend pas un plan fini.

/atlas:as-coded ne réécrit jamais une intention posée pendant le codage : quand le code la contredit, l’écart reste visible à l’écran, et c’est toi qui tranches. /atlas:parcours raconte le voyage de la donnée en 3 à 8 étapes cliquables, et écrit son évaluation des critères, jamais les critères eux-mêmes.

/atlas:review juge : correctness, robustesse, sécurité, cohérence entre services, superflu. Ses findings arrivent là où on lit, en fils ancrés à la ligne, jamais en rapport à côté — et il ne publie rien. Sa conclusion, elle, va dans le fil de feature : l’unique conversation posée sur la feature entière, et non sur un symbole (Ticket, fils et Journal). /atlas:answer répond aux fils dont le dernier message est de toi, explique les nœuds marqués ?, ouvre un fil sur les nœuds notés 4 qui n’en ont aucun, et ne résout jamais rien : un fil se clôt à la main.

Entre les skills, il y a un moment sans skill : pendant que vous codez, l’IA appelle les outils au fil de l’eau — intent (le titre métier d’un nœud), goal (le pourquoi), unsure (le doute), un fil sur un piège repéré. C’est ce moment-là qui rend la relecture utile : intent et does écrits par la même lecture s’accordent toujours et n’apprennent rien ; écrits à deux moments, leur écart est précisément ce qu’Atlas montre.

Le serveur MCP

atlas mcp est un serveur stdio : il n’écoute aucun port, c’est ton client qui le lance au démarrage de la session et lui parle par son entrée standard. Tu ne le tapes jamais à la main.

Il ne calcule rien : il traduit des questions en appels au daemon, qui reste seul à lire git et le code. Il démarre le daemon au lancement si la session est sous un projet Atlas — une session ouverte ailleurs n’allume rien chez toi. Une erreur d’outil revient en texte lisible dans la réponse, pour que le modèle puisse corriger son appel. Les outils apparaissent dans ta session sous la forme mcp__atlas__<nom> : mcp__atlas__digest, mcp__atlas__comment, etc.

Servir tes propres skills : atlas guide

Si tu as déjà un skill de review maison, tu ne veux pas le remplacer par /atlas:review : tu veux qu’il agisse avec Atlas — lire la carte avant le code, poser un fil par finding, conclure dans le fil de feature — en gardant ses propres checks. C’est ce que sert atlas guide : le fragment de consignes d’un moment d’Atlas, à injecter dans ton skill, sans rien recopier et sans composer des skills entre eux.

atlas guide           # la liste des moments servis, un par ligne, avec son résumé
atlas guide review    # le fragment du moment « review », sur la sortie standard
atlas guide answer    # celui du moment « réponse aux fils »

Deux moments sont servis aujourd’hui : review (« comment LIRE Atlas et y ÉCRIRE pendant une review — jamais comment reviewer : tes checks restent les tiens ») et answer (« comment LIRE ce qui attend une réponse dans Atlas et y RÉPONDRE, quel que soit le skill qui te fait répondre »). Un moment inconnu est refusé en nommant ceux qui existent ; la commande sans argument fait foi.

Le texte n’est pas écrit deux fois : il est extrait du skill Atlas du même moment. Il n’y a donc qu’un seul propriétaire de la règle, et le skill d’Atlas reste autonome — rien ne lui est injecté.

La ligne à écrire dans ton skill, telle quelle, dans sa section de process :

!`atlas guide review`

Ton client exécute la commande au chargement du skill et colle le fragment dans le prompt. Le fragment commence par un titre-témoin — # Agir avec Atlas — review — pour que ton skill puisse dire « Atlas n’est pas là » plutôt que de faire semblant.

C’est cette ligne qui fait le travail, pas le serveur MCP seul : mesuré, un skill maison qui déroule ses propres checks, avec le serveur branché mais sans cette ligne, n’a posté aucun fil. Le serveur annonce les moments ; la ligne fait entrer dedans.

L’outil MCP guide rend exactement le même texte, sans passer par le shell — pour une IA qui entre dans le moment en cours de route. Différence : l’outil est soumis à la même garde que les autres (daemon joignable, projet de la session), tandis que la commande lit le paquet installé et répond même daemon arrêté.

Ce qu’Atlas ne fait pas

  • Il ne lance aucune IA, et n’en appelle aucune. Pas de clé d’API, pas d’agent, pas d’appel sortant vers un modèle : c’est ta session qui parle.
  • Il ne publie rien tout seul. Aucun skill n’a le droit de publier ; l’outil ne s’appelle que sur ta demande explicite, et une note publiée ne se supprime pas.
  • Il ne répond pas sur un autre projet que le tien. Si le daemon sert un autre workspace que ta session, tous les outils refusent en nommant les deux chemins plutôt que de répondre à côté.
  • Il n’installe rien dans ton dos : atlas init ne pose pas le plugin, et rien ne met à jour ta session de code sans que tu la redémarres.

Limites connues

  • Les skills ne sont pas portables, le serveur MCP l’est. Un autre client MCP consomme les douze outils tels quels ; les cinq procédures, elles, sont au format de Claude Code.
  • Le plugin est copié, pas lu en place. Tant que tu n’as pas relancé atlas plugin install (ou atlas update) et redémarré la session, tu travailles avec la version précédente des skills, sans aucun signal.
  • La session doit être ouverte sous le projet. La remontée part du dossier courant ; la variable d’environnement que mentionne le refus ne change pas la réponse des outils.
