Le Harnais

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s'appliquent — et ce qu'Atlas lui garde fermé.

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s’appliquent — et ce qu’Atlas lui garde fermé.

Une consigne est une règle de ton projet attachée à l’endroit où elle s’applique — un fichier, un dossier, une sorte de fichier, un repo, une stack, une commande. Le Harnais la sert à l’IA de ta session de code quand elle touche cet endroit, au lieu d’un long document lu au démarrage et oublié en route ; il sert de même les critères de tes tickets. Ce n’est ni une décision métier, qui revient par son contrat (Les décisions métier), ni un précédent, un fait passé servi comme une piste (Les précédents) : c’est une décision du projet, servie avec autorité.

Ce qu’est une consigne

Une consigne tient en une phrase qu’on peut coller dans une conversation, suivie de son pourquoi. Deux clés la rangent :

clé valeurs ce qu’elle dit
côté code · produit code : comment on construit ici. produit : ce que le produit garantit à qui s’en sert — une règle métier
nature éviter · faire · pourquoi · vérifier · métier les quatre premières pour le code ; métier, et elle seule, pour le produit

L’endroit : une ou plusieurs lignes où, chacune <sorte> <valeur>. Sept sortes sont servies :

tu écris ce que ça désigne
fichier projet-api/src/paiement/paiement.service.ts ce fichier : le repo membre, puis le chemin dans le repo
dossier projet-api/src/paiement tout fichier dessous, à la frontière d’un dossier : src/paiement ne couvre pas src/paiement2
famille migration tout fichier que les règles de nom de tes stacks et de project.json rangent dans cette famille
couche ctrl tout fichier dont le chemin prouve la couche ; sinon rien, et le geste compte « non garanti », à part
service projet-api tout fichier de ce repo membre
stack nest tout fichier d’un repo où elle est prouvée ou déclarée
geste git commit une commande que l’IA lance : ses mots entiers, dans l’ordre, options sautées

Un service ou une stack inconnu du projet est refusé, les noms existants dits. Quatre autres sortes se lisent sans être servies : symbole ou contrat projet-api::src/x.ts::Nom, une entrée (entrée POST /api/remboursements), un mot du vocabulaire du projet (mot panier). L’IA les lit à la demande, par l’outil harnais (Ce que l’IA lit et écrit).

geste git commit touche git -C . commit -m "…" comme cd projet-api && git commit, jamais git commit-tree ni git log --grep commit. Un worktree posé hors du chapeau compte comme son repo principal.

Une consigne sans ligne où est du tronc commun : elle vaut partout, et l’IA la reçoit à l’ouverture de chaque session, pas à un endroit (plus bas).

Écrire une consigne

Chaque consigne est un fichier Markdown, .atlas-workspace/consignes/<id>.md, dont le nom est l’identifiant : minuscules, chiffres et tirets, 64 caractères au plus. Le dossier vit dans le workspace et se partage avec lui (Configurer un projet). Par exemple migration-avec-down.md :

# Une migration s'écrit avec son retour arrière : jamais de down vide.
- côté: code
- nature: éviter
- où: famille migration
- où: dossier projet-api/src/migrations
- ticket: PROJ-380
- source: PROJ-380::t3a9c2f10

## Pourquoi
Un down vide a bloqué un retour arrière en production.
ligne ce qu’elle porte
# … (obligatoire) la consigne, 120 caractères au plus
- côté: · - nature: (obligatoires) voir plus haut ; produit va avec métier, et réciproquement
- sous: une précision libre : forme écartée, modèle à suivre, choix en attente, décision
- où: (répétable) un endroit ; aucun = tronc commun
- ticket: le ticket qui l’a fait naître
- source: (répétable) le fil qui la fonde, par sa clé <feature>::<fil> ; active, elle prend la place de ce précédent dans ses fichiers et dossiers (Les précédents)
## Pourquoi ce que la règle évite, ce qui a coûté
## Règle une règle métier en table Markdown : une ligne d’en-tête, puis une ligne par cas

Avant les sections, seules des lignes - clé: valeur. Un seul refus, et rien n’est lu : clé inconnue ou en double, autre section que Pourquoi ou Règle, endroit mal formé, source qui n’est pas une clé de fil, table illisible, phrase trop longue. Refusée, elle n’est servie à personne ; atlas consigne liste la montre précédée de ⚠, avec chaque raison.

⚠️ Le fichier porte le contenu, jamais la provenance. Une ligne - statut:, - origine:, - adoptee:, - confirmee: ou - invalidee: est refusée : « la provenance (statut, origine, adoption, confirmation) ne s’écrit pas dans le fichier : Atlas la pose au geste ».

Ce que l’IA reçoit, et quand

Le service passe par un hook : une commande que Claude Code lance juste avant que l’IA lise un fichier, l’écrive ou lance une commande. Celui d’Atlas, atlas consigne --hook, vient avec le plugin : rien à configurer au-delà d’atlas plugin install et d’un redémarrage de ta session (Brancher l’IA). Il demande à l’instance de ton projet quoi servir.

La première fois que l’IA touche un endroit dans une session, elle reçoit ses consignes, et ses critères (Les critères, les cas et leur preuve) :

ce que fait l’IA ce que fait le hook
elle lit un fichier — par l’éditeur, ou par une commande qui le nomme il ajoute les consignes à ce qu’elle lit ; l’outil passe
elle écrit un fichier dont elle n’a encore reçu aucune consigne dans la session il refuse l’écriture une fois, consignes jointes au refus ; la tentative suivante passe
elle lance une commande qu’une consigne geste désigne il ajoute la consigne ; la commande passe

Pourquoi refuser : ce qui est ajouté arrive après le geste — à temps sur une lecture, trop tard sur une écriture à l’aveugle. Une commande qui n’écrit aucun fichier (git commit) n’est jamais refusée.

Une écriture par le shell compte comme une écriture par l’éditeur quand Atlas sait lire ce qu’elle vise : une redirection (>, >>), tee, sed -i, perl -i, mv, cp, rm, touch, truncate, install, git restore, git checkout -- … — sur un fichier nommé par un chemin ou un nom à extension.

Le texte reçu commence par « Consignes du projet pour cet endroit — à appliquer avant d’écrire : », puis, par élément, sa phrase et, entre parenthèses, l’endroit qui l’a fait arriver (ce fichier (…), toute migration…), d’où il vient — consigne adoptée par alice, le 2026-10-09, consigne écrite par l'IA de la session de carol (review), le 2026-10-09, ticket PROJ-412, consigne écrite hors d'Atlas, sans geste, critère PROJ-412#3 · codé (relu par as-coded, le …) — et la première ligne de son Pourquoi, jamais la table. Un refus finit par « Cette écriture est refusée une fois pour que tu les lises : réessaie en les appliquant. »

Ce qui règle le choix :

  • une fois par endroit et par session : une consigne de dossier ne revient pas à chaque fichier touché dedans, mais par un autre de ses endroits, dans une nouvelle session, après un redémarrage de l’instance ou douze heures sans aucun geste ;
  • la plus précise d’abord : un fichier ou une commande, puis un dossier, le plus profond d’abord, puis une famille, une couche, un service, une stack ; à précision égale, ce qui vient d’un humain — adopté, confirmé, ou écrit à la main —, puis le produit, puis l’identifiant : ce que l’IA écrit ne chasse jamais les tiennes du plafond ;
  • cinq consignes et trois critères ou cas de recette au plus par geste, deux plafonds séparés. Au-delà, le texte le dit — « … et 2 autres au-delà du plafond, non servies. » — et ils comptent comme vus : une écriture n’est refusée qu’une fois.

Ce que ça coûte. Le hook tourne dans toutes tes sessions Claude Code avec le plugin, même hors projet. Mesuré le 09-10 : 43 ms par geste hors projet, 52 ms sans instance, 60 ms avec ; lire les critères ajoute 87 ms au premier geste de l’instance, puis 13 à 19 ms. Il ne bloque jamais : hors projet, sans instance, sur une réponse illisible ou de plus d’1,5 s, l’outil passe ; ce qui arrive trop tard ne compte pas, et revient au prochain geste au même endroit. Il ne démarre aucune instance : atlas, atlas start ou le serveur MCP, si.

Le tronc commun arrive autrement : à l’ouverture de la session. Le hook ne le sert jamais ; le serveur MCP le joint à ses instructions quand ta session démarre, quel que soit le client — Claude Code, Gemini CLI, Codex (Brancher l’IA). En font partie les consignes actives sans endroit, dans l’ordre du plafond — ce qu’un humain a adopté ou confirmé, puis le produit, puis l’identifiant :

LES CONSIGNES DU PROJET (tronc commun) — valables partout, sans endroit : applique-les sans attendre qu'un fichier te les rappelle.
· Trois états, jamais deux : oui · non · pas pu regarder. (consigne adoptée par alice, le 2026-10-09)

Trois états : dix consignes au plus — au-delà, « … et 3 autres, au-delà du plafond de 10 : atlas consigne liste les montre. » ; rien s’il n’y en a aucune, ou hors d’un projet Atlas ; « pas pu les lire (…) », avec la raison, quand l’instance ne répond pas à temps ou sert un autre projet. La liste en dit le poids : tronc commun : servi à chaque ouverture de session, ≈ 41 tokens (estimés sur la taille du texte).

La vie d’une consigne, gardée

Chaque geste dont la réponse du hook arrive à temps s’enregistre : c’est la vie d’une consigne — servie combien de fois, la première et la dernière, et combien de fois reprise après un refus : une écriture refusée, consignes jointes, puis réécrite au même fichier dans la même session. À l’ouverture d’une session, seul compte ce que le serveur MCP a vraiment servi du tronc commun, dix au plus. Chaque session aussi, les 200 dernières par poste : ses gestes, son poids servi estimé, ses refus, ses reprises.

L’instance la tient en mémoire, sans retarder le hook, et l’écrit au plus toutes les dix minutes et quand elle s’arrête, dans son casier de vie : .atlas-workspace/consignes/vie/<ton adresse git>.<machine>.json, partagé avec le workspace, jamais écrit par l’IA — la même adresse sur deux machines fait deux postes, additionnés. La page Harnais lit la mémoire de ton instance et le disque des autres postes.

Sans identité git, ton poste ne garde rien et la page ne lit la vie d’aucun poste : elle le dit parmi les illisibles, avec la commande à lancer — puis atlas restart. Un casier illisible n’est jamais écrasé : le tien, ton poste n’y note rien et la page ne mesure plus la vie jusqu’à ce qu’il soit réparé ou retiré ; celui d’un autre poste compte parmi les illisibles. Une écriture ratée se dit sur la page.

Servie d’office, à regarder, invalidée

Toute consigne qui se lit est servie dès qu’elle existe, que l’IA l’ait écrite par son outil ou toi à la main, sans aucun geste. Elle reste à regarder tant qu’aucun humain ne l’a adoptée ou confirmée ; seule une invalidée n’est plus servie.

geste par où à quelle condition
l’IA écrit l’outil consigne, geste ecrire ; Atlas écrit le fichier un identifiant libre (tiré de la phrase s’il manque), son ticket, ni la phrase d’une invalidée, ni une phrase qui vit déjà là
l’IA écarte l’outil consigne, geste ecarter une consigne servie qu’elle n’applique pas ici, avec sa raison — c’est ce que tu relis
tu confirmes atlas consigne confirmer <id> une consigne servie : tu gardes la version servie, elle n’est plus à regarder
tu adoptes atlas consigne adopter <id> une invalidée, ou une retouchée depuis son adoption : le fichier tel qu’il est, s’il se lit
tu invalides atlas consigne invalider <id> <la raison> une raison écrite, toujours

Le ticket d’une consigne que l’IA écrit : celui qu’elle donne, sinon celui de son fait, le fil qui la fonde — jamais d’une source, qui peut venir d’une autre feature —, une feature déclarée du projet. Sans aucun, rien n’est écrit. Depuis un fil sans où non plus : la réponse liste les endroits du nœud, ou « tronc commun ».

Le doublon : la même phrase — casse, accents et blancs mis à part — au même endroit est refusée, qu’y vive une consigne, un critère, un cas ou une décision ; le tronc commun est un endroit. Refusée ainsi ou écrite, la réponse dit ce qui vit déjà à ses endroits, dix lignes au plus : Atlas compare des phrases, pas des sens, et une règle reformulée se voit là.

Le fait, facultatif : la clé du fil qui la fonde. Atlas le vérifie — un humain y a répondu, ou le code a bougé depuis — et le garde dans sa provenance ; faux ou invérifiable, tout est refusé, avec pourquoi.

L’IA ne peut jamais modifier, adopter, confirmer ni invalider une consigne : aucun outil n’y mène, et la porte lui ferme le dossier. Toi, tu peux réadopter une invalidée.

Chaque geste laisse un cachet, posé par Atlas : qui (l’adresse de git config user.email dans le chapeau), quand, sur quelle version du texte, la raison d’un écart ou d’une invalidation — jamais ce que l’appelant prétend. Les cachets vivent dans .atlas-workspace/consignes/cachets/, un fichier par auteur, jamais réécrits : le statut se déduit de leur suite. Sans identité git, aucun geste n’est posé, et rien n’est écrit. Un cachet contraire à ces règles ne compte pas : la liste dit ⚠ geste ignoré, et pourquoi.

Un geste retient son texte — l’écriture de l’IA, ton adoption, ta confirmation : si le fichier est retouché ensuite, même au point de ne plus se lire, ce texte reste servi, et la liste prévient : « ⚠ retouchée depuis son adoption : la version adoptée est servie ». adopter sert la nouvelle, confirmer garde celle en vigueur. Sans aucun geste, c’est le fichier qui est servi.

atlas consigne liste (ou atlas consigne) se lit partout, même depuis un script : pour chaque consigne, ● active ou ✗ invalidée, son identifiant, sa phrase ; dessous, à regarder : … servie d'office et la commande qui tranche, qui l’a adoptée — alice (IA), le 2026-10-09 quand l’IA de la session d’alice l’a écrite — et sur quel fait, l’invalidation et sa raison, les écarts de l’IA. Puis les illisibles, les décisions métier, le poids du tronc commun et les critères (Les critères, les cas et leur preuve).

Les trois gestes exigent un terminal : lancés par l’IA ou un script, refusés — « « atlas consigne invalider » est un geste de l’humain : il se lance dans un terminal. » Un geste qui ne changerait rien est dit, pas posé : adopter une consigne servie telle quelle (le refus dit de la confirmer), confirmer une invalidée ou ce qu’un humain a déjà confirmé, invalider deux fois. Aucun ne s’applique à un critère. La page Harnais les fait aussi, d’un clic.

Les critères, les cas et les décisions

Le Harnais sert aussi les critères de tes tickets et les cas de ton scénario de recette, et compte les décisions métier : Les critères, les cas et leur preuve.

La porte du workspace

Atlas tient lui-même une partie de .atlas-workspace/ : il y date, signe et met en forme ce qu’il écrit. La porte refuse à l’IA toute écriture à la main sur ces chemins, par l’éditeur comme par le shell, et lui dit par où passer :

sous .atlas-workspace/ par où l’IA passe
features/<id>/feature.json l’outil declare
les annotations, les fils, le parcours, le plan d’une feature les outils annotate, comment, parcours, plan
precedents/ l’outil sonde
consignes/, cachets compris l’outil consigne
la curation d’une feature (tes endossements) aucun outil : c’est ton geste
les recettes, le scénario de recette, socle/ la commande atlas recette (La recette)
project.json aucun outil : Config › Projet, ou ta main

Le refus commence par « Atlas tient lui-même .atlas-workspace/… » et nomme ce que le chemin contient ; il revient à chaque fois. Effacer ou déplacer un dossier qui contient ces fichiers, celui d’une feature par exemple, est refusé aussi.

Restent ouverts : la spec, ticket.md, que le skill ticket écrit dans ta session ; ce que la porte ne nomme pas (un POC dans le dossier d’une feature, une stack maison) ; lire tout fichier du workspace ; écrire ailleurs à partir de l’un d’eux. Jugée sur le chemin seul, elle tient même sans instance démarrée. Elle ne concerne que l’IA ; toi, tu écris où tu veux.

Le skill d’une écriture

Chaque écriture de l’IA dit de quel skill elle vient, par son champ skill : l’un des six moments — ticket, resolve, review, resolve-review, as-coded, recette —, answer quand elle répond à un fil, ou aucun hors de tout skill.

Il est exigé par comment, annotate, parcours et consigne : sans lui, ou inconnu, l’écriture est refusée, la liste donnée. N’en demandent pas : ranger un fil, marquer une décision remplacée, une annotation qui ne touche que la structure de la carte. Un message qui signe un moment porte ce moment d’office ; un skill contraire est refusé. Les sept skills d’Atlas passent le leur ; le serveur MCP l’annonce à chaque ouverture.

C’est lui qui rend un critère codé, et la provenance d’une consigne, d’un critère ou d’un précédent le dit, à l’IA comme sur la page Harnais : « (review) », « moment inconnu » s’il n’a pas été dit, « hors moment » pour aucun.

⚠️ Après une mise à jour d’Atlas, redémarre ta session de code. Une session ouverte avant garde l’outil d’avant, qui ne transmet pas ce champ : toutes ses écritures sont refusées, et le refus finit par « redémarre-la ». Son outil consigne dit encore proposer : Atlas écrit, et la réponse donne le nom d’aujourd’hui, ecrire ; adopter est refusé.

Ce qu’Atlas ne fait pas

  • Il ne vérifie pas que le code respecte une consigne : il la sert au bon moment, il ne remplace ni un test ni la CI ; une reprise après un refus ne dit pas qu’elle a été suivie.
  • Il n’approuve rien à ta place : le hook ajoute ou refuse, il n’autorise jamais un outil — les demandes de permission de Claude Code restent les tiennes.
  • Il ne recopie ni ne réécrit un critère : il le relit dans ticket.md, qui reste à toi.
  • Il ne fond pas consignes et précédents, et ne partage aucune consigne entre projets.

Limites connues

  • Le hook n’existe que dans Claude Code, avec le plugin : Gemini CLI et Codex, ou un serveur MCP déclaré à la main, n’ont ni service à l’endroit ni porte, et rien ne le signale ; seuls le tronc commun et ce que leur IA demande par l’outil harnais leur arrivent, par le serveur MCP.
  • Une commande qui écrit sans dire où n’est pas vue — un script qui ouvre un fichier, patch, git apply : ni consigne ni porte ; Atlas compte ces gestes — la part « gestes non garantis » de la page Harnais —, sans dire lesquels.
  • Les outils de recherche de Claude Code ne déclenchent rien : seuls la lecture, l’écriture et le shell passent par le hook.
  • Le terminal n’est pas une authentification : l’instance ne vérifie pas qui l’appelle — une porte qu’une IA ne prend pas par mégarde, pas une serrure.
  • Un casier de cachets illisible perd ses invalidations : la consigne repart servie, et le hook le dit — « non garanti », dans ce que l’IA reçoit.
  • Le coût n’est mesuré qu’en partie : les 60 ms ne comptent pas le temps que met l’instance à choisir les consignes.
  • Le tronc commun n’arrive qu’à l’ouverture : une session longue ne le reçoit pas une seconde fois, même après une écriture ou une confirmation.
