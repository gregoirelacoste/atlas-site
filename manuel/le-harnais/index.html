Le Harnais

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s'appliquent — et ce qu'Atlas lui garde fermé.

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s’appliquent — et ce qu’Atlas lui garde fermé.

Une consigne est une règle de ton projet, attachée à un endroit. Le Harnais la sert à l’IA quand elle y travaille, comme les critères de tes tickets. Elle fait autorité ; les décisions métier reviennent par leur contrat, les précédents comme des pistes.

Ce qu’est une consigne

Une consigne tient en une phrase qu’on peut coller dans une conversation, suivie de son pourquoi. Deux clés la rangent :

clé valeurs ce qu’elle dit
côté code · produit code : comment on construit ici. produit : ce que le produit garantit à qui s’en sert — une règle métier
nature éviter · faire · pourquoi · vérifier · métier éviter, faire, métier : une règle (son pourquoi est exigé quand l’IA l’écrit) ; vérifier ; pourquoi : une explication, technique côté code, métier côté produit

L’endroit : une ou plusieurs lignes où, chacune <sorte> <valeur>. Huit sortes sont servies :

tu écris ce que ça désigne
fichier projet-api/src/paiement/paiement.service.ts ce fichier : le repo membre, puis le chemin dans le repo
dossier projet-api/src/paiement tout fichier dessous, à la frontière d’un dossier : src/paiement ne couvre pas src/paiement2
symbole projet-api::src/x.ts::Nom ce symbole, quand l’IA touche son fichier
famille migration tout fichier que les règles de nom de tes stacks et de project.json rangent dans cette famille
couche ctrl tout fichier dont le chemin prouve la couche ; sinon rien, et le geste compte « non garanti », à part
service projet-api tout fichier de ce repo membre
stack nest tout fichier d’un repo où elle est prouvée ou déclarée
geste git commit une commande que l’IA lance : ses mots entiers, dans l’ordre, options sautées

Un service ou une stack inconnu est refusé, noms existants dits. Trois autres se lisent sans être servies : contrat projet-api::src/x.ts::Nom, une entrée (entrée POST /api/remboursements), un mot du vocabulaire du projet (mot panier). L’IA les lit par l’outil harnais (Ce que l’IA lit et écrit).

geste git commit touche git -C . commit, jamais git commit-tree. Un worktree hors du chapeau compte comme son repo principal.

Une consigne sans ligne où est du tronc commun : elle vaut partout, et l’IA la reçoit à l’ouverture de chaque session, pas à un endroit (plus bas).

Écrire une consigne

Chaque consigne est un fichier Markdown, .atlas-workspace/consignes/<id>.md, dont le nom est l’identifiant : minuscules, chiffres et tirets, 64 caractères au plus. Le dossier se partage avec le workspace (Configurer un projet). Exemple, migration-avec-down.md :

# Une migration s'écrit avec son retour arrière : jamais de down vide.
- côté: code
- nature: éviter
- où: famille migration
- où: dossier projet-api/src/migrations
- ticket: PROJ-380
- source: PROJ-380::t3a9c2f10

## Pourquoi
Un down vide a bloqué un retour arrière en production.
ligne ce qu’elle porte
# … (obligatoire) la consigne, 120 caractères au plus
- côté: · - nature: (obligatoires) voir plus haut ; produit va avec métier ou pourquoi
- sous: une précision libre : forme écartée, modèle à suivre, choix en attente, décision
- où: (répétable) un endroit ; aucun = tronc commun
- ticket: le ticket qui l’a fait naître
- source: (répétable) le fil qui la fonde, par sa clé <feature>::<fil> ; active, elle prend la place de ce précédent dans ses fichiers et dossiers (Les précédents)
## Pourquoi ce que la règle évite, ce qui a coûté
## Règle une règle métier en table Markdown : une ligne d’en-tête, puis une ligne par cas

Avant les sections, seules des lignes - clé: valeur. Un seul refus, et rien n’est lu : clé inconnue ou en double, autre section que Pourquoi ou Règle, endroit mal formé, source qui n’est pas une clé de fil, table illisible, phrase trop longue, caractère invisible, ligne nommée. Refusée, elle n’est servie à personne ; atlas consigne liste la montre précédée de ⚠.

⚠️ Le fichier porte le contenu, jamais la provenance. Une ligne - statut:, - origine:, - adoptee:, - confirmee: ou - invalidee: est refusée : « la provenance (statut, origine, modification, invalidation) ne s’écrit pas dans le fichier : Atlas la pose au geste ».

Ce que l’IA reçoit, et quand

Le service automatique passe par un hook, lancé autour d’une lecture, d’une écriture ou d’une commande de Claude Code. atlas consigne --hook vient avec le plugin, installé par atlas plugin install (Brancher l’IA). Il demande à l’instance de ton projet quoi servir.

La reconnaissance lui dit ses limites de langage, capacité et manifeste : une stack non établie ne devient pas « absente ».

Quand l’IA touche un endroit, elle reçoit ses consignes, et ses critères (Les critères, les cas et leur preuve) :

ce que fait l’IA ce que fait le hook
elle lit un fichier — par l’éditeur, ou par une commande qui le nomme il ajoute les consignes à ce qu’elle lit ; l’outil passe
elle écrit un fichier où une règle s’applique il refuse l’écriture une fois, la règle en entier même déjà reçue à la lecture ; le reste s’ajoute sans refuser
elle lance une commande qu’une consigne geste désigne il ajoute la consigne ; la commande passe

Une règle refuse parce que l’ajout arrive après le geste. La tentative suivante passe ; une commande qui n’écrit rien n’est jamais refusée. Un refus vaut pour un lecteur : la session et son agent (le fil principal, ou un agent d’aide).

Une écriture par le shell compte comme une écriture par l’éditeur quand Atlas sait lire ce qu’elle vise : une redirection, tee, sed -i, mv, cp, rm… — sur un fichier nommé par un chemin ou un nom à extension.

Le texte reçu a un bloc par famille, sous ses mots (« Règle … — à appliquer », « Garde … — à vérifier après ton changement »…) ; puis, par élément, sa phrase et, entre parenthèses, l’endroit qui l’a fait arriver, d’où il vient — consigne adoptée par alice le 09-10, critère PROJ-412#3 · relu par as-coded le … — et la première ligne de son Pourquoi, jamais la table.

Ce qui règle le choix :

  • une fois par lecteur et par époque : un texte déjà envoyé revient en rappel d’une ligne — sa clé, le début de sa phrase, depuis quand, le fichier qui le fait revenir —, entier après un compactage ou une nouvelle session ; sans départ de session vu, tout revient entier ;
  • la plus précise d’abord : un fichier ou une commande, puis un dossier (le plus profond d’abord), une famille, une couche, un service, une stack ; à précision égale, ce qui vient d’un humain, puis le produit, puis l’identifiant : ce que l’IA écrit ne chasse jamais les tiennes du plafond ;
  • cinq consignes et trois critères ou cas de recette au plus par geste, deux plafonds séparés. Au-delà, le texte le dit — « … et 2 autres au-delà du plafond, non servies. » — et ils ne comptent jamais comme envoyés.

Ce que ça coûte. Le hook tourne dans toutes tes sessions Claude Code, même hors projet. 32 à 40 ms par geste (14-10) ; après une commande du terminal, un processus de plus (~50 ms, 28-10), qui ne lit rien sauf après un test en échec ou un git restore. Il ne bloque jamais : hors projet, sans instance, sur une réponse illisible ou de plus d’1,5 s, l’outil passe ; ce qui arrive trop tard revient au prochain geste au même endroit. Il ne démarre aucune instance : atlas, atlas start ou le serveur MCP, si.

Le tronc commun arrive à l’ouverture de la session, par le serveur MCP, quel que soit le client (Brancher l’IA). En font partie les consignes actives sans endroit, sous le titre « LES CONSIGNES DU PROJET (tronc commun) », chacune suivie de sa provenance.

Dix consignes au plus — au-delà, « … et 3 autres, au-delà du plafond de 10 » ; rien sans consigne ou hors d’un projet Atlas ; « pas pu les lire (…) » et sa raison si l’instance ne répond pas. La liste en dit le poids, estimé.

La vie d’une consigne, gardée

Le journal de ton poste garde ce que le hook, le prologue et l’ouverture envoient ; quand la réponse part, le casier partagé en reçoit la projection : la vie d’une consigne (comptes, premier et dernier service), les 200 dernières sessions vues (gestes, poids, refus), une ligne par lecteur, élément et fichier. La reprise après un refus ne se compte plus depuis le 19-10.

L’instance l’écrit toutes les dix minutes au plus, et à l’arrêt : .atlas-workspace/consignes/vie/<ton adresse git>.<machine>.json. Deux machines font deux postes, additionnés. La page Harnais lit la mémoire locale et le disque partagé des autres. Les autres canaux y écrivent leur trace eux-mêmes (Les critères, les cas et leur preuve).

Sans identité git, ton poste ne garde rien, et la page le dit avec la commande à lancer — puis atlas restart. Un casier illisible n’est jamais écrasé : ton poste n’y note rien jusqu’à réparation ; celui d’un autre poste compte parmi les illisibles.

Servie d’office, modifiée, invalidée

Toute consigne qui se lit est servie dès qu’elle existe, que l’IA l’ait écrite par son outil ou toi à la main. Rien n’attend un geste de toi : ni confirmer, ni adopter. Le seul geste qui te reste : demander à l’IA de modifier ou d’invalider une ligne (/atlas:harnais), ou l’invalider toi-même.

Trois états, dits par leur cause : en vigueur, mis en doute, retiré — déduits des cachets et de l’index. Mise en doute, elle reste servie, avec sa cause : son ancre a changé, ou deux sessions IA l’ont déclarée perime ou contredit-code. Retirée — invalidée, son lieu disparu, sa source coupée, ses citations de code éteintes —, elle n’est plus servie mais reste lisible, avec sa raison et sa source. Écartée hors-sujet à un fichier par deux sessions, elle n’y est plus servie, ailleurs si. Modifiée à ta demande, elle repart en vigueur, et la modification devient la cause. Le code se relit au build de l’index ; avant, « code pas regardé ».

geste par où à quelle condition
l’IA écrit l’outil consigne, geste ecrire ; Atlas écrit le fichier une source qui se retrouve (ci-dessous), une raison pour une règle ou une vérification, ni la phrase d’une invalidée, ni une phrase qui vit déjà là, ni un identifiant pris
l’IA modifie l’outil consigne, geste modifier à ta demande ; ce qu’elle tait se garde, ses sources aussi ; la version d’avant reste lisible sur la page
l’IA invalide l’outil consigne, geste invalider à ta demande, avec sa raison : une consigne, une piste de l’amorçage (mise de côté), un précédent à un nœud
l’IA écarte l’outil sonde, ecarte par sa clé, une raison parmi quatre (hors sujet · déjà su · périmé · contredit par le code) ; ref dit où s’il y a été servi, sinon le dernier fichier servi ; sans lieu, rien ne se retire
tu invalides atlas consigne invalider <id> <la raison>, ou la page une raison écrite, toujours

À ta demande veut dire : tu as lancé /atlas:harnais dans cette session, ou répondu au skill que l’IA y a lancé, il y a moins d’une demi-heure (le hook UserPromptSubmit le prouve). Sinon, l’outil refuse de modifier ou d’invalider, et le dit — toujours sans ce hook (Gemini CLI, Codex). La ligne dit alors « l’IA (harnais), à la demande de X le JJ-MM », jamais « confirmée ». Un critère, un cas, une décision ne s’invalident pas ainsi : le refus dit où ils se corrigent.

La source d’une consigne que l’IA écrit porte un signal : un fil où un humain a répondu, ou dont le code a bougé depuis (fait, vérifié), des fils où un humain a parlé (sources), des lignes entières (citations) d’un message humain, d’une spec réécrite ou d’un écart de recette, retrouvées à leur version, ou ta demande. Du code cité l’accompagne, jamais seul. Sinon rien n’est écrit, et le refus dit quoi citer ; un ticket seul n’en est pas une. Depuis un fil sans où, rien non plus : la réponse liste les endroits du nœud, ou « tronc commun ». Toutes ses citations de code éteintes au build de l’index, elle n’est plus servie ; sans elles, elle suit son lieu. « Pas pu regarder » ne retire rien.

Le doublon : même phrase au même endroit (casse, accents et blancs mis à part) face à une consigne, un critère, un cas ou une décision, refusée.

Chaque geste laisse un cachet, posé par Atlas : qui (son user.email git), quand, si tu l’as demandé, sur quelle version du texte, la raison d’un écart ou d’une invalidation, et la session de l’IA qui écarte — jamais ce que l’appelant prétend. Les cachets vivent dans .atlas-workspace/consignes/cachets/, un fichier par auteur, jamais réécrits : le statut se déduit de leur suite. Sans identité git, aucun geste. Un cachet contraire à ces règles ne compte pas, et la liste le dit ; ceux d’avant (adoptée, confirmée) se lisent.

Un geste retient son texte : retouchée à la main, la version écrite par Atlas reste servie, et la liste le dit.

atlas consigne liste, par consigne : ● en vigueur, ⚠ mise en doute ou ✗ retirée, son identifiant, sa phrase ; dessous, sa cause datée, qui l’a écrite ou modifiée — l'IA (harnais), à la demande de alice, le 2026-10-09 —, sur quel fait, les écarts de l’IA. Puis illisibles, décisions métier, tronc commun et critères.

atlas consigne invalider exige un terminal : lancé par l’IA ou un script, refusé. confirmer et adopter sont refusés. La page Harnais invalide aussi.

Chercher, ajouter et amorcer

Chercher dans le Harnais : une question suffit, sans fichier ni feature. La recherche reste en évaluation. /atlas:harnais propose, montre, puis écrit, modifie ou invalide.

Le passage, sans que personne le lance : chaque moment signé finit par passage_harnais. L’IA relit les sources à signal de la feature, 12 à la fois, et en fait naître des consignes qui les citent : au symbole d’un fil de nœud, sinon dans un repo ou un dossier du diff. Le CLAUDE.md passe en premier, sur la moitié du lot au plus (l’importer). Il lit aussi ce que le hook garde sur ton poste, secrets filtrés : un test rouge ou un git restore après une écriture de l’IA (un démenti), ton prompt qui la corrige, nés au fichier qu’ils touchaient. Seules les lignes citées entrent ; le reste s’efface au passage, ou après 7 jours.

L’amorçage extrait des pistes des commits, documents et commentaires : /atlas:amorcer-harnais, sans ticket. Une piste classée Règle n’est pas une consigne. Vivante, le hook la sert à part, sans rien refuser. Dans Harnais → Amorçage historique, tu la mets de côté avec ta raison (ou l’IA, à ta demande) ; rien ne s’y active plus. Engagement, Méthode et Mémoire restent des pistes. Parcours, preuves et limites : Amorcer le Harnais.

Les critères, les cas et les décisions

Le Harnais sert aussi les critères de tes tickets et les cas de ton scénario de recette, et compte les décisions métier : Les critères, les cas et leur preuve.

La porte du workspace

Atlas tient une partie de .atlas-workspace/ : il y date, signe et met en forme ce qu’il écrit. La porte refuse à l’IA toute écriture à la main sur ces chemins, par l’éditeur comme par le shell, et lui dit par où passer :

sous .atlas-workspace/ par où l’IA passe
features/<id>/feature.json l’outil declare
les annotations, les fils, le parcours, le plan d’une feature les outils annotate, comment, parcours, plan
precedents/ l’outil sonde
harnais-historique/ l’outil amorcage_harnais, sans activation humaine
consignes/, cachets et passages compris les outils consigne et passage_harnais
la curation d’une feature (tes endossements) aucun outil : c’est ton geste
les recettes, le scénario de recette, socle/ la commande atlas recette (La recette)
project.json aucun outil : Config › Projet, ou ta main

Le refus nomme ce que le chemin contient et revient à chaque fois ; effacer ou déplacer un dossier qui les contient aussi.

Restent ouverts : la spec, ticket.md, que le skill ticket écrit dans ta session ; ce que la porte ne nomme pas (un POC, une stack maison) ; lire tout fichier du workspace ; écrire ailleurs à partir de l’un d’eux. Jugée sur le chemin seul, elle tient même sans instance. Elle ne concerne que l’IA.

La porte des moments

review, as-coded, answer et recette n’écrivent pas de code, mais le retrait de Write et Edit de leur skill ne vaut que le tour qui le lance. La porte des moments tient la règle d’un tour à l’autre : atlas moment <son nom>, lancé par le skill, l’ouvre pour l’agent qui le lance ; le hook refuse alors à chaque fois toute écriture dans un repo du projet, en disant comment en sortir. Du fil principal, elle tient aussi ses agents d’aide. Signer le moment, lancer resolve ou resolve-review, ou finir la session la ferme (atlas moment fin pour answer).

Le skill d’une écriture

Chaque écriture de l’IA dit de quel skill elle vient, par son champ skill : l’un des six moments — ticket, resolve, review, resolve-review, as-coded, recette —, answer, harnais, amorcer-harnais, ou aucun hors de tout skill.

Il est exigé par comment, annotate, parcours, consigne et le dépôt d’amorcage_harnais : sans lui, ou inconnu, l’écriture est refusée, la liste donnée. N’en demandent pas : ranger un fil, marquer une décision remplacée, une annotation qui ne touche que la structure de la carte. Un message qui signe un moment porte ce moment d’office ; un skill contraire est refusé. Les skills d’Atlas qui écrivent passent le leur ; le serveur MCP l’annonce à chaque ouverture.

La provenance d’un critère codé le dit, à l’IA comme sur la page Harnais : « (review) », « moment inconnu », « hors moment » (aucun).

⚠️ Après une mise à jour, redémarre ta session de code : un ancien outil sans ce champ fait refuser toutes ses écritures.

Ce qu’Atlas ne fait pas

  • Il ne vérifie pas que le code respecte une consigne : il la sert au bon moment, il ne remplace ni un test ni la CI.
  • Il n’approuve rien à ta place : le hook ajoute ou refuse, il n’autorise jamais un outil — les demandes de permission de Claude Code restent les tiennes.
  • Il ne fond pas consignes et précédents, et ne partage aucune consigne entre projets.

Limites connues

  • Le hook n’existe que dans Claude Code, avec le plugin : Gemini CLI et Codex, ou un serveur MCP déclaré à la main, n’ont ni service à l’endroit ni porte, ni porte des moments (règle par le texte du skill seul), et rien ne le signale ; seuls le tronc commun et ce que leur IA demande par l’outil harnais leur arrivent. Leurs traces sont « non garanties ».
  • Une commande qui écrit sans dire où n’est pas vue — un script qui ouvre un fichier, patch, git apply : ni consigne ni porte ; Atlas les compte (« gestes non garantis » sur la page Harnais), sans dire lesquels.
  • Les outils de recherche de Claude Code ne déclenchent rien : seuls lecture, écriture et shell passent par le hook.
  • Le terminal n’est pas une authentification : l’instance ne vérifie pas qui l’appelle — une porte qu’une IA ne prend pas par mégarde, pas une serrure. Ta demande (un fichier du poste) et un message humain (la route des fils) s’y forgent ; une spec réécrite ne dit pas qui l’a écrite.
  • Un casier de cachets illisible perd ses invalidations : la consigne repart servie, et le hook le dit — « non garanti », dans ce que l’IA reçoit.
  • Le tronc commun n’arrive qu’à l’ouverture : une session longue ne le reçoit pas une seconde fois.
