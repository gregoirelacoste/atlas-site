Le Harnais

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s'appliquent — et ce qu'Atlas lui garde fermé.

Les règles de ton projet et les critères de tes tickets, servis à ton IA là où ils s’appliquent — et ce qu’Atlas lui garde fermé.

Une consigne est une règle de ton projet, attachée à un endroit. Le Harnais la sert à l’IA quand elle y travaille, comme les critères de tes tickets. Elle fait autorité ; les décisions métier reviennent par leur contrat, les précédents comme des pistes.

Ce qu’est une consigne

Une consigne tient en une phrase qu’on peut coller dans une conversation, suivie de son pourquoi. Deux clés la rangent :

clé valeurs ce qu’elle dit
côté code · produit code : comment on construit ici. produit : ce que le produit garantit à qui s’en sert — une règle métier
nature éviter · faire · pourquoi · vérifier · métier éviter, faire, métier : une règle (son pourquoi est exigé quand l’IA l’écrit) ; vérifier ; pourquoi : une explication, technique côté code, métier côté produit

L’endroit : une ou plusieurs lignes où, chacune <sorte> <valeur>. Sept sortes sont servies :

tu écris ce que ça désigne
fichier projet-api/src/paiement/paiement.service.ts ce fichier : le repo membre, puis le chemin dans le repo
dossier projet-api/src/paiement tout fichier dessous, à la frontière d’un dossier : src/paiement ne couvre pas src/paiement2
famille migration tout fichier que les règles de nom de tes stacks et de project.json rangent dans cette famille
couche ctrl tout fichier dont le chemin prouve la couche ; sinon rien, et le geste compte « non garanti », à part
service projet-api tout fichier de ce repo membre
stack nest tout fichier d’un repo où elle est prouvée ou déclarée
geste git commit une commande que l’IA lance : ses mots entiers, dans l’ordre, options sautées

Un service ou une stack inconnu du projet est refusé, les noms existants dits. Quatre autres sortes se lisent sans être servies : symbole ou contrat projet-api::src/x.ts::Nom, une entrée (entrée POST /api/remboursements), un mot du vocabulaire du projet (mot panier). L’IA les lit par l’outil harnais (Ce que l’IA lit et écrit).

geste git commit touche git -C . commit comme cd projet-api && git commit, jamais git commit-tree. Un worktree hors du chapeau compte comme son repo principal.

Une consigne sans ligne où est du tronc commun : elle vaut partout, et l’IA la reçoit à l’ouverture de chaque session, pas à un endroit (plus bas).

Écrire une consigne

Chaque consigne est un fichier Markdown, .atlas-workspace/consignes/<id>.md, dont le nom est l’identifiant : minuscules, chiffres et tirets, 64 caractères au plus. Le dossier se partage avec le workspace (Configurer un projet). Exemple, migration-avec-down.md :

# Une migration s'écrit avec son retour arrière : jamais de down vide.
- côté: code
- nature: éviter
- où: famille migration
- où: dossier projet-api/src/migrations
- ticket: PROJ-380
- source: PROJ-380::t3a9c2f10

## Pourquoi
Un down vide a bloqué un retour arrière en production.
ligne ce qu’elle porte
# … (obligatoire) la consigne, 120 caractères au plus
- côté: · - nature: (obligatoires) voir plus haut ; produit va avec métier ou pourquoi
- sous: une précision libre : forme écartée, modèle à suivre, choix en attente, décision
- où: (répétable) un endroit ; aucun = tronc commun
- ticket: le ticket qui l’a fait naître
- source: (répétable) le fil qui la fonde, par sa clé <feature>::<fil> ; active, elle prend la place de ce précédent dans ses fichiers et dossiers (Les précédents)
## Pourquoi ce que la règle évite, ce qui a coûté
## Règle une règle métier en table Markdown : une ligne d’en-tête, puis une ligne par cas

Avant les sections, seules des lignes - clé: valeur. Un seul refus, et rien n’est lu : clé inconnue ou en double, autre section que Pourquoi ou Règle, endroit mal formé, source qui n’est pas une clé de fil, table illisible, phrase trop longue. Refusée, elle n’est servie à personne ; atlas consigne liste la montre précédée de ⚠.

⚠️ Le fichier porte le contenu, jamais la provenance. Une ligne - statut:, - origine:, - adoptee:, - confirmee: ou - invalidee: est refusée : « la provenance (statut, origine, adoption, confirmation) ne s’écrit pas dans le fichier : Atlas la pose au geste ».

Ce que l’IA reçoit, et quand

Le service automatique passe par un hook, lancé avant une lecture, une écriture ou une commande de Claude Code. atlas consigne --hook vient avec le plugin, installé par atlas plugin install (Brancher l’IA). Il demande à l’instance de ton projet quoi servir.

La reconnaissance lui dit ses limites de langage, capacité et manifeste : une stack non établie ne devient pas « absente ».

La première fois que l’IA touche un endroit dans une session, elle reçoit ses consignes, et ses critères (Les critères, les cas et leur preuve) :

ce que fait l’IA ce que fait le hook
elle lit un fichier — par l’éditeur, ou par une commande qui le nomme il ajoute les consignes à ce qu’elle lit ; l’outil passe
elle écrit un fichier dont elle n’a encore reçu aucune consigne dans la session il refuse l’écriture une fois si une règle est servie ; le reste s’ajoute sans refuser
elle lance une commande qu’une consigne geste désigne il ajoute la consigne ; la commande passe

Une règle refuse parce que ce qui est ajouté arrive après le geste. La tentative suivante passe ; une commande qui n’écrit aucun fichier (git commit) n’est jamais refusée.

Une écriture par le shell compte comme une écriture par l’éditeur quand Atlas sait lire ce qu’elle vise : une redirection (>, >>), tee, sed -i, mv, cp, rm, touch, git restore… — sur un fichier nommé par un chemin ou un nom à extension.

Le texte reçu a un bloc par famille, sous ses mots : « Règle … — à appliquer », « Engagement … — établi : garde-le, ou dis que ton ticket le change » (critères, cas), « Garde … — à vérifier après ton changement », « Contexte … — à savoir » ; puis, par élément, sa phrase et, entre parenthèses, l’endroit qui l’a fait arriver, d’où il vient — consigne adoptée par alice le 09-10, critère PROJ-412#3 · relu par as-coded le … — et la première ligne de son Pourquoi, jamais la table. Un refus tombe une fois, pour que tu lises ces règles.

Ce qui règle le choix :

  • une fois par endroit et par session : une consigne de dossier ne revient pas à chaque fichier touché dedans, mais par un autre de ses endroits, dans une nouvelle session, après un redémarrage de l’instance ou douze heures sans geste ;
  • la plus précise d’abord : un fichier ou une commande, puis un dossier (le plus profond d’abord), une famille, une couche, un service, une stack ; à précision égale, ce qui vient d’un humain, puis le produit, puis l’identifiant : ce que l’IA écrit ne chasse jamais les tiennes du plafond ;
  • cinq consignes et trois critères ou cas de recette au plus par geste, deux plafonds séparés. Au-delà, le texte le dit — « … et 2 autres au-delà du plafond, non servies. » — et ils comptent comme vus : une écriture n’est refusée qu’une fois.

Ce que ça coûte. Le hook tourne dans toutes tes sessions Claude Code, même hors projet. Mesuré le 14-10, hors démarrage de la commande : 32 à 40 ms par geste, 123 à 134 ms au premier de l’instance. Il ne bloque jamais : hors projet, sans instance, sur une réponse illisible ou de plus d’1,5 s, l’outil passe ; ce qui arrive trop tard revient au prochain geste au même endroit. Il ne démarre aucune instance : atlas, atlas start ou le serveur MCP, si.

Le tronc commun arrive autrement : à l’ouverture de la session. Le hook ne le sert jamais ; le serveur MCP le joint à ses instructions quand ta session démarre, quel que soit le client — Claude Code, Gemini CLI, Codex (Brancher l’IA). En font partie les consignes actives sans endroit, dans l’ordre du plafond — ce qu’un humain a adopté ou confirmé, puis le produit, puis l’identifiant — sous le titre « LES CONSIGNES DU PROJET (tronc commun) », chacune suivie de sa provenance.

Trois états : dix consignes au plus — au-delà, « … et 3 autres, au-delà du plafond de 10 : atlas consigne liste les montre. » ; rien sans consigne ou hors d’un projet Atlas ; « pas pu les lire (…) » avec la raison si l’instance ne répond pas à temps ou sert un autre projet. La liste en dit le poids, estimé sur la taille du texte.

La vie d’une consigne, gardée

Chaque réponse du hook arrivée à temps nourrit la vie d’une consigne : comptes, premier et dernier service, reprises après un refus — une écriture refusée puis rejouée au même fichier dans la même session. Les 200 dernières sessions par poste gardent gestes, poids estimé, refus et reprises.

L’instance garde cette vie en mémoire et l’écrit toutes les dix minutes au plus, et à l’arrêt : .atlas-workspace/consignes/vie/<ton adresse git>.<machine>.json. Deux machines font deux postes, additionnés. La page Harnais lit la mémoire locale et le disque partagé des autres. Chaque service laisse aussi une trace, dans le même casier : élément, session, canal, fichier, lignes écrites ensuite (Les critères, les cas et leur preuve).

Sans identité git, ton poste ne garde rien : la page le dit parmi les illisibles, avec la commande à lancer — puis atlas restart. Un casier illisible n’est jamais écrasé : ton poste n’y note rien jusqu’à réparation ; celui d’un autre poste compte parmi les illisibles.

Servie d’office, à regarder, invalidée

Toute consigne qui se lit est servie dès qu’elle existe, que l’IA l’ait écrite par son outil ou toi à la main, sans aucun geste. Elle reste à regarder tant qu’aucun humain ne l’a adoptée ou confirmée ; seule une retirée n’est plus servie.

Trois états, dits par leur cause : en vigueur, mis en doute, retiré — déduits des cachets et de l’index. Mise en doute, elle reste servie, avec sa cause : son ancre a changé, ou deux sessions IA l’ont déclarée perime ou contredit-code. hors-sujet et deja-su restent locaux. Retirée — invalidée, ou son fichier n’existe plus —, elle n’est plus servie mais reste lisible. Ta confirmation la remet en vigueur et devient la cause affichée. Le code se relit au build de l’index ; avant, « code pas regardé ».

geste par où à quelle condition
l’IA écrit l’outil consigne, geste ecrire ; Atlas écrit le fichier un identifiant libre (tiré de la phrase s’il manque), son ticket (sauf /atlas:harnais), une raison pour une règle ou une vérification, ni la phrase d’une invalidée, ni une phrase qui vit déjà là
l’IA écarte l’outil sonde, ecarte un élément servi, par sa clé, avec une raison parmi quatre (hors sujet · déjà su · périmé · contredit par le code) et un détail libre en plus — c’est ce que tu relis
tu confirmes atlas consigne confirmer <id> une consigne servie : tu gardes la version servie, elle n’est plus à regarder
tu adoptes atlas consigne adopter <id> une invalidée, ou une retouchée depuis son adoption : le fichier tel qu’il est, s’il se lit
tu invalides atlas consigne invalider <id> <la raison> une raison écrite, toujours

Le ticket d’une consigne que l’IA écrit : celui qu’elle donne, sinon celui du fil de son fait — jamais d’une source —, une feature déclarée du projet ; sans aucun, rien n’est écrit — sauf pour /atlas:harnais lancé par toi (le hook UserPromptSubmit le prouve, une demi-heure) ; sinon le ticket est exigé, toujours sans ce hook (Gemini CLI, Codex). Depuis un fil sans où non plus : la réponse liste les endroits du nœud, ou « tronc commun ».

Le doublon : même phrase au même endroit, casse, accents et blancs mis à part, refusée face à une consigne, un critère, un cas ou une décision. La réponse montre dix lignes au plus : comparaison de phrases, pas de sens.

Le fait, facultatif : la clé du fil qui la fonde. Atlas le vérifie — un humain y a répondu, ou le code a bougé depuis — et le garde dans sa provenance ; faux ou invérifiable, tout est refusé, avec pourquoi.

L’IA ne peut jamais modifier, adopter, confirmer ni invalider une consigne : aucun outil n’y mène, et la porte lui ferme le dossier.

Chaque geste laisse un cachet, posé par Atlas : qui (l’adresse de git config user.email dans le chapeau), quand, si tu l’as demandée (/atlas:harnais), sur quelle version du texte, la raison d’un écart ou d’une invalidation, et la session de l’IA qui écarte (celle du client ; sans elle, le serveur MCP, et la cause le dit) — jamais ce que l’appelant prétend. Les cachets vivent dans .atlas-workspace/consignes/cachets/, un fichier par auteur, jamais réécrits : le statut se déduit de leur suite. Sans identité git, aucun geste n’est posé. Un cachet contraire à ces règles ne compte pas : la liste dit ⚠ geste ignoré, et pourquoi.

Un geste retient son texte : retouché ensuite, même illisible, il reste servi, et la liste prévient « ⚠ retouchée depuis son adoption ». adopter sert la nouvelle, confirmer garde celle en vigueur.

atlas consigne liste se lit partout, même depuis un script : par consigne, ● en vigueur, ⚠ mise en doute ou ✗ retirée, son identifiant, sa phrase ; dessous, sa cause datée, à regarder : … servie d'office et la commande qui tranche, qui l’a adoptée — alice (IA), le 2026-10-09 quand l’IA de la session d’alice l’a écrite (l'IA de la session d'alice, à sa demande (harnais)) —, sur quel fait, les écarts de l’IA. Puis illisibles, décisions métier, tronc commun et critères (Les critères, les cas et leur preuve).

Les trois gestes exigent un terminal : lancés par l’IA ou un script, refusés — « « atlas consigne invalider » est un geste de l’humain : il se lance dans un terminal. » Un geste sans effet est dit, pas posé : adopter une consigne servie telle quelle (le refus dit de la confirmer), confirmer une invalidée ou une déjà confirmée, invalider deux fois. Aucun ne s’applique à un critère. La page Harnais les fait aussi, d’un clic.

Chercher, ajouter et amorcer

Chercher dans le Harnais : une question suffit, sans fichier ni feature. La recherche reste en évaluation. /atlas:harnais propose, montre, écrit, puis donne la commande de confirmation.

L’amorçage extrait des pistes des commits, documents et commentaires : /atlas:amorcer-harnais, sans ticket. Une piste classée Règle n’est pas une consigne active. L’import ne la sert ni au hook ni au tronc commun. Dans Harnais → Amorçage historique, tu actives une Règle, une Garde ou un Contexte : raison, lieu actuel et confirmation explicite exigés. Atlas crée une consigne de code adoptée par l’humain, avec sa provenance. Engagement, Méthode et Mémoire restent des pistes. Parcours, preuves et limites : Amorcer le Harnais.

Les critères, les cas et les décisions

Le Harnais sert aussi les critères de tes tickets et les cas de ton scénario de recette, et compte les décisions métier : Les critères, les cas et leur preuve.

La porte du workspace

Atlas tient une partie de .atlas-workspace/ : il y date, signe et met en forme ce qu’il écrit. La porte refuse à l’IA toute écriture à la main sur ces chemins, par l’éditeur comme par le shell, et lui dit par où passer :

sous .atlas-workspace/ par où l’IA passe
features/<id>/feature.json l’outil declare
les annotations, les fils, le parcours, le plan d’une feature les outils annotate, comment, parcours, plan
precedents/ l’outil sonde
harnais-historique/ l’outil amorcage_harnais, sans activation humaine
consignes/, cachets compris l’outil consigne
la curation d’une feature (tes endossements) aucun outil : c’est ton geste
les recettes, le scénario de recette, socle/ la commande atlas recette (La recette)
project.json aucun outil : Config › Projet, ou ta main

Le refus commence par « Atlas tient lui-même .atlas-workspace/… », nomme ce que le chemin contient et revient à chaque fois. Effacer ou déplacer un dossier qui contient ces fichiers est refusé aussi.

Restent ouverts : la spec, ticket.md, que le skill ticket écrit dans ta session ; ce que la porte ne nomme pas (un POC, une stack maison) ; lire tout fichier du workspace ; écrire ailleurs à partir de l’un d’eux. Jugée sur le chemin seul, elle tient même sans instance. Elle ne concerne que l’IA.

La porte des moments

review, as-coded, answer et recette n’écrivent pas de code, mais le retrait de Write et Edit de leur skill ne vaut que le tour qui le lance. La porte des moments tient la règle d’un tour à l’autre : atlas moment <son nom>, lancé par le skill, l’ouvre pour l’agent qui le lance ; le hook refuse alors à chaque fois toute écriture dans un repo du projet, en disant comment en sortir. Du fil principal, elle tient aussi ses agents d’aide. Signer le moment, lancer resolve ou resolve-review, ou finir la session la ferme (atlas moment fin pour answer).

Le skill d’une écriture

Chaque écriture de l’IA dit de quel skill elle vient, par son champ skill : l’un des six moments — ticket, resolve, review, resolve-review, as-coded, recette —, answer, harnais, amorcer-harnais, ou aucun hors de tout skill.

Il est exigé par comment, annotate, parcours, consigne et le dépôt d’amorcage_harnais : sans lui, ou inconnu, l’écriture est refusée, la liste donnée. N’en demandent pas : ranger un fil, marquer une décision remplacée, une annotation qui ne touche que la structure de la carte. Un message qui signe un moment porte ce moment d’office ; un skill contraire est refusé. Les neuf skills d’Atlas passent le leur ; le serveur MCP l’annonce à chaque ouverture.

La provenance d’un critère codé le dit, à l’IA comme sur la page Harnais : « (review) », « moment inconnu », « hors moment » (aucun).

⚠️ Après une mise à jour, redémarre ta session de code. Un ancien outil sans ce champ fait refuser toutes ses écritures. L’ancien proposer écrit et rend ecrire ; adopter est refusé.

Ce qu’Atlas ne fait pas

  • Il ne vérifie pas que le code respecte une consigne : il la sert au bon moment, il ne remplace ni un test ni la CI ; une reprise après un refus ne dit pas qu’elle a été suivie.
  • Il n’approuve rien à ta place : le hook ajoute ou refuse, il n’autorise jamais un outil — les demandes de permission de Claude Code restent les tiennes.
  • Il ne fond pas consignes et précédents, et ne partage aucune consigne entre projets.

Limites connues

  • Le hook n’existe que dans Claude Code, avec le plugin : Gemini CLI et Codex, ou un serveur MCP déclaré à la main, n’ont ni service à l’endroit ni porte, ni porte des moments (règle par le texte du skill seul), et rien ne le signale ; seuls le tronc commun et ce que leur IA demande par l’outil harnais leur arrivent. Leurs traces sont « non garanties ».
  • Une commande qui écrit sans dire où n’est pas vue — un script qui ouvre un fichier, patch, git apply : ni consigne ni porte ; Atlas compte ces gestes — la part « gestes non garantis » de la page Harnais —, sans dire lesquels.
  • Les outils de recherche de Claude Code ne déclenchent rien : seuls lecture, écriture et shell passent par le hook.
  • Le terminal n’est pas une authentification : l’instance ne vérifie pas qui l’appelle — une porte qu’une IA ne prend pas par mégarde, pas une serrure.
  • Un casier de cachets illisible perd ses invalidations : la consigne repart servie, et le hook le dit — « non garanti », dans ce que l’IA reçoit.
  • Le tronc commun n’arrive qu’à l’ouverture : une session longue ne le reçoit pas une seconde fois.
